2|第11.17章: 文件各层之间的关系
3|为什么这一章重要
4|到目前为止我们见到了六个文件类型家族：<code>wine</code>、<code>nt</code>、<code>win32</code>、<code>posix</code>、<code>c</code> 和 <code>filebuf</code>。它们看起来像是彼此平行、互不相干的 API &mdash; 但并不是。它们构成一个<strong>栈</strong>，每一层都是用下面那层实现的。
5|理解这个栈是良好使用 <code>fast_io</code> 的关键。它解释了为什么 <code>iobuf_file</code> 在每个平台上都“就是能用”、为什么你可以自由混用各层，以及 <code>native_file</code> 真正意味着什么。
6|层次结构
7|从最底层（最接近内核）到最高层：
8|<strong>第 1 层：</strong><code>wine</code>（最低层，Wine 翻译层）
9|<strong>第 2 层：</strong><code>nt</code> / <code>zw</code>（NT 内核接口，Nt* 与 Zw* 函数在用户空间完全相同）
10|<strong>第 3 层：</strong><code>win32</code>（Win32 API）
11|<strong>第 4 层：</strong><code>posix</code>（POSIX 文件描述符）
12|<strong>第 5 层：</strong><code>c</code>（C 标准库 FILE*）
13|<strong>第 6 层：</strong><code>filebuf</code>（C++ 标准库，最高层）
14|<strong>这 6 层在<em>所有</em>编程语言中都存在</strong>，不只是 C++。每种现代语言都建立在 C 或 C++ 运行时之上，或者直接使用同样的操作系统 API。当你在 Python、Java、Rust、Go 或任何其他语言里做文件 I/O 时，最终都要经过同样的这些层：
15|Python 的 <code>open()</code> 使用 CPython 的 C 实现，后者调用 libc
16|Java 的 <code>FileInputStream</code> 用 JNI 调用 C/C++ 代码
17|Rust 的 <code>std::fs::File</code> 直接调用操作系统 API，或者经由 libc
18|Go 的 <code>os.Open</code> 用 cgo 调用 C 函数，或者直接发起系统调用
19|Node.js 使用 libuv，而 libuv 包装 POSIX/Win32 API
20|理解这些层能帮你理解<em>任何</em>语言的文件 I/O 在底下是如何工作的，而不只是 C++。<strong>因此，理解它们对使用任何编程语言都至关重要</strong> &mdash; 无论是在 Python 里调试性能问题、理解 Java 的文件操作为何表现出某种行为，还是在 Rust 里优化 I/O，同样的原理都适用。
21|写成一串链条，箭头表示“建立在……之上”：
22|每一层都<strong>包装它下面那层</strong>。当这不可能时（因为下面那层没有暴露可用的 API），这一层就直接调用底层系统调用并包装<em>那个</em>。
23|层次图
24|这个层栈是<strong>平台相关</strong>的，并非每个平台都有全部层。下面是展示所有可能层的一般层次：
25|<strong>注意：</strong>这是一个简化的概览。实际的层取决于平台，并非每个平台都有全部层：
26|<strong>在 POSIX 系统上</strong>（Linux、macOS、FreeBSD）：只有第 4-6 层存在（libc POSIX fd、libc FILE*、filebuf）。第 1-3 层（wine、nt、win32）不存在。
27|<strong>在 Windows 上</strong>（原生）：第 2-6 层都存在（NT HANDLE、Win32 HANDLE、CRT fd、CRT FILE*、filebuf）。CRT 文件描述符（第 4 层）由 C 运行时（MSVCRT/UCRT）提供，内部是 HANDLE 的包装。
28|<strong>在 Wine 上</strong>：所有层都可能存在。Wine 把 Windows API 调用（第 2-3 层）翻译成宿主 POSIX 调用（第 4 层），再进入宿主内核。
29|下面是每个典型平台的详细图示。
30|在 POSIX 系统上（Linux、macOS、FreeBSD 等）
31|在 POSIX 系统上，这个栈很直接：C++ 标准库包装 libc，libc 同时提供 <code>FILE*</code> 和 POSIX 文件描述符，后者包装进入内核的系统调用。<code>FILE*</code> 与 POSIX 文件描述符都是 libc 的一部分。
32|在 Windows 上（原生）
33|在 Windows 上，CRT（C 运行时：MSVCRT 或 UCRT）同时提供 <code>FILE*</code>（第 5 层）和文件描述符（第 4 层）。文件描述符是 Win32 HANDLE 的包装 &mdash; 内部上，CRT 调用 <code>CreateFileW</code> 并保存 HANDLE，然后返回一个映射到该 HANDLE 的小整数文件描述符。你可以用 <code>_get_osfhandle(fd)</code> 与 <code>_open_osfhandle(handle, flags)</code> 在两者之间转换（见第11.14章）。
34|在 Wine 上（POSIX 宿主上的 Windows 程序）
35|在 Wine 上，Windows 各层（CRT、Win32、NT）都存在，但 Wine 把 NT 系统调用翻译成宿主 POSIX 系统调用。所以调用链经过 Wine 的翻译层（第 1 层），然后进入宿主的 libc，再进入宿主内核。这就是 Wine 程序能在 Linux、macOS 和 FreeBSD 上运行的原因。
36|每一层都对应一个真实的系统组件：
37|<strong>filebuf</strong> &mdash; C++ 标准库（<code>libstdc++</code>、<code>libc++</code>，或 MSVC 的 STL）。在 Windows 上它们以 <code>libstdc++-6.dll</code>（MinGW）、<code>libc++.dll</code> / <code>c++.dll</code>（LLVM libc++ &mdash; <code>${CPU}-windows-gnu</code> 用 <code>libc++.dll</code>，<code>${CPU}-windows-msvc</code> 用 <code>c++.dll</code>）或 <code>msvcp{version}.dll</code>（MSVC，例如 <code>msvcp140.dll</code>）的形式存在。
38|<strong>c</strong> &mdash; libc（<code>glibc</code>、<code>musl</code>、<code>msvcrt.dll</code>/<code>ucrt</code>）。<code>FILE*</code>、<code>fopen</code>、<code>fread</code>、<code>fprintf</code> 和 <code>printf</code> 住在这里。在 POSIX 系统上，libc 还提供 POSIX 文件描述符层（第 4 层）。
39|<strong>posix</strong> &mdash; POSIX 文件描述符与系统调用（<code>open</code>、<code>read</code>、<code>write</code>、<code>close</code>）。在 Linux/macOS/FreeBSD 上这是 libc 的一部分。在 Windows 上没有原生 POSIX 层（兼容层除外）。
40|<strong>win32</strong> &mdash; Windows 上的 <strong>kernel32.dll</strong>。<code>CreateFileW</code>、<code>ReadFile</code>、<code>WriteFile</code> 以及其他 Win32 文件 API 住在这里。这是“传统的”Windows API。
41|<strong>nt</strong> &mdash; Windows 上的 <strong>ntdll.dll</strong>。<code>NtCreateFile</code>、<code>NtReadFile</code>、<code>NtWriteFile</code> 以及其他原生 NT API 住在这里。这是<strong>真正的</strong> Windows 内核接口 &mdash; kernel32.dll 本身也是建立在 ntdll.dll 之上的。
42|<strong>zw</strong> &mdash; 也在 <strong>ntdll.dll</strong> 里。<code>ZwCreateFile</code>、<code>ZwReadFile</code>、<code>ZwWriteFile</code> 等。在用户空间，<code>Nt*</code> 与 <code>Zw*</code> 函数<strong>完全相同</strong> &mdash; 它们都调用进入内核。区别只在内核态：<code>Nt*</code> 函数校验指针参数（用于来自用户态的调用），而 <code>Zw*</code> 函数跳过参数校验（用于来自可信内核态代码的调用）。由于在用户空间行为相同，<code>fast_io</code> 把 <code>::fast_io::zw_file</code> 提供为 <code>::fast_io::nt_file</code> 的别名。
43|<strong>wine</strong> &mdash; Wine 的翻译层。在 Linux/macOS 上运行 Windows 程序时，Wine 把 NT 系统调用翻译成宿主 POSIX 系统调用。
44|所以当你调用 <code>std::fstream</code> 时，Windows 上的调用链是：C++ 标准库 &rarr; libc（MSVCRT/ucrt，<code>FILE*</code>）&rarr; kernel32.dll（<code>CreateFileW</code>）&rarr; ntdll.dll（<code>NtCreateFile</code>）&rarr; 内核。在 Linux 上则是：C++ 标准库 &rarr; libc（glibc/musl，<code>FILE*</code> 与 POSIX fd）&rarr; <code>open()</code>/<code>read()</code> 系统调用 &rarr; 内核。
45|<code>fast_io</code> 让你跳过一些层。如果你要不带缓冲地直接调用内核，就用 <code>native_file</code>；如果你需要与遗留代码兼容，就用 <code>c_file</code> 或 <code>filebuf_file</code>。你选适合自己需要的层。
46|在 Linux、FreeBSD 和 macOS 上只用 <code>posix</code> 分支。在 Windows 上使用 <code>nt</code> 与 <code>win32</code> 分支。只有在 POSIX 宿主上运行于 Wine 下时才使用 <code>wine</code> 分支。
47|<strong>平台可用性：</strong>
48|<code>wine_file</code> 只在为 Wine 编译时可用（运行在 POSIX 宿主上）。
49|<code>nt_file</code> 与 <code>win32_file</code> 只在 Windows（以及 Wine）上可用。
50|<code>posix_file</code> 在所有符合 POSIX 的系统（Linux、macOS、FreeBSD 等）上可用，在使用 POSIX 兼容层时在 Windows 上也可用。
51|<code>c_file</code> 与 <code>filebuf_file</code> 到处都可用，因为它们依赖 C 与 C++ 标准库。
52|<strong>重要：</strong>这些关系<strong>不是</strong>由 <code>fast_io</code> 定义的，而是由操作系统和编译器的 C/C++ 运行时供应商定义的。例如在 POSIX 系统上，libc 的 <code>FILE*</code> 是由 libc 实现（glibc、musl 等）建立在 POSIX 文件描述符之上的，而 C++ 标准库的 <code>::std::filebuf</code> 是由 C++ 运行时库建立在 <code>FILE*</code> 之上的。<code>fast_io</code> 只是总结并包装这些既有的关系 &mdash; 它不发明新的关系。

91|包装的黄金法则
92|<code>fast_io</code> 为<strong>每一</strong>层提供包装，而每个包装做两件事之一：
93|<strong>包装下面那层的 API。</strong>例如 <code>c_file</code> 建立在 <code>posix_file</code> 之上，因为 POSIX 上的 C 标准库本身就建立在 POSIX 文件描述符之上。
94|当下面的运行时没有暴露可用 API 时，<strong>直接调用更底层的系统调用</strong>。从 <code>c_file</code> 往下到 <code>posix_file</code> 时常常如此，因为 libc 并不公开暴露它内部的 fd &mdash; 于是 <code>fast_io</code> 直接发起系统调用并包装结果。
95|在层之间转换
96|当你在层之间移动时，方向决定方法：
97|<strong>由低到高</strong>（例如 <code>posix_file</code> &rarr; <code>c_file</code> &rarr; <code>filebuf_file</code>）：使用 <code>::std::move</code>。句柄的所有权被向上转移。
98|<strong>由高到低</strong>（例如 <code>filebuf_file</code> &rarr; <code>c_file</code> &rarr; <code>posix_file</code>）：用 <code>static_cast</code> 转换到底层的 <code>io_observer</code>。这给你一个对底层句柄的非拥有视图。

102|<strong><code>native_xxx</code> 是什么意思？</strong>
103|<code>::fast_io::native_file</code> 是 <code>fast_io</code> 在当前平台上想用的最低不带缓冲层的别名。它在编译期被选定：
104|<strong>Linux、FreeBSD、macOS 等</strong> &rarr; <code>::fast_io::native_file</code> = <code>::fast_io::posix_file</code>
105|<strong>Windows NT 家族</strong>（NT、2000、XP、7、10、11）&rarr; <code>::fast_io::native_file</code> = <code>::fast_io::nt_file</code>
106|<strong>Windows 9x 家族</strong>（95、98、ME）&rarr; <code>::fast_io::native_file</code> = <code>::fast_io::win32_file</code>
107|同样的别名规则适用于观察者：<code>native_io_observer</code> 在 POSIX 系统上是 <code>posix_io_observer</code>，在 Windows NT 上是 <code>nt_io_observer</code>。
108|带缓冲的类型 <code>basic_iobuf_file</code> 则是用 <code>basic_native_file</code> 定义的：
109|所以当你写 <code>::fast_io::iobuf_file f(u8"x.txt", open_mode::out);</code> 时，你得到的是建立在“<code>fast_io</code> 认为属于你平台的 native 层”之上的带缓冲 I/O。

119|要点
120|<strong>把这六层背下来。</strong>它们不是随意的 &mdash; 它们反映了操作系统和编译器运行时实际是如何实现文件 I/O 的。理解这个层次结构能解释 <code>FILE*</code> 为何有这样的行为、<code>mmap</code> 为何比 <code>fread</code> 快，以及不同 API 在底下是如何相互关联的。
121|这六层构成严格的层次：<code>wine =&gt; nt =&gt; win32 =&gt; posix =&gt; c =&gt; filebuf</code>。
122|每一层包装它下面那层。当下面那层没有暴露可用 API 时，<code>fast_io</code> 直接调用内核并包装那个。
123|<code>fast_io</code> 为<strong>每一</strong>层提供包装，并让你自由混用各层。
124|<code>native_xxx</code> 是 <code>fast_io</code> 在当前平台最低层想用的那一层：POSIX 系统上是 <code>posix_file</code>，Windows NT 上是 <code>nt_file</code>，Windows 9x 上是 <code>win32_file</code>。
125|你可以从系统调用级别的句柄出发，逐层移动构建出 <code>::std::fstream</code>：<code>posix_file</code> &rarr; <code>c_file</code> &rarr; <code>filebuf_file</code> &rarr; <code>::std::ofstream::rdbuf()</code>。
126|你也可以往反方向下降：<code>static_cast</code> 到合适的 <code>xxx_io_observer</code> 得到一个非拥有视图，而观察者暴露了原始原生句柄。
