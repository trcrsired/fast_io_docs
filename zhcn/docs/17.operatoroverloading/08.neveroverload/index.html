第17.8章 不该存在的运算符重载

English

1. 正好有两个没有任何可辩护的用法

在整个运算符集合里，正好有两种重载在任何程序里都是错的， 理由与风格无关：它们各自抹掉了语言对这个表达式做出的一个保证， 而且都是静默抹掉的。

其它一切都是需要判断的，而本章一直是这份判断的记录： 值类型上的 + 与 * （第17.3章）、 == 与 <=> （第17.4章）、 ++ 与 -- （第17.5章）、 []、*、-> 与 () （第17.7章）。 剩下两个运算符值得单独一节，因为它们既不是被禁止的，也不是安全的： && 和 || 在某些类型上完全合理， 在另一些类型上就是正确性 bug，而这个区别不属于口味问题（第4节）。

2. ,：无法被正确重载的运算符

内建的逗号运算符一次做两件事，而第二件才是要紧的。 它求值左操作数，然后在它之后求值右操作数，再丢弃左值。 逗号出现在真实代码里的唯一理由就是这个： for (i = 0, j = n; ...) 是把两条语句塞进一个子句， 并且对它们的顺序有一个保证。

重载的逗号是一次函数调用，而函数调用这两半都不给你。 操作数变成函数实参，所以它们之间没有顺序； "丢弃左值"也一并没有了：运算符返回什么都行。 


#include <fast_io.h>

/* the comma operator, overloaded: `a , b` becomes operator,(a, b) */
struct operand
{
	int tag{};
};

[[nodiscard]] inline operand operator,(operand a, operand b) throws
{
	::fast_io::io::print("  operator, ran\n");
	return b;
}

[[nodiscard]] operand make(int t) throws
{
	::fast_io::io::print("  make(", t, ")\n");
	return operand{t};
}

int main()
{
	try
	{
		::fast_io::io::println("built-in comma: two int values, sequenced left to right");
		(::fast_io::io::print("  left\n"), ::fast_io::io::print("  right\n"));

		::fast_io::io::println("overloaded comma: the operands are function arguments");
		auto const r = (make(0), make(1));
		::fast_io::io::println("  result tag = ", r.tag);
	}
	catch throws (::std::error e)
	{
		::fast_io::io::perrln("error: ", e);
	}
}

  left
  right
overloaded comma: the operands are function arguments
  make(0)
  make(1)
  operator, ran
  result tag = 1

输出里内建的那部分是有保证的：left 在 right 开始之前就已完成。 重载的那部分没有保证。两次 make() 都在 operator, 运行之前发生， 而编译器可以按任意顺序做它们 —— 这一次它先做了 make(0)， 而程序里没有任何东西规定必须如此。一个看到 a, b、 知道内建规则的读者，会读出一个"有顺序保证"的含义， 而那个类型刚刚把这个保证删掉了。

这件事没有补救办法，也没有哪种惯用法需要它。 如果你想让两件事按顺序发生，就写两条语句。 如果你想要一个构建器，就给它一个能看出累积过程的名字（add(a).add(b)）。 逗号运算符是从 C 继承来的，被少数"列表字面量"库重载； 代价由每一个逗号表达式的每一位读者付出 —— 他们要问一个本不该问的问题。

3. operator&：弄坏语言的那一个

允许 operator& 是个错误，而且不是小错误。 本章里另一个无药可救的重载是逗号（第2节），它破坏的是求值顺序。 operator& 破坏的是更根本的东西：C 程序有史以来指代一个对象所用的唯一操作。

在 C 里，&obj 就是“obj 的地址”。句号。 没有例外，没有类型能重新定义它，而语言里每一个接口都建立在这句话上： malloc 的结果是通过 &p 存下来的， scanf 通过 &n 写回，memcpy 收的是 &x。C++ 保留了这套语法，却允许任何类把这句话拿走： 


#include <fast_io.h>
#include <memory>

struct sneaky
{
	int v{};

	[[nodiscard]] sneaky *operator&() noexcept /* C++ lets you write this. Never write it. */
	{
		return nullptr;
	}
};

template <typename T>
[[nodiscard]] bool points_at_its_argument(T &ref) noexcept
{
	return &ref != nullptr; /* true for every type in the language, except the ones that lie */
}

int main()
{
	try
	{
		int plain{7};
		sneaky s{7};

		::fast_io::io::println("plain: &x != nullptr        ", ::fast_io::mnp::boolalpha(points_at_its_argument(plain)));
		::fast_io::io::println("sneaky: &x != nullptr       ", ::fast_io::mnp::boolalpha(points_at_its_argument(s)));
		::fast_io::io::println("&s == nullptr               ", ::fast_io::mnp::boolalpha(&s == nullptr));
		::fast_io::io::println("::std::addressof(s) == null ", ::fast_io::mnp::boolalpha(::std::addressof(s) == nullptr));
		::fast_io::io::println("s.v                         ", s.v);
	}
	catch throws (::std::error e)
	{
		::fast_io::io::perrln("error: ", e);
	}
}


plain: &x != nullptr        true
sneaky: &x != nullptr       false
&s == nullptr               true
::std::addressof(s) == null false
s.v                         7

把第三行和第四行放在一起读。&s 是 nullptr， 而这个对象活得好好的，就在一个真实地址上。没有诊断、没有警告、调用方也无从发现： 一个写 &ref 的模板 —— 也就是每个容器、每个包装、 每个排序算法、每个调试器都在做的事 —— 静默地收到了一个谎话。 这就是第二行那个 false，而第一行对语言里其它每个类型都是 true。

疤痕组织：std::addressof

标准库被逼着要有一条出路，而它就是一个只干一件事的函数： 


  template<typename _Tp>
    [[__nodiscard__,__gnu__::__always_inline__]]
    inline _GLIBCXX17_CONSTEXPR _Tp*
    addressof(_Tp& __r) noexcept
    { return __builtin_addressof(__r); }

  // _GLIBCXX_RESOLVE_LIB_DEFECTS
  // 2598. addressof works on temporaries
  template<typename _Tp>
    const _Tp* addressof(const _Tp&&) = delete;

这是 libstdc++ 的 <bits/move.h>，值得盯着看一会儿： std::addressof 不是算法，也不是库特性。 它是带标准名字的编译器魔法 —— __builtin_addressof —— 而它存在的全部理由，就是 & 不再表示 & 的含义了。 那个被 delete 掉的右值重载（LWG 2598）同理： 如果 & 保住了它的含义，这些措辞一个字都不需要。

所以这个特性的代价不是由重载它的那个类型付出的。 它是由世界上每个模板付出的 —— 它们现在必须写 ::std::addressof(x)， 而语言本该让它们写 &x；也是由每个读者付出的 —— 他必须知道 &x 不等于 x 的地址， 除非 x 的类型是某个拒绝了这项特性的人写的。 而且这份代价付得不均匀：你能不能用到 std::addressof， 取决于你的标准库，也取决于你是不是 freestanding。 第20章 会接着讲这件事， 因为在那里答案并不是"总是有"。

当年为什么允许？历史上的答案是 COM。在微软的对象模型里， 智能指针按惯例让 &p 回答一个 T**， 这样某个函数就能把新的接口指针装进去，调用点写成 CoCreateInstance(..., &p, ...)。 这个约定现在已经无法收拾：对每个模板来说，&p 是"p 的地址"； 对每个 COM 调用点来说，&p 是"p 内部那个 T* 的地址"； 而类型系统里没有任何东西能区分它们。 如果你想要那个输出参数的写法，就给它起个名字 —— p.address_for_init() —— 让 &p 保留它的含义。

对自己代码的规则没有例外：永远不要重载一元 &。 二元 & 也别重载，理由见 第17.3章 的算术论证 —— 如果你的类型有一个按位与，读者就必须知道用的是哪一种含义。 也不要设计一个必须靠它的接口：一个需要 &x 表示别的东西的类型， 有的是接口问题，而命名函数能解决它。

4. && 与 ||：不是错的，但要清楚它的代价

这两个不在上一张表里，也不该在。 在那些必须对"值"而不是对"控制流"建模的库里（掩码、lane 向量、位集）， 重载它们是常规做法；而在另一种代码里，它确实是一个真实的正确性 bug。 把这两种情况说清楚，值得一节。

失去的是什么：右操作数不被求值这件事。 用内建运算符时，a && b 在 a 为假时根本不会求值 b。用重载的版本时，b 是一个函数实参，所以它在调用之前就被求值了。 如果 b 是一个"求值本身就是目的"的表达式 —— 被空指针检查守卫的解引用、一个绝不能发生的调用 —— 那么这个守卫就不再守卫，而且没有任何东西会报告它： 


#include <fast_io.h>

/* explicit operator bool: usable in a boolean context, invisible everywhere else */
struct handle_flag
{
	bool open{};

	[[nodiscard]] constexpr explicit operator bool() const noexcept
	{
		return open;
	}
};

/* the right operand: proves whether it was evaluated */
[[nodiscard]] inline bool right() throws
{
	::fast_io::io::print("  right() was evaluated\n");
	return true;
}

struct short_circuit
{
	bool value{};

	[[nodiscard]] constexpr explicit operator bool() const noexcept
	{
		return value;
	}
};

namespace bad
{
struct gate
{
	bool value{};
};

/* a user-defined operator&&: both operands are evaluated before the call */
[[nodiscard]] inline bool operator&&(gate, bool b) noexcept
{
	return b;
}
}

int main()
{
	try
	{
		handle_flag const f{};
		::fast_io::io::println("static_cast<bool>(f) = ", static_cast<bool>(f), "   !f = ", !f,
							   "   (f + 1 would not compile)");

		::fast_io::io::println("builtin && with a false left operand:");
		bool const r1{static_cast<bool>(short_circuit{false}) && right()};
		::fast_io::io::println("  result = ", r1);

		::fast_io::io::println("user-defined operator&& with a false left operand:");
		bool const r2{bad::gate{false} && right()};
		::fast_io::io::println("  result = ", r2);
	}
	catch throws (::std::error e)
	{
		::fast_io::io::print("error: ");
		::fast_io::io::println(e);
	}
}

builtin && with a false left operand:
  result = 0
user-defined operator&& with a false left operand:
  right() was evaluated
  result = 1

内建的那次，输出里没有来自 right() 的那一行：它根本没被调用。 用户定义的那次，它在运算符运行之前就跑了。 当右操作数是一个"必须可以被跳过"的表达式时，这个重载是 bug —— 不是风格问题。

没有失去的是什么：当两个操作数都已经是一个值的时候，什么都没失去。 短路求值的存在是为了跳过某次求值；如果没有任何东西可跳过，也就没什么可失去的。 硬件掩码里没有控制流：左操作数是一个寄存器，右操作数是一个寄存器， "与"是一条指令。这正是重载 && 正确的场合 —— 包一层编译器的向量扩展类型，这里的 && 是按 lane 的合取， 而 & 反而是错误的拼写，因为在一个语义是"逐 lane 真假"的接口上， 它会读成按位与： 


#include <fast_io.h>
#include <cstdint>

/* the compiler's vector extensions: four 32-bit lanes in one register */
typedef ::std::int_least32_t lanes4 __attribute__((__vector_size__(16)));

struct mask4
{
	lanes4 lane{};

	/* element-wise "and". Both operands are already values, so there is no
	   right-hand side that short-circuiting could have skipped. */
	[[nodiscard]] friend mask4 operator&&(mask4 a, mask4 b) noexcept
	{
		return mask4{a.lane & b.lane};
	}
};

int main()
{
	try
	{
		mask4 const a{lanes4{-1, -1, 0, 0}};
		mask4 const b{lanes4{-1, 0, -1, 0}};
		mask4 const both{a && b};
		::fast_io::io::println("a       ", a.lane[0], " ", a.lane[1], " ", a.lane[2], " ", a.lane[3]);
		::fast_io::io::println("b       ", b.lane[0], " ", b.lane[1], " ", b.lane[2], " ", b.lane[3]);
		::fast_io::io::println("a && b  ", both.lane[0], " ", both.lane[1], " ", both.lane[2], " ", both.lane[3]);
	}
	catch throws (::std::error e)
	{
		::fast_io::io::perrln("error: ", e);
	}
}


a       -1 -1 0 0
b       -1 0 -1 0
a && b  -1 0 0 0

三条 lane 独立判定，一个表达式，没有分支、没有临时对象、也没有任何一个可以被跳过的操作数。 那个 && 不是"坏掉的 &&"； 它是唯一能让这个表达式仍然读起来像"对 lane 的逻辑运算"的拼写 —— 与本章其它地方同一个检验，只不过用在一个 && 的含义 恰好就是硬件本来具备的含义的类型上。

所以这两个的规则是关于操作数的，不是关于运算符的： 两边都已经是值时（掩码、位集、lane 向量、算好的 bool），可以重载； 右边是一个"你会被迫求值"的表达式时，不要重载。

5. 经验法则

  • 永远不要重载 ,。函数调用无法给它的实参排序， 而排序正是逗号运算符唯一要做的事。
  • 永远不要重载一元 &。它是 C 用来指代对象五十年的那个操作， 而补救办法 —— std::addressof —— 是编译器魔法， 现在每个模板都得调用它 （第3节）。
  • 两个操作数都已经是值时，重载 && 和 || 没问题， 因为短路求值没有东西可跳过；右操作数带副作用时，那就是 bug。 向量扩展的包装是标准的"可以"，被守卫的解引用是标准的"不可以"。
  • 不要在类级别写 operator new / operator delete （第18.7章）。
  • 其余的都要逐个判断，用 第17.2章 的四个问题。
