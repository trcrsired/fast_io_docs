第17.8章 不该存在的运算符

English

1. 五个永远错误的

有五个运算符在每个程序里都是错的，理由与风格无关。 每一个都不是口味问题：重载它就改变了语言对这个表达式所做的承诺。

运算符 重载它破坏了什么
&& 短路求值。a && b 变成一次函数调用， 所以即使 a 为假，b 也会被求值。 每个“先检查指针再解引用”的写法都静默失效。
|| 同上，另一边。
, 求值顺序。内建逗号运算符从左到右求值并丢弃左边结果； 重载之后它就是一次普通函数调用，实参的求值顺序是不确定的。
&（一元，取地址） 取地址。C 保持了半个世纪的一个特性， 也是语言最不该交出去的那一个 （第3节）。
operator T() 对转换的局部推理。程序里任何地方的任何隐式转换都可能调用它。 唯一的例外是 explicit operator bool，它在使用点被检查。

2. 把 && 量出来

关于短路的说法不是理论，而且很容易演示：把右操作数做成一个会宣告自己的函数， 然后比较内建运算符和用户定义运算符。 


#include <fast_io.h>

/* explicit operator bool: usable in a boolean context, invisible everywhere else */
struct handle_flag
{
	bool open{};

	[[nodiscard]] constexpr explicit operator bool() const noexcept
	{
		return open;
	}
};

/* the right operand: proves whether it was evaluated */
[[nodiscard]] inline bool right() throws
{
	::fast_io::io::print("  right() was evaluated\n");
	return true;
}

struct short_circuit
{
	bool value{};

	[[nodiscard]] constexpr explicit operator bool() const noexcept
	{
		return value;
	}
};

namespace bad
{
struct gate
{
	bool value{};
};

/* a user-defined operator&&: both operands are evaluated before the call */
[[nodiscard]] inline bool operator&&(gate, bool b) noexcept
{
	return b;
}
}

int main()
{
	try
	{
		handle_flag const f{};
		::fast_io::io::println("static_cast<bool>(f) = ", static_cast<bool>(f), "   !f = ", !f,
							   "   (f + 1 would not compile)");

		::fast_io::io::println("builtin && with a false left operand:");
		bool const r1{static_cast<bool>(short_circuit{false}) && right()};
		::fast_io::io::println("  result = ", r1);

		::fast_io::io::println("user-defined operator&& with a false left operand:");
		bool const r2{bad::gate{false} && right()};
		::fast_io::io::println("  result = ", r2);
	}
	catch throws (::std::error e)
	{
		::fast_io::io::print("error: ");
		::fast_io::io::println(e);
	}
}


static_cast<bool>(f) = 0   !f = 1   (f + 1 would not compile)
builtin && with a false left operand:
  result = 0
user-defined operator&& with a false left operand:
  right() was evaluated
  result = 1

内建的情形里，输出记录中没有任何来自 right() 的行 —— 它从未被调用。 用户定义的情形里，right() 在运算符执行之前就被求值了， 因为运算符就是函数，而函数的实参在调用之前求值。 如果你的类型需要“并且”的语义，就用 explicit operator bool 写 a && b，让语言自己去做；或者写一个命名函数 （both(a, b)、a.and_then(b)），让名字说出两边都会执行。

同一个程序里的 explicit operator bool 才是值得拥有的转换： 它在 if、while、! 和 && 里都能用，而其他场合一概不参与。这是编译期保证，不是约定： 


handle_flag f;
int x{f + 1};


error: no match for ‘operator+’ (operand types are ‘handle_flag’ and ‘int’)

对比 1998 年的替代方案 —— 不带 explicit 的 operator bool()： 它会转换成 int，于是 f + 1 能编译， f < g、f && x、if (f == true) 也都能编译，这个类型的含义就此溶解。explicit 就是 “一个行为像布尔的类型”和“一个在你不注意时变成整数的类型”之间的差别。

3. operator&：弄坏语言的那一个

允许 operator& 是个错误，而且不是小错误。 本章其它每一条破坏的都是一个便利：短路求值、顺序点、流的错误通道。 operator& 破坏的是 C 程序有史以来指代一个对象所用的唯一操作。

在 C 里，&obj 就是“obj 的地址”。句号。 没有例外，没有类型能重新定义它，而语言里每一个接口都建立在这句话上： malloc 的结果是通过 &p 存下来的， scanf 通过 &n 写回，memcpy 收的是 &x。C++ 保留了这套语法，却允许任何类把这句话拿走： 


#include <fast_io.h>
#include <memory>

struct sneaky
{
	int v{};

	[[nodiscard]] sneaky *operator&() noexcept /* C++ lets you write this. Never write it. */
	{
		return nullptr;
	}
};

template <typename T>
[[nodiscard]] bool points_at_its_argument(T &ref) noexcept
{
	return &ref != nullptr; /* true for every type in the language, except the ones that lie */
}

int main()
{
	try
	{
		int plain{7};
		sneaky s{7};

		::fast_io::io::println("plain: &x != nullptr        ", ::fast_io::mnp::boolalpha(points_at_its_argument(plain)));
		::fast_io::io::println("sneaky: &x != nullptr       ", ::fast_io::mnp::boolalpha(points_at_its_argument(s)));
		::fast_io::io::println("&s == nullptr               ", ::fast_io::mnp::boolalpha(&s == nullptr));
		::fast_io::io::println("::std::addressof(s) == null ", ::fast_io::mnp::boolalpha(::std::addressof(s) == nullptr));
		::fast_io::io::println("s.v                         ", s.v);
	}
	catch throws (::std::error e)
	{
		::fast_io::io::perrln("error: ", e);
	}
}


plain: &x != nullptr        true
sneaky: &x != nullptr       false
&s == nullptr               true
::std::addressof(s) == null false
s.v                         7

把第三行和第四行放在一起读。&s 是 nullptr， 而这个对象活得好好的，就在一个真实地址上。没有诊断、没有警告、调用方也无从发现： 一个写 &ref 的模板 —— 也就是每个容器、每个包装、 每个排序算法、每个调试器都在做的事 —— 静默地收到了一个谎话。 这就是第二行那个 false，而第一行对语言里其它每个类型都是 true。

疤痕组织：std::addressof

标准库被逼着要有一条出路，而它就是一个只干一件事的函数： 


  template<typename _Tp>
    [[__nodiscard__,__gnu__::__always_inline__]]
    inline _GLIBCXX17_CONSTEXPR _Tp*
    addressof(_Tp& __r) noexcept
    { return __builtin_addressof(__r); }

  // _GLIBCXX_RESOLVE_LIB_DEFECTS
  // 2598. addressof works on temporaries
  template<typename _Tp>
    const _Tp* addressof(const _Tp&&) = delete;

这是 libstdc++ 的 <bits/move.h>，值得盯着看一会儿： std::addressof 不是算法，也不是库特性。 它是带标准名字的编译器魔法 —— __builtin_addressof —— 而它存在的全部理由，就是 & 不再表示 & 的含义了。 那个被 delete 掉的右值重载（LWG 2598）同理： 如果 & 保住了它的含义，这些措辞一个字都不需要。

所以这个特性的代价不是由重载它的那个类型付出的。 它是由世界上每个模板付出的 —— 它们现在必须写 ::std::addressof(x)， 而语言本该让它们写 &x；也是由每个读者付出的 —— 他必须知道 &x 不等于 x 的地址， 除非 x 的类型是某个拒绝了这项特性的人写的。 而且这份代价付得不均匀：你能不能用到 std::addressof， 取决于你的标准库，也取决于你是不是 freestanding。 第20章 会接着讲这件事， 因为在那里答案并不是"总是有"。

当年为什么允许？历史上的答案是 COM。在微软的对象模型里， 智能指针按惯例让 &p 回答一个 T**， 这样某个函数就能把新的接口指针装进去，调用点写成 CoCreateInstance(..., &p, ...)。 这个约定现在已经无法收拾：对每个模板来说，&p 是"p 的地址"； 对每个 COM 调用点来说，&p 是"p 内部那个 T* 的地址"； 而类型系统里没有任何东西能区分它们。 如果你想要那个输出参数的写法，就给它起个名字 —— p.address_for_init() —— 让 &p 保留它的含义。

对自己代码的规则没有例外：永远不要重载一元 &。 二元 & 也别重载，理由见 第17.3章 的算术论证 —— 如果你的类型有一个按位与，读者就必须知道用的是哪一种含义。 也不要设计一个必须靠它的接口：一个需要 &x 表示别的东西的类型， 有的是接口问题，而命名函数能解决它。

4. << 和 >>：流运算符

这两个值得单独一节，因为它们是被过度使用最多的 C++ 运算符， 而且 第18.5章 已经说明 iostream 不能用：它们依赖虚继承、依赖跨 DLL 的 type_info 同一性、 依赖大多数平台上根本没有的异常处理。剩下还值得说的是： 即使 iostream 能用，为什么运算符这种形式也是错的。

  • << 表示两件不同的事。对整数它是位移； 对流它是“把这个值格式化进流并返回流”。同一个标点，两个不相干的操作， 靠“左操作数是不是流”来区分。
  • 它没有错误通道。失败被记录在流的状态位里， 所以 std::cout << a << b 不可能在你看得见的地方失败； 你必须记得以后检查 std::cout.fail()，而没人这么做。
  • 它隐藏方向。a >> b 读起来像比较， 实际是“从 a 读进 b”，而对大多数读者来说箭头指反了。
  • 它不能在一处被扩展。格式化策略（编码、宽度、进制、区域、缓冲） 必须绕着一个全局流对象传递，因为运算符没有地方放它们。

fast_io 的答案是两个命名函数加一个定制点： 调用侧的 ::fast_io::io::print(...) 和 ::fast_io::io::scan(...)， 类型侧的 print_define / scan_define （第15.11章）。 格式是实参，失败是 throws 契约， 而类型是由在它自己命名空间里找到的重载来打印的，不是一个全局运算符。

5. 那些“聪明”的运算符

还有一类不是按规则错误，而是实践中错误：标点代表的操作和这个标点所表示的意思不一样。

写成 实际含义 改成
路径上的 p1 / p2 用分隔符连接两个路径，分配一个新字符串 join(p1, p2)
标志位或集合上的 a | b 并集、按位或、或者把一个值管道进某个变换 —— 三种含义 set_union、with_flag
a & b 某些库里表示相似度 similarity(a, b)
a ^ b 某些库里表示对称差 symmetric_difference(a, b)
矩阵上的 a * b 视库而定，可能是会分配的乘法，也可能是逐元素乘 matmul(a, b)
把 a! 当阶乘 一次对 operator! 的调用，无法表达失败和大小 factorial(n)，并且注意它会溢出

把这张表和 第17.3章 区分开的，就是 第17.2章 那四个问题：如果这个操作会分配、会失败，或者在不同库里含义不同， 那它就不是算术操作，也就不该得到算术标点。

6. operator new 与 operator delete

类级分配函数是这一类里的最后一个成员，它单独占一页，因为这是唯一一种 不仅误导而且危险的场合：它改变了这个类型每个对象的分配策略， 在调用点看不见，无法被类型系统报告，并且把一个 ABI 决定焊进了你的头文件。 见 第18.7章。

7. 经验法则

  • 永远不要重载 &&、||、, 或 &。没有例外，而 & 是四者中最糟的： 它撕毁了 C 从 1972 年保持到今天的承诺，而修补它的代价， 是标准库多了一个叫 std::addressof 的编译器内建 （第3节）。
  • explicit operator bool 是唯一值得写的转换运算符。 其余的一律用命名函数（to_integer()、as_string()）。
  • 不要写 operator<< 或 operator>>。 用 print、scan 以及它们的定制点。
  • 如果标点的日常含义不是这个操作的含义，这个操作就要有一个名字。
  • 永远不要在类级别写 operator new / operator delete （第18.7章）。
