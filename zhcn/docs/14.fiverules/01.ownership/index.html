第14.1章：所有权：析构函数启动规则

English

1. 句柄不是值

::open 返回一个 int，但这个 int 不是文件。它是内核拥有的一张表里的 索引。第一个文件关闭后，同一个数字可以被另一个文件复用；复制这个数字也不会创建第二个文件。由此有三条性质：

  • 它必须被释放。表是有限的。一个永远不被 ::close 的描述符会泄漏一个槽位。
  • 它活着的时候只有一个所有者。两个对象都以为自己拥有同一个数字，就会都去释放它。
  • 数字不是资源。打开文件描述活在 kernel 里；数字只是句柄。

编译器不知道哪个 int 是句柄、哪个是计数。它用同样的方式复制所有 int。 这就是本章所有 bug 的来源。

2. 规则：析构函数改变拷贝

先写析构函数，因为它是告诉你“这个类拥有东西”的声明： 

class my_posix_file
{
    int fd_{-1};

public:
    explicit my_posix_file(::fast_io::cstring_view path, ::std::int_least32_t flags) throws;

    ~my_posix_file() noexcept
    {
        if (fd_ != -1)
        {
            ::close(fd_);
        }
    }
};

编译器仍然会为这个类生成拷贝构造和拷贝赋值。两者都复制 fd_。两者都产生一个自以为拥有同一个 描述符的对象。第一个析构函数关闭它；第二个析构函数再次关闭这个数字，而它现在可能属于一个无关的文件。 这不是理论问题。

如果一个类有释放资源的析构函数，它必须声明拷贝操作。删除它们，或者写一个正确的拷贝。 留着隐式版本就是 bug。

警告：只有析构函数、没有拷贝决定，就是 bug。 如果类有析构函数，却没有 = delete，也没有真正的拷贝构造/拷贝赋值，编译器会生成浅拷贝。 对资源所有者来说，这就是重复释放、释放后使用，或者两者都有。至少写： 
T(T const &) = delete;
T &operator=(T const &) = delete;
然后再决定类型是否还要可移动。

安全的默认是删除： 

    my_posix_file(my_posix_file const &) = delete;
    my_posix_file &operator=(my_posix_file const &) = delete;

这些是声明，不是注释。它们参与重载决议，任何拷贝都会被编译器拒绝。如果类型应该可移动，接着声明移动操作； 如果不该，就也删除它们： 

    my_posix_file(my_posix_file &&other) noexcept;
    my_posix_file &operator=(my_posix_file &&other) noexcept;

“也许移动操作”这个说法是对的。移动是另一种能力。不可移动类型删除全部四个拷贝/移动操作，只保留析构和 获取资源的构造。可移动类型实现两个移动、删除两个拷贝。你不能做的是把拷贝留给隐式版本。

3. C++ Primer 的例子

《C++ Primer》第五版用 HasPtr 演示这个失败：类通过裸指针拥有一个 std::string，在析构函数里释放它，却没有写拷贝操作。书里用 new 和 delete。本教程用 fast_io 的分配器和显式 placement new 做同一个例子，让分配策略可见。

分配器有两层。::fast_io::native_global_allocator 是非类型化分配器：它发放原始字节。 ::fast_io::native_typed_global_allocator<T> 是类型化适配器：它的 allocate_die(1) 为一个 T 预留正确大小和对齐的存储。两者都不构造对象。 placement new 才构造： 

#include <new>
#include <string>

using string_alloc = ::fast_io::native_typed_global_allocator<::std::string>;

std::string *make_string(std::string const &s)
{
    auto *p{string_alloc::allocate_die(1)}; // storage, not an object
    try
    {
        return ::new (static_cast<void *>(p)) std::string(s); // placement new
    }
    catch (...)
    {
        string_alloc::deallocate_n(p, 1);
        throw;
    }
}

void destroy_string(std::string *p) noexcept
{
    if (p != nullptr)
    {
        p->~basic_string();               // end the object's lifetime
        string_alloc::deallocate_n(p, 1); // return the storage
    }
}

allocate_die 在分配失败时终止，这是本书的策略；allocate 和 allocate_try 是会抛出的变体。重要的是生命周期被拆开了：分配给你存储，placement new 开始对象， 析构函数结束对象，deallocate_n 归还存储。没有 delete，也没有“产生块的分配器” 和“释放块的分配器”不匹配的问题。 

class HasPtr
{
public:
    HasPtr(std::string const &s = std::string())
        : ps{make_string(s)}, i{} {}

    ~HasPtr() { destroy_string(ps); }

    // WRONG: the compiler generates these two.
    // They copy ps, not the string.
    // HasPtr(HasPtr const &) = default;
    // HasPtr &operator=(HasPtr const &) = default;

private:
    std::string *ps;
    int i;
};

按值传一个，bug 就出现了： 

HasPtr f(HasPtr hp)      // hp is a shallow copy
{
    HasPtr ret = hp;     // another shallow copy
    return ret;          // hp and ret are destroyed
}

int main()
{
    HasPtr p{"some values"};
    f(p);                // both destructors destroy p.ps
    HasPtr q{p};         // p.ps is already dangling
}

参数和局部拷贝共享同一个 ps。f 返回时，两个析构函数在同一个指针上运行： 重复析构和重复归还。调用者的对象留下悬空指针，所以下一次拷贝读到已释放内存。析构函数是对的；隐式拷贝不是。

修复有两个显式选择。如果拷贝没有意义，删除它： 

    HasPtr(HasPtr const &) = delete;
    HasPtr &operator=(HasPtr const &) = delete;

现在 f(p) 和 HasPtr q{p} 不能编译。如果拷贝有意义，写一个分配自己 string 的 真正拷贝；那是第14.3章和 第14.4章。

4. Chromium 也遇到过同一个 bug

这不只是教学例子。Chromium 的 ChromeDriver 130 发布说明记录了一次五法则清理：某个类声明了类外析构函数， 却没有匹配的移动操作，于是编译器静默回退到拷贝。修复补上了缺失的声明。相关改动是 crrev.com/c/5846757，跟踪 issue 是 crbug.com/364788123。

编译器接受了代码。症状出现在别处。这就是缺失特殊成员的签名：语言给你一个默认值，而默认值对所有者来说是错的。 HasPtr 是同一个失败的最小版本；Chromium 是同一个失败在大规模代码库里的重复。

5. 这一章构建什么

贯穿的示例是一个 move-only 文件： 

class my_posix_file
{
    int fd_{-1};

public:
    my_posix_file() noexcept = default;
    explicit my_posix_file(::fast_io::cstring_view path, ::std::int_least32_t flags) throws;

    ~my_posix_file() noexcept;

    my_posix_file(my_posix_file const &) = delete;
    my_posix_file &operator=(my_posix_file const &) = delete;

    my_posix_file(my_posix_file &&other) noexcept;
    my_posix_file &operator=(my_posix_file &&other) noexcept;

    void swap(my_posix_file &other) noexcept;

    [[nodiscard]] bool is_open() const noexcept;
    [[nodiscard]] ::std::int_least32_t native_handle() const noexcept;
};

文件描述符是身份，不是值。同一个文件可以有两个描述符，但那是显式系统调用（::dup）， 不是编译器应该背着你做的事。删除拷贝明确表达了这一点。移动仍然有用：从工厂返回文件、放进容器， 或者把所有权传给另一个作用域。

fast_io 自己的文件类型做同样的选择：可移动，不可拷贝。这里缩减后的类只保留规则需要的东西， 所以每个声明都能和页面上的代码对照。

6. 五个成员，一个决定

声明 它回答的问题 对这个类
~my_posix_file() 谁关闭描述符？ ::close，一次，在一个地方。
my_posix_file(my_posix_file const&) 拷贝拥有什么？ = delete：拷贝就是第二个所有者。
operator=(my_posix_file const&) 拷贝赋值发生什么？ = delete，同样的原因。
my_posix_file(my_posix_file&&) 所有权如何转移？ 取走 fd_，留下 -1。
operator=(my_posix_file&&) 所有权如何替换？ 关闭自己的，取走对方的，清空源。

决定不是“五个函数全写或全不写”。决定是“这个类拥有资源吗？”如果拥有，析构函数启动规则， 拷贝操作是你必须先明确的东西。
