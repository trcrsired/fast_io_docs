第14章：五法则

English

1. 这条规则不是“写五个函数”

这个名字有误导性。五法则不是说每个类都应该手写五个特殊成员函数。它说的是这五个特殊成员是一个 整体：如果你声明了其中一个，就必须决定另外几个怎么办。大多数类一个都不该声明。拥有资源的类必须 声明它需要的那些。

《C++ Primer》先讲拷贝构造、拷贝赋值和析构，再给出规则。本章从析构函数开始，因为析构函数是警告信号： 一旦类说“我释放资源”，拷贝问题就被逼出来了。机制相同；这个顺序是为了更早暴露 bug。

真正危险的情况比名字暗示的更小、更尖锐：

如果一个类有释放资源的析构函数，编译器生成的拷贝构造函数和拷贝赋值几乎一定是错的。 把它们声明为 = delete，或者写一个正确的拷贝。绝不要留着隐式版本。

析构函数在说“这个对象拥有东西，必须释放”。隐式拷贝在说“复制句柄”。这两句话不能同时为真。 结果就是两个对象都以为自己拥有同一个资源：重复释放、释放后使用，或者两者都有。

警告：没有 = delete 的析构函数就是 bug。 如果你写了析构函数，却把拷贝操作留给隐式版本，编译器会浅拷贝句柄。至少把两个拷贝操作都声明为删除。 如果类型还可移动，声明移动；如果不可移动，把移动也删除。

2. C++ Primer 的 HasPtr：最小的 bug

《C++ Primer》第五版在拷贝控制章节用了这个例子。类通过裸指针拥有一个 std::string，在析构函数里释放它，却把拷贝构造和拷贝赋值留给编译器。分配辅助函数 make_string 和 destroy_string 使用 fast_io 的分配器和 placement new； 它们在第14.1章介绍。 

class HasPtr
{
public:
    HasPtr(std::string const &s = std::string())
        : ps{make_string(s)}, i{} {}

    ~HasPtr() { destroy_string(ps); }

    // WRONG: copy construction and copy assignment are compiler-generated.
    // They copy ps, not the string.

private:
    std::string *ps;
    int i;
};

现在按值传一个： 

HasPtr f(HasPtr hp)      // hp is a copy of the argument
{
    HasPtr ret = hp;     // another copy of the same pointer
    // ...
    return ret;          // ret and hp are destroyed here
}

int main()
{
    HasPtr p{"some values"};
    f(p);                // hp and ret both delete p.ps
    HasPtr q{p};         // p.ps is already dangling
}

参数 hp 是 p 的浅拷贝：它持有同一个 ps 指针。局部对象 ret 又是另一个浅拷贝。f 返回时，两个析构函数都运行，都对同一个指针调用 delete。这是重复释放。调用者的 p 留下悬空指针，所以下一个 HasPtr q{p} 复制的是一个已经失效的指针。bug 不在析构函数里；bug 在编译器写的拷贝里。

修复不是一句注释，而是一个声明： 

class HasPtr
{
public:
    HasPtr(std::string const &s = std::string())
        : ps{make_string(s)}, i{} {}

    ~HasPtr() { destroy_string(ps); }

    HasPtr(HasPtr const &) = delete;
    HasPtr &operator=(HasPtr const &) = delete;

private:
    std::string *ps;
    int i;
};

f(p) 和 HasPtr q{p} 现在不能编译。这正是目的：bug 从运行时移到了编译期。 如果拷贝有明确含义，另一种选择是写真正的拷贝构造和拷贝赋值，分配一个新的 string；两个选择是 “删除”和“实现”，永远不是“交给编译器”。

3. Chromium 为这个 bug 付过代价

这不是只存在于教科书里的问题。Chromium 的 ChromeDriver 130 发布说明记录了一次跨类的五法则清理： 某些类声明了类外析构函数，却没有匹配的移动操作，于是编译器静默回退到拷贝。缺失的声明后来被补上， 原因正是上面那条：析构函数加隐式拷贝就是一个等着发生的所有权 bug。

相关改动是 crrev.com/c/5846757，跟踪 issue 是 crbug.com/364788123。修复本身是机械的，但发现它并不机械：编译器接受了代码，症状出现在 别处。这就是缺失特殊成员声明的签名。

C++ Primer 的 HasPtr 是同一个失败的最小版本。Chromium 是同一个失败在大规模代码库里的 重复。两个尺度上，规则是一样的。

4. 五个成员是一个整体

成员 它决定什么 如果你拥有资源
~T() 资源如何释放 写它。这条声明启动整条规则。
T(T const&) 拷贝时新对象拥有什么 = delete，或者分配/复制一个真正的资源。
operator=(T const&) 赋值后已有对象拥有什么 = delete，或者释放旧的、获取真正的新的。
T(T&&) 如何取走将死对象的资源 类型应可移动就实现；否则删除。
operator=(T&&) 已有对象如何接管并清空源 类型应可移动就实现；否则删除。

如果类有用户声明的析构函数、拷贝构造或拷贝赋值，编译器不会生成移动构造和移动赋值。这就是为什么 单独一个析构函数会静默地把你留给拷贝，也是为什么“删除拷贝”之后通常要跟着“写移动”或“连移动也删除”。

最好的结果仍然是零法则：根本不拥有裸资源。把 int 放进一个已经实现 这条规则的类型里，让组合替你生成特殊成员。这一章讲的是你做不到零法则的那一天。

5. 两个示例

本章用两个所有者来教同一条规则。第一个是内存：C++ Primer 的 HasPtr，它通过 fast_io 的 native_typed_global_allocator<std::string> 分配存储，用 placement new 构造 string，在析构函数里显式调用析构并归还存储。第二个是文件描述符： my_posix_file，它拥有一个 POSIX 描述符，用 ::open 获取、::close 释放。它刻意是 move-only 的，和 fast_io 自己的文件类型一样：描述符是身份，不是值，所以不允许拷贝。 骨架是： 

class my_posix_file
{
    int fd_{-1};

public:
    my_posix_file() noexcept = default;
    explicit my_posix_file(::fast_io::cstring_view path, ::std::int_least32_t flags) throws;

    ~my_posix_file() noexcept;

    my_posix_file(my_posix_file const &) = delete;
    my_posix_file &operator=(my_posix_file const &) = delete;

    my_posix_file(my_posix_file &&other) noexcept;
    my_posix_file &operator=(my_posix_file &&other) noexcept;

    void swap(my_posix_file &other) noexcept;
};

拷贝操作不是“漏了”，而是在类里显式删除的。这就是一个能编译的类和一个正确的类之间的区别。

7. 怎么读这一章

把 14.1 和 14.2 当作规则来读。把 14.3 和 14.4 当作拷贝的两种合法答案来读：删除它，或者写一个真正的 拷贝。读 14.5 和 14.6，因为大多数拥有资源的类型即使不能拷贝也应该可以移动。把 14.7 到 14.10 当作让正确实现安全的机制。把 14.11 当作完整的类。

如果你的类没有裸资源，停在零法则：五个都不写，让编译器做它该做的事。这一章其余部分只适用于真正拥有 东西的类。
