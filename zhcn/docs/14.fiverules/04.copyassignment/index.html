第14.4章：拷贝赋值：删除，或者使用临界行

English

1. 拷贝构造和拷贝赋值是一个决定

拷贝构造创建新对象。拷贝赋值修改一个已经拥有东西的已有对象。它们是不同操作，但回答同一个策略问题： 这个类型允许第二个所有者吗？

如果答案是否，两个都删除： 

    my_posix_file(my_posix_file const &) = delete;
    my_posix_file &operator=(my_posix_file const &) = delete;

拷贝构造被删除、拷贝赋值却可用，几乎总是错误。两个操作应该一致，而编译器不会替你强制。把这一对在类里写清楚。

警告：只删除一对中的一个是不完整的。 如果你写了 T(T const &) = delete;，却把拷贝赋值留给隐式版本，编译器仍然可能生成一个浅拷贝句柄的 赋值。两个都删除，或者两个都实现。

2. 如果选择拷贝：临界行

赋值有一个构造没有的问题：左边对象已经拥有资源。函数必须释放旧资源并获取新资源。唯一的问题是顺序， 而错误的顺序是所有人最先写出的那个： 

    // WRONG: destroy first
    HasPtr &operator=(HasPtr const &other)
    {
        destroy_string(ps);              // old string gone
        ps = make_string(::fast_io::string_view{other.ps->data(), other.ps->size()}); // no failure here, but old value is gone
        i = other.i;
        return *this;
    }

如果克隆可能失败，对象已经失去了旧值，又没有新值可替换。fast_io::string 是 noexcept 的， 所以这个特定的克隆不会失败；但这个顺序仍然是克隆可能失败时应该使用的模式。把可能失败的步骤先做进局部变量， 此时对象还没被碰： 

    HasPtr &operator=(HasPtr const &other)
    {
        auto *new_ps{make_string(::fast_io::string_view{other.ps->data(), other.ps->size()})}; // clone first, *this untouched
        destroy_string(ps);                   // ---- critical line ----
        ps = new_ps;
        i = other.i;
        return *this;
    }

线上方：克隆在一般情况下可能失败（这里不会），*this 没变。线下方： destroy_string 和指针/整数写入都不会失败，所以对象从旧值移动到新值，没有中间损坏状态。 当克隆可能失败时，这就是强异常安全保证。

这个顺序也让自赋值不需要特判。如果 this == &other，新 string 在旧指针被销毁之前分配并拷贝， 然后替换指针。对象最终拥有一个新 string，值相同。没有数据丢失。

3. 完整的深拷贝类

class HasPtr
{
public:
    HasPtr(::fast_io::string_view s = {})
        : ps{make_string(s)}, i{} {}

    HasPtr(HasPtr const &other)
        : ps{other.ps ? make_string(::fast_io::string_view{other.ps->data(), other.ps->size()}) : nullptr},
          i{other.i}
    {
    }

    HasPtr &operator=(HasPtr const &other)
    {
        auto *new_ps{other.ps ? make_string(::fast_io::string_view{other.ps->data(), other.ps->size()}) : nullptr};
        destroy_string(ps);
        ps = new_ps;
        i = other.i;
        return *this;
    }

    ~HasPtr() { destroy_string(ps); }

private:
    ::fast_io::string *ps;
    ::std::size_t i;
};

这个类可拷贝，所以它还必须处理移动操作，或者接受移动回退到拷贝。移动是另一个决定；见 第14.5章和 第14.6章。这里的重点是拷贝赋值是显式的： 它知道旧资源，并且有临界行。

4. 返回类型与自检

按引用返回 *this，让赋值可以串联，并像内建赋值一样工作： 

a = b = c; // parsed as a = (b = c)

当你在销毁前分配时，不需要自检。当实现先释放时，才需要，因为 a = a 会在读取值之前销毁它。如果你写了安全顺序，不要因为教程都这么写就加检查；如果你写了不安全顺序， 检查也不足以修复失败路径。

同样的推理适用于移动赋值，但顺序是被迫的：移动没有副本可分配，所以必须先释放，因此必须检查自移动。 这个不对称在第14.6章。

5. 两个合法答案

所有权 拷贝构造 拷贝赋值
唯一（文件、socket、锁） = delete = delete
可拷贝，带真实资源（深拷贝） 分配/复制新资源 先分配，再在临界线下方提交

没有第三行叫“交给编译器”。如果类有析构函数，那一行就是 bug。

6. 需要记住什么

  • 一起删除拷贝构造和拷贝赋值，或者一起正确实现。
  • 赋值必须释放旧资源，但只能在新资源安全之后。
  • 临界行把可能失败的准备和不会失败的提交分开。
  • 先分配再销毁；自赋值就不需要特判。
  • 按引用返回 *this。
  • 移动赋值顺序相反，而且确实需要自检。
