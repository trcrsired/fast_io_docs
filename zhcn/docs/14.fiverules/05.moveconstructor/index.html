第14.5章: 移动构造函数：接管资源

English

1. 对拥有者来说移动意味着什么

复制必须产生第二个描述符，因为两个对象都要活下去。移动则不必：源对象即将被销毁，所以目标可以直接接管描述符，并把源对象留空。

没有系统调用，没有内核表里的第二个条目，也不会失败：两次 int 写入。这就是语言引入 && 参数的全部理由。 


	my_posix_file(my_posix_file const &) = delete;
	my_posix_file &operator=(my_posix_file const &) = delete;

	my_posix_file(my_posix_file &&other) noexcept : fd_{other.fd_}
	{
		other.fd_ = -1; // the source no longer owns anything
	}

两行都重要。没有第二行，描述符就会有两个所有者：目标会关闭它，然后源的析构函数会再次关闭同一个数字 — 可能那时它已经被交给一个无关的文件了。

2. 如果你不写，std::move 会去复制

这是每个人都会踩一次的陷阱。::std::move 什么也不移动；它是一次到右值引用的强制转换，它所做的只是让移动构造函数成为候选。如果没有移动构造函数，就会改用复制构造函数，而这并不是错误： 


#include <fast_io.h>
#include <fast_io_dsal/string_view.h>

using namespace ::fast_io::io;

class only_copy
{
	int fd_{-1};

public:
	explicit only_copy(::fast_io::cstring_view path, ::std::int_least32_t flags) throws
	{
		::std::int_least32_t fd{::open(path.c_str(), flags, 0644)};
		if (fd == -1) [[unlikely]]
		{
			throw throws static_cast<::std::errc>(errno);
		}
		fd_ = fd;
	}

	only_copy(only_copy const &other) throws : fd_{::dup(other.fd_)}
	{
		if (fd_ == -1) [[unlikely]]
		{
			throw throws static_cast<::std::errc>(errno);
		}
	}

	~only_copy() noexcept
	{
		if (fd_ != -1)
		{
			::close(fd_);
		}
	}

	[[nodiscard]] bool is_open() const noexcept
	{
		return fd_ != -1;
	}

	[[nodiscard]] ::std::int_least32_t native_handle() const noexcept
	{
		return fd_;
	}
};

int main()
{
	{ // make sure the example file exists
		::std::int_least32_t fd{::open("demo.txt", O_WRONLY | O_CREAT, 0644)};
		::close(fd);
	}

	only_copy a{"demo.txt", O_RDONLY};
	println("a = ", a.native_handle());

	only_copy b{::std::move(a)}; // no move constructor: this calls the copy constructor
	println("b = ", b.native_handle(), ", a = ", a.native_handle(), ", a.is_open() = ", a.is_open());
}


a = 3
b = 4, a = 3, a.is_open() = 1

a 仍然拥有 3，b 拥有一个新复制出来的 4。这次移动悄悄变成了复制 — 对文件来说是一次白费的系统调用，对更大的东西来说是白费的深拷贝。

只有当你没有写复制构造函数、复制赋值、移动赋值或析构函数中的任何一个时，编译器才会生成移动构造函数。我们的类把这些全写了，所以全都要我们自己写。这也是“写五者之一，就得到五者全部”并非传说的原因：它是一条决定编译器愿意生成什么的规则。

对 move-only 类型，回退方式不同：拷贝构造被删除，所以 ::std::move(a) 不会静默拷贝， 而是编译失败。这是正确结果。如果类型应该可移动，就声明移动构造；如果不该，就也删除移动， 把所有权留在一个地方。

3. 为什么 noexcept 不是可选项

在我们的类里，以及在每个拥有资源的严肃类里，移动构造函数都是 noexcept。这不是礼貌。容器通过移动元素来重新分配，而只有在移动不会在重新分配中途失败时，它们才能这么做。fast_io 的容器会在编译期检查这一点： 


error: static assertion failed: vector element types must be nothrow move constructible
       or trivially relocatable

把移动构造函数的 noexcept 改成 throws，你就得到针对 ::fast_io::vector<my_posix_file> 的那条诊断。容器不是在吹毛求疵；如果一次重新分配的第 5 次移动失败，它没有任何办法把元素放回去。

在赫布异常下，这个承诺比通常更强。noexcept 函数不能调用 throws 函数，除非它自己处理失败： 


error: call to a 'throws' or 'return_failure{E}' function must be handled by an enclosing
       'try { } catch throws', or the calling function needs a herbceptions specification
       so the error can propagate

所以 noexcept 不是一个可以在运行期违背的承诺；它是编译器通过检查函数体里每一次调用来验证的主张。即使你想，移动构造函数也不能调用 ::dup。

4. 源对象是空的，但没死

移动之后 other.fd_ 是 -1，而那是该类的一个有效状态，不是损坏：

  • 它的析构函数运行时什么都不关闭；
  • is_open() 返回 false；
  • 给它赋一个新文件会让它重新打开；
  • 读取、写入或复制它会抛出 ::std::errc::bad_file_descriptor（第14.10章）。

正因为这个状态，类才有默认构造函数和那个 -1 成员初始化器：被移出的对象必须能什么也不做地活完它的生命周期。

5. 实际使用

程序把一个文件移动进新对象，然后把其中两个放进 ::fast_io::vector，而后者需要那个 noexcept 移动才能接受这个类型： 


#include <fast_io.h>
#include <fast_io_dsal/string_view.h>
#include <fast_io_dsal/vector.h>

using namespace ::fast_io::io;

class my_posix_file
{
	int fd_{-1};

public:
	explicit my_posix_file(::fast_io::cstring_view path, ::std::int_least32_t flags) throws
	{
		::std::int_least32_t fd{::open(path.c_str(), flags, 0644)};
		if (fd == -1) [[unlikely]]
		{
			throw throws static_cast<::std::errc>(errno);
		}
		fd_ = fd;
	}

	my_posix_file(my_posix_file const &) = delete;
	my_posix_file &operator=(my_posix_file const &) = delete;

	my_posix_file(my_posix_file &&other) noexcept : fd_{other.fd_}
	{
		other.fd_ = -1;
	}

	~my_posix_file() noexcept
	{
		if (fd_ != -1)
		{
			::close(fd_);
		}
	}

	[[nodiscard]] bool is_open() const noexcept
	{
		return fd_ != -1;
	}

	[[nodiscard]] ::std::int_least32_t native_handle() const noexcept
	{
		return fd_;
	}
};

static_assert(::std::is_nothrow_move_constructible_v<my_posix_file>);
static_assert(::std::is_nothrow_destructible_v<my_posix_file>);

int main()
{
	{ // make sure the example file exists
		::std::int_least32_t fd{::open("demo.txt", O_WRONLY | O_CREAT, 0644)};
		::close(fd);
	}

	my_posix_file a{"demo.txt", O_RDONLY};
	println("a = ", a.native_handle());

	my_posix_file b{::std::move(a)};
	println("b = ", b.native_handle(), ", a = ", a.native_handle(), ", a.is_open() = ", a.is_open());

	::fast_io::vector<my_posix_file> files;
	files.push_back(my_posix_file{"demo.txt", O_RDONLY});
	files.push_back(my_posix_file{"demo.txt", O_RDONLY});
	println("the vector holds ", files.size(), " files:");
	for (my_posix_file const &f : files)
	{
		println("  fd = ", f.native_handle());
	}
}


a = 3
b = 3, a = -1, a.is_open() = 0
the vector holds 2 files:
  fd = 4
  fd = 5

开头那些 static_assert 就是五行的本章总结：该类型可移动构造不抛异常、可复制构造、不可复制构造不抛异常（复制一个文件确实可能失败）、析构不抛异常。把它们读作这个类的契约；程序其余部分只是在演示契约成立。

6. 从 const 对象移动会变成复制

移动构造函数接受 T&&，它不能绑定到 const 对象：把描述符取走会修改它。所以 my_posix_file const & 实参会被复制，而对 const 对象用 ::std::move 只会悄悄地什么都不做： 


my_posix_file const c{"demo.txt", O_RDONLY};
my_posix_file d{::std::move(c)};   // calls the copy constructor
// c is still open

这是正确的，也解释了为什么按 my_posix_file 按值取参数、再把它们 ::std::move 进成员能工作：复制发生在调用处，移动发生在构造函数里。
