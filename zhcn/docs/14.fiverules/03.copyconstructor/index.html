第14.3章: 复制构造函数：两个对象，两份资源

English

1. 复制必须意味着什么

析构函数回答“谁释放它”。复制构造函数回答下一个问题：当一个新对象由已有对象构造出来时，新对象拥有什么？

对第13章的 point 来说答案很简单：它自己的两个数字。对拥有者来说，答案必须是“它自己的资源”，而为一个已打开的文件取得第二个描述符的唯一办法，是向内核要一个：::dup。 


int dup(int fd);              // a new descriptor for the same open file
int dup2(int fd, int newfd);  // make newfd refer to the same open file

2. 你什么都不写时编译器会写什么

没有复制构造函数的类会得到一个自动生成的版本，而生成的那个对 point 做的事一样：复制每个成员。对 int 来说就是把数字复制一份。数字不是描述符 — 它只是一个描述符的名字。 


#include <fast_io.h>
#include <fast_io_dsal/string_view.h>

using namespace ::fast_io::io;

// No copy constructor, no move constructor, no assignment: the compiler
// supplies member-wise versions of all of them.
class shallow_file
{
	int fd_{-1};

public:
	explicit shallow_file(::fast_io::cstring_view path, ::std::int_least32_t flags) throws
	{
		::std::int_least32_t fd{::open(path.c_str(), flags, 0644)};
		if (fd == -1) [[unlikely]]
		{
			throw throws static_cast<::std::errc>(errno);
		}
		fd_ = fd;
	}

	~shallow_file() noexcept
	{
		if (fd_ != -1)
		{
			::close(fd_);
		}
	}

	[[nodiscard]] ::std::int_least32_t native_handle() const noexcept
	{
		return fd_;
	}
};

int main()
{
	shallow_file a{"demo.txt", O_RDONLY};
	println("a = ", a.native_handle());

	{
		shallow_file b{a}; // copies the number, not the file
		println("b = ", b.native_handle(), ", b owns the same descriptor = ", b.native_handle() == a.native_handle());
	} // b closes the descriptor it thinks it owns

	println("after b died, a = ", a.native_handle(), ", still valid = ", ::fcntl(a.native_handle(), F_GETFD) != -1);

	shallow_file c{"demo.txt", O_RDONLY};
	println("c = ", c.native_handle(), ", the number came back");
} // c and a both close descriptor 3


a = 3
b = 3, b owns the same descriptor = 1
after b died, a = 3, still valid = 0
c = 3, the number came back

b 有同样的 int，所以它有同一个所有者的主张，所以它消亡时会关闭那个描述符。那一行之后 a 仍然持有 3，而 3 已经不再打开：a 成了一个悬空的拥有者。之后每次使用它都会以 EBADF 失败，而它的析构函数会第二次关闭描述符 3 — 那时它可能已经属于完全不同的文件了，正如输出的最后两行所示。关闭别人的文件是最恶毒的 bug 之一，因为症状出现的地方离错误很远。

编译器生成的复制是逐成员的，而对句柄的逐成员复制永远是错的。这就是五法则存在的理由：你不能同时要编译器生成的复制和生成的析构函数。五者之一属于你之后，五个全都属于你。

3. 复制构造函数：自己的描述符


	my_posix_file(my_posix_file const &other) throws : fd_{::dup(other.fd_)}
	{
		if (fd_ == -1) [[unlikely]]
		{
			throw throws static_cast<::std::errc>(errno);
		}
	}

分三部分来读。

  • 参数是 const&。复制构造函数不能修改它复制的东西；如果它能，my_posix_file const & 参数就无法被复制，const 对象就会变成二等公民。
  • ::dup 发生在成员初始化列表里。那是成员被初始化的唯一地方（第13.6章），而把可能失败的调用放在那里，意味着它运行时还什么都没有被修改。
  • 是 throws，因为 ::dup 可能失败。当进程打开的描述符太多时它以 EMFILE 失败，当源对象没有描述符时它以 EBADF 失败 — 这正是复制一个被移出的文件会发生的事（第14.10章）。
为什么不先关闭再按路径重新打开？因为文件未必还在那个路径上，而且重新打开会丢掉文件偏移和打开模式。::dup 复制的是那个已打开的文件，而不是名字，所以即使文件被改名或删除它依然有效。

4. 两个描述符，一个打开的文件

复制到底共享了什么？下面的程序向文件写入十个字节，然后复制一个读者，再依次从每个句柄读四个字节： 


#include <fast_io.h>
#include <fast_io_dsal/string_view.h>

using namespace ::fast_io::io;

class my_posix_file
{
	int fd_{-1};

public:
	explicit my_posix_file(::fast_io::cstring_view path, ::std::int_least32_t flags) throws
	{
		::std::int_least32_t fd{::open(path.c_str(), flags, 0644)};
		if (fd == -1) [[unlikely]]
		{
			throw throws static_cast<::std::errc>(errno);
		}
		fd_ = fd;
	}

	my_posix_file(my_posix_file const &other) throws : fd_{::dup(other.fd_)}
	{
		if (fd_ == -1) [[unlikely]]
		{
			throw throws static_cast<::std::errc>(errno);
		}
	}

	~my_posix_file() noexcept
	{
		if (fd_ != -1)
		{
			::close(fd_);
		}
	}

	[[nodiscard]] ::std::int_least32_t native_handle() const noexcept
	{
		return fd_;
	}

	::std::size_t read_some(char *buf, ::std::size_t n) throws
	{
		auto ret{::read(fd_, buf, n)};
		if (ret == -1) [[unlikely]]
		{
			throw throws static_cast<::std::errc>(errno);
		}
		return static_cast<::std::size_t>(ret);
	}

	::std::size_t write_some(char const *buf, ::std::size_t n) throws
	{
		auto ret{::write(fd_, buf, n)};
		if (ret == -1) [[unlikely]]
		{
			throw throws static_cast<::std::errc>(errno);
		}
		return static_cast<::std::size_t>(ret);
	}
};

int main()
{
	{
		my_posix_file out{"demo.txt", O_WRONLY | O_CREAT | O_TRUNC};
		out.write_some("0123456789", 10);
	}

	my_posix_file a{"demo.txt", O_RDONLY};
	my_posix_file b{a}; // copy: a descriptor of its own, same open file description
	println("a = ", a.native_handle(), ", b = ", b.native_handle());

	char buf[16]{};
	a.read_some(buf, 4);
	println("read from a: ", ::fast_io::mnp::os_c_str_with_known_size(buf, 4));
	b.read_some(buf, 4);
	println("read from b: ", ::fast_io::mnp::os_c_str_with_known_size(buf, 4));

	my_posix_file c{"demo.txt", O_RDONLY};
	c.read_some(buf, 4);
	println("read from c: ", ::fast_io::mnp::os_c_str_with_known_size(buf, 4));
}


a = 3, b = 4
read from a: 0123
read from b: 4567
read from c: 0123

看看这三次读取。

  • a 与 b 拥有不同的描述符（3 和 4），所以关闭一个不会关闭另一个，各自的析构函数恰好关闭一个描述符。这正是复制安全的原因。
  • 但它们共享文件偏移：在 a 读了 0123 之后，b 的读取从 4567 继续，而不是从开头。::dup 复制的是打开文件描述，而偏移是它的一部分。
  • c 是单独打开的，所以它有自己的打开文件描述，从头读到 0123。

所以 my_posix_file 的副本是一个共享流的独立拥有者。这是底层系统诚实的语义，类不应当假装不是这样。如果你需要独立的偏移，就重新打开文件（c），而不是复制。

5. 复制完全没有意义的时候

对文件来说，复制描述符是有意义的，所以我们支持它。对许多资源来说并非如此：一把锁要么被持有要么没有，一个缓冲区只有一个所有者，一个进行中的 ::open 无法被复制。这样的类就明确说出来： 


class my_lock
{
public:
	my_lock(my_lock const &) = delete;
	my_lock &operator=(my_lock const &) = delete;
};

任何试图复制它的人都会得到编译期拒绝，而不是运行期的两次 ::close： 


error: use of deleted function 'my_lock::my_lock(const my_lock&)'
note:   declared here

fast_io 在所有权无法复制的地方也这样做：它的 posix_file_factory — 那个在文件对象接管之前持有新描述符的对象 — 正是因为这个理由删除了复制构造函数和复制赋值。

复制是关于所有权的承诺，不是关于字节的承诺。“这个能被复制吗？”与“副本意味着什么？”是同一个问题。如果你不能用一句话回答第二个问题，就删掉复制。
