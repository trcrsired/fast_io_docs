第14.2章: 析构函数：那个总会运行的函数

English

1. 那个总会运行的函数

析构函数没有参数、没有返回类型，也没有办法按名字调用。它在对象的生命周期结束时运行：

  • 在声明该对象的块结束时；
  • 当 throw throws 离开那个块时，包括 try 的块（其处理者即将运行）；
  • 当 return 离开拥有它的函数时；
  • 对成员来说，在它们的所有者消亡时，按声明的逆序运行。

这正是 C++ 不需要 finally 块就能管理资源的全部原因：释放挂在生命周期上，而不是挂在某条代码路径上，于是没有任何路径可以忘记。

警告：析构函数不是孤立的声明。 一旦类有了释放资源的析构函数，编译器生成的拷贝构造和拷贝赋值就是错的，因为它们复制句柄而不是资源。 为两者声明 = delete，或者写真正的拷贝操作。用户声明的析构函数还会抑制隐式移动操作， 所以 move-only 类型必须显式声明移动，或者把移动也删除。
C++ Primer 的 HasPtr 是最小证明（第14.1章）； Chromium 的五法则清理是同一个 bug 的大规模版本。

2. 写它

在我们的类里，析构函数是三行，其中两行是检查空状态： 


	~my_posix_file() noexcept
	{
		if (fd_ != -1)
		{
			::close(fd_);
		}
	}

这个检查不是防御性的噪音。::close(-1) 会以 EBADF 失败，而析构函数没有办法报告失败，所以必须识别出空状态而不是去关闭它。类里其他每个成员都依赖同一个哨兵。

只有一个地方关闭描述符。在最终的类里，那段函数体住在 reset(newfd = -1) 中，而析构函数只是 reset();。析构函数、移动赋值以及复制赋值中“丢掉旧文件”那一步都经过它，所以整个类里恰好只有一次对 ::close 的调用。

3. 析构函数不能失败

这不是风格规则，而是被强制执行的： 


error: destructor cannot be declared with a herbceptions ('throws'/'return_failure{E}')
       exception specification

一个报告失败的析构函数将没有人可以报告：对象已经消失，处理者已经在返回，也没有第二轮清理。语言干脆禁止它，编译器也同意。

其后果比听起来更严格。在赫布异常下，一个 noexcept 函数甚至不能调用可能失败的函数，除非它自己处理失败。所以析构函数不能打印： 


error: call to a 'throws' or 'return_failure{E}' function must be handled by an enclosing
       'try { } catch throws', or the calling function needs a herbceptions specification
       so the error can propagate

fast_io 的每次打印都可能失败 — 输出设备可能已经不在了（第2.14章）— 所以 println 是 throws，析构函数不能使用它。如果你坚持，可以在析构函数里处理失败： 


	~loud() noexcept
	{
		try
		{
			println("goodbye");
		}
		catch throws (::std::error)
		{
			// nothing left to say, and nobody left to say it to
		}
	}

但注意处理者在做什么：它把错误吞掉了。这就是“noexcept”的代价。报告是留给还有调用者的代码的；清理是留给析构函数的。

不要在析构函数里做可能失败的工作。如果一个操作可能失败而你在意这个失败，它就该放在调用者能够处理的具名成员函数里 — close()、flush()、commit() — 而析构函数只做那部分不会失败的。这正是 fast_io 真正的 posix_file 有一个 throws 的 close()，而它的析构函数是 noexcept 的原因。

4. 观察它发生

下面的程序问操作系统（而不是问这个类）描述符是否还开着。::fcntl(fd, F_GETFD) 在描述符有效时成功，一旦关闭就以 EBADF 失败，所以它独立于我们类的任何信念来回答这个问题： 


#include <fast_io.h>
#include <fast_io_dsal/string_view.h>

using namespace ::fast_io::io;

class my_posix_file
{
	int fd_{-1};

public:
	explicit my_posix_file(::fast_io::cstring_view path, ::std::int_least32_t flags) throws
	{
		::std::int_least32_t fd{::open(path.c_str(), flags, 0644)};
		if (fd == -1) [[unlikely]]
		{
			throw throws static_cast<::std::errc>(errno);
		}
		fd_ = fd;
	}

	~my_posix_file() noexcept
	{
		if (fd_ != -1)
		{
			::close(fd_);
		}
	}

	void reset() noexcept
	{
		if (fd_ != -1)
		{
			::close(fd_);
		}
		fd_ = -1;
	}

	[[nodiscard]] bool is_open() const noexcept
	{
		return fd_ != -1;
	}

	[[nodiscard]] ::std::int_least32_t native_handle() const noexcept
	{
		return fd_;
	}
};

int main()
{
	{ // make sure the example file exists
		::std::int_least32_t fd{::open("demo.txt", O_WRONLY | O_CREAT, 0644)};
		::close(fd);
	}

	::std::int_least32_t raw{};

	{
		my_posix_file f{"demo.txt", O_RDONLY};
		raw = f.native_handle();
		println("inside the block:  fd ", raw, ", valid = ", ::fcntl(raw, F_GETFD) != -1);
	}
	println("after the block:   fd ", raw, ", valid = ", ::fcntl(raw, F_GETFD) != -1);

	try
	{
		my_posix_file f{"demo.txt", O_RDONLY};
		raw = f.native_handle();
		println("inside the try:    fd ", raw, ", valid = ", ::fcntl(raw, F_GETFD) != -1);
		throw throws ::std::errc::invalid_argument;
	}
	catch throws (::std::error e)
	{
		print("caught: ", e, "\n");
		println("in the handler:    fd ", raw, ", valid = ", ::fcntl(raw, F_GETFD) != -1);
	}

	my_posix_file g{"demo.txt", O_RDONLY};
	g.reset();
	println("after reset():     is_open = ", g.is_open());
}


inside the block:  fd 3, valid = 1
after the block:   fd 3, valid = 0
inside the try:    fd 3, valid = 1
caught: [posix](22)Invalid argument
in the handler:    fd 3, valid = 0
after reset():     is_open = 0

那段输出里能看到三件事。

  • 析构函数在块结束时运行。块内描述符 3 有效；块之后的那一行就无效了。没有人调用 ::close。
  • 当赫布异常离开块时它也会运行。在 try 内部描述符有效；在处理者里它已经关闭了。try 块的局部对象在处理者运行之前就被销毁，这正是处理者可以相信它看到的是干净状态的全部原因。
  • reset() 就是按需执行的同一次关闭。在 g.reset() 之后文件被关闭、对象为空，并且在再次给它一个描述符之前一直为空。

5. 顺序，以及逆序销毁意味着什么

局部对象按构造的逆序销毁，类成员按声明的逆序销毁。复制赋值（第14.4章）在把一个即将不再拥有的描述符交给临时对象时依赖这一点：临时对象在整个表达式结束时消亡，远在赋值完成之后，所以旧描述符是在新的那个就位之后才被关闭的。 


{
	my_posix_file a{"one.txt", O_RDONLY}; // constructed first
	my_posix_file b{"two.txt", O_RDONLY}; // constructed second
}   // b destroyed first, then a

这条规则不是细节：如果在你的代码所需的顺序里 b 活得没有 a 久，你遇到的不是 bug，而是一段不重叠的生命期 — 没有任何析构函数能把你从那里救出来。
