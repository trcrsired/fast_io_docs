第15.2章 概念：编译器替你检查的要求

English

1. 没有概念的函数模板要你付出什么

裸的函数模板什么都接受。编译器在有人调用它之前根本不看函数体，之后才把实参替换进去， 然后报出任何出错的地方 —— 通常深在好几层、在你没写过的头文件里。 


template <typename T>
[[nodiscard]] inline ::std::string_view show(T const &t) noexcept
{
	return t.name();
}

show(42) 不会告诉你“42 没有 name()”。它说的是 show<int> 的实例化失败了，并指向函数体，附一句 int 没有成员 name。若嵌套三层模板，这条信息会变成一整页 “in instantiation of”。

概念的解法是：把要求写在前面，让调用者读得到，让编译器在实例化任何 东西之前就检查它。

2. 概念就是一个具名的 requires 表达式


template <typename T>
concept named = requires(T const t) {
	{ t.name() } -> ::std::convertible_to<::std::string_view>;
};

template <named T>
[[nodiscard]] inline ::std::string_view show(T const &t) noexcept
{
	return t.name();
}

把 named 读作“关于类型的谓词”。 named<widget> 是 true 或 false； named<int> 是 false，而且这个判断不编译函数体。

requires(T const t) { ... } 这种写法叫要求列表。 每一项有四种形状：

要求 含义
t.name() 这个表达式是良构的
{ t.name() } -> X 良构，且结果类型满足概念 X
{ t.name() } noexcept 良构，且不会抛 —— 在本书里这是一条真实要求
typename T::value_type 这个类型存在

花括号里的一切都是不求值的：不调用、不运行，失败也不是错误，只让概念变成 false。

3. 约束一个比较器

本书要求每个比较器都是 noexcept （第8.1章）。概念可以一字不差地写下这一点， 于是忘记 noexcept 的比较器会在调用点被拒绝，而不是悄悄变慢、或者更糟 —— 从比较里抛出： 


template <typename F>
concept comparator = requires(F f, int a, int b) {
	{ f(a, b) } noexcept -> ::std::convertible_to<bool>;
};

template <comparator F>
inline void my_sort(int *first, ::std::size_t n, F cmp) noexcept
{
	for (::std::size_t i{1}; i < n; ++i)
	{
		for (::std::size_t j{i}; j != 0 && cmp(first[j], first[j - 1]); --j)
		{
			auto const t{first[j]};
			first[j] = first[j - 1];
			first[j - 1] = t;
		}
	}
}

my_sort(data, 3, ::std::ranges::greater{}) 能编译： ::std::ranges::greater 的调用运算符是 noexcept。 一个没写 noexcept 的 lambda 编译不过，而这个编译器会明确告诉你原因： 


error: no matching function for call to ‘my_sort(int [3], int, main()::<lambda(int, int)>)’
  • candidate 1: ‘template<class F>  requires  comparator<F> void my_sort(int*, std::size_t, F)’
    • constraints not satisfied
        { f(a, b) } noexcept -> ::std::convertible_to<bool>;
      • ‘f.main()::<lambda(int, int)>(a, b)’ is not ‘noexcept’

六行就是全部收益：要求写在一处、调用者找得到，错误信息点出要求而不是函数体。

4. 用类型特征也能约束

两类要求可以自由组合。一个概念既能要求某个成员函数（语法），也能要求类型的某个性质（语义）： 


template <typename T>
concept byte_like = ::std::integral<T> && (sizeof(T) == 1);

::std::integral<T> 是建立在 ::std::is_integral_v 上的库概念；(sizeof(T) == 1) 是普通的常量表达式。两者都必须成立。

语法那一半优先用现成的。::std::integral 是对标准库自己持有的类型的承诺； requires { t.size() } 是对调用者传入的任何类型的承诺，即使标准库日后又加了 一个重载，它仍然成立。

5. 包含关系：约束更紧的那个胜出

两个重载都可行，其中一个要求了另一个的一切、并且还多一点，这时选约束更强的那个。 这不是什么平局规则的花招，而是因为两个概念是彼此的子集。 


template <typename T>
concept integral_like = ::std::integral<T>;

template <typename T>
concept byte_like = integral_like<T> && (sizeof(T) == 1);

template <integral_like T>
[[nodiscard]] inline ::std::string_view kind(T) noexcept
{
	return "integral";
}

template <byte_like T>
[[nodiscard]] inline ::std::string_view kind(T) noexcept
{
	return "byte";
}

kind(static_cast<char>(1)) 打印 byte，因为 byte_like 是用 integral_like 写出来的，因此已知更严格。 注意方向：只有当更强概念的定义里按名字包含更弱概念时，包含关系才成立。 两个恰好有交集但互不相关概念会形成歧义，调用直接编译不过。

6. 概念在哪里被检查

概念出现在四个地方，全部在编译期：

  • 作为类型约束： template <named T>。
  • 作为后置子句： template <typename T> requires named<T>。意思相同，写法不同； 约束很长时用子句。
  • 作为一个变量： named<T> 是 bool， 可以用 static_assert 检查，也可以放进 if constexpr（第15.7章）。
  • 作为临时 requires： requires { t.size(); } 直接写在函数体里，不起名字。

下面整个程序打印四个答案，而且不实例化任何你没要求它实例化的东西： 


#include <fast_io.h>
#include <concepts>
#include <string_view>

struct widget
{
	[[nodiscard]] ::std::string_view name() const noexcept { return "widget"; }
};

template <typename T>
concept named = requires(T const t) {
	{ t.name() } -> ::std::convertible_to<::std::string_view>;
};

template <typename T>
concept byte_like = ::std::integral<T> && (sizeof(T) == 1);

template <named T>
[[nodiscard]] inline ::std::string_view show(T const &t) noexcept
{
	return t.name();
}

template <byte_like T>
[[nodiscard]] inline ::std::string_view kind(T) noexcept
{
	return "byte";
}

int main()
{
	try
	{
		::fast_io::io::println(show(widget{}));
		::fast_io::io::println(kind(static_cast<char>(1)));
	}
	catch throws (::std::error e)
	{
		::fast_io::io::perrln(e);
	}
}

输出：


widget
byte

7. 概念做不到的事

概念是编译期谓词。它不能决定运行期的任何事，不能让一个变量这一轮装 widget、 下一轮装 gadget，也不会出现在二进制里。

人们退而求其次的两个办法是带 virtual 的继承 （第18章）与类型擦除 （第15.9章）。 本章用后者，因为它除了必须动态的那一次调用之外，把一切都保持静态绑定。

8. 经验法则

  • 概念用两次就起名字；只用一次就写内联 requires。
  • 用其他概念来约束，绝不用裸 enable_if。只有编译器看得见包含关系， 包含关系才起作用。
  • 算法依赖 noexcept 时，就把 noexcept 写进概念；本书的比较器与 分配器总是如此。
  • 不要约束用不到的东西。一个要求五个成员、只用两个的概念，只会毫无理由地拒绝类型。
  • 记住概念并不减少膨胀：它只是更早地拒绝错误实参。膨胀是 第15.8章的事。
