第19.2章：C++ 遗留异常

English

1. 这个特性是什么

C++ 的异常机制就是本书所说的遗留异常。它有三个关键字和一套类继承体系： 


#include <fast_io.h>
#include <stdexcept>

int main()
{
	try
	{
		int const a{84};
		for (int b : {2, 0})
		{
			if (b == 0)
			{
				throw ::std::runtime_error("division by zero");
			}
			::fast_io::io::print("84 / ", b, " = ", a / b, "\n");
		}
	}
	catch (::std::runtime_error const &e)
	{
		::fast_io::io::print("caught runtime_error: ", ::fast_io::mnp::os_c_str(e.what()), "\n");
	}
}


84 / 2 = 42
caught runtime_error: division by zero

规则是这样的：throw 接受任意类型的值，把它拷贝到实现拥有的存储里，然后放弃当前函数；unwinder 逐帧遍历调用栈，边走边析构自动对象，直到找到匹配的处理块。匹配靠 RTTI 完成，所以 catch (::std::runtime_error const &e) 能匹配派生类型，而 catch (...) 能匹配任何东西。处理块按顺序尝试，第一个匹配者胜出，而用 throw; 重新抛出的处理块会让搜索继续。

因为三十年间语言提供的唯一共同基类就是 ::std::exception 及其 what()，所以每个库都在它下面发明了自己的一套继承，而从捕获到的错误里取出消息的唯一办法就是一次返回 char const * 的虚调用。这就是赫布异常要取代的设计，而它值得你了解，因为即使你不写它，你也一定会读到它。

2. 一次抛出到底花多少

遗留异常的一次抛出不是一次跳转。它先用 __cxa_allocate_exception 分配异常对象 —— 在每一个实现里，都是失败路径上的一次堆分配 —— 然后调用 __cxa_throw，后者开始一次两阶段的栈遍历，对每一帧都去问 personality routine，再通过运行时类型信息匹配处理块。接着它析构一路走过的所有东西，最后才运行处理块。

那就测量。下面的程序把同一个错误抛出二十万次：一半作为遗留的 ::std::runtime_error，一半作为赫布异常。两个循环都由同一个数组驱动，因此什么都不会被折叠掉，而且两者都记录有多少次错误抵达了处理块。 


#include <fast_io.h>
#include <stdexcept>

namespace
{
constexpr ::std::size_t round_count{200000};
constexpr ::std::size_t small_mask{3};

inline ::std::int_least64_t to_ns(::fast_io::posix_timespec64 d) noexcept
{
	return static_cast<::std::int_least64_t>(d.tv_sec) * 1000000000 + static_cast<::std::int_least64_t>(d.tv_nsec);
}

/* the values live in memory the optimizer cannot reason about */
::std::size_t count_legacy(::std::uint_least32_t const *values) throws
{
	::std::size_t caught{};
	for (::std::size_t i{}; i != round_count; ++i)
	{
		try
		{
			if (values[i] == 0)
			{
				throw ::std::runtime_error("riser");
			}
		}
		catch (::std::exception const &)
		{
			++caught;
		}
	}
	return caught;
}

::std::size_t count_herbception(::std::uint_least32_t const *values) throws
{
	::std::size_t caught{};
	for (::std::size_t i{}; i != round_count; ++i)
	{
		try
		{
			if (values[i] == 0)
			{
				throw throws ::std::errc::invalid_argument;
			}
		}
		catch throws (::std::error e)
		{
			++caught;
		}
	}
	return caught;
}
} // namespace

int main()
{
	auto *buffer{static_cast<::std::uint_least32_t *>(::std::malloc(round_count * sizeof(::std::uint_least32_t)))};
	if (buffer == nullptr)
	{
		::std::abort();
	}
	for (::std::size_t i{}; i != round_count; ++i)
	{
		buffer[i] = static_cast<::std::uint_least32_t>((i * 2654435761u) >> 7) & small_mask;
	}
	::std::size_t legacy_caught{};
	::std::size_t herbception_caught{};
	::std::int_least64_t legacy_ns{};
	::std::int_least64_t herbception_ns{};
	try
	{
		auto const start{::fast_io::posix_clock_gettime(::fast_io::posix_clock_id::monotonic_raw)};
		legacy_caught = count_legacy(buffer);
		legacy_ns = to_ns(::fast_io::posix_clock_gettime(::fast_io::posix_clock_id::monotonic_raw) - start);

		auto const start2{::fast_io::posix_clock_gettime(::fast_io::posix_clock_id::monotonic_raw)};
		herbception_caught = count_herbception(buffer);
		herbception_ns = to_ns(::fast_io::posix_clock_gettime(::fast_io::posix_clock_id::monotonic_raw) - start2);
	}
	catch throws (::std::error e)
	{
		::fast_io::io::print("error ", e, "\n");
		return 1;
	}
	::std::free(buffer);
	::fast_io::io::print("caught        ", legacy_caught, " ", herbception_caught, " throws out of ", round_count, "\n"
		"total ns      ", legacy_ns, " ", herbception_ns, "\n"
		"ps per throw  ", legacy_ns * 1000 / static_cast<::std::int_least64_t>(legacy_caught), " ",
		herbception_ns * 1000 / static_cast<::std::int_least64_t>(herbception_caught), "\n");
}


caught        49999 49999 throws out of 200000
total ns      46726099 44253
ps per throw  934540 885

大约一微秒对一纳秒。有意思的不是这个比值，而是遗留的失败路径会分配并且遍历内存，这意味着它还有第二种失败方式（在报告错误的时候内存不足）、第二种变慢方式（帧表上的缓存缺失），而且根本没有常数上界。赫布异常的路径就是两个寄存器加一个条件跳转，这甚至让编译器在结果无人使用时把它整个删掉。

3. 它对环境有什么要求

把同一个程序编译成目标文件，然后问它还缺什么： 


__cxa_allocate_exception
__cxa_begin_catch
__cxa_end_catch
__cxa_free_exception
__cxa_throw
__gxx_personality_v0
_Unwind_Resume

其中四个就是异常机制本身：分配、抛出、进入/退出 catch，以及 itanium 的 personality routine __gxx_personality_v0 —— 那是 unwinder 用来判断某一帧是否捕获任何东西的函数（此外还有平台 unwinder 里的 _Unwind_Resume）。要让这些调用真正工作，一个二进制还需要：

  • 一个 unwinder：一个理解目标帧布局的栈遍历器；
  • 路径上每个函数的帧表（.eh_frame）和语言异常表（.gcc_except_table），并且要在加载器里注册，好让遍历器找得到；
  • 每套 ABI 一个 personality routine，以及一个负责异常对象生命周期的运行时；
  • RTTI：用来匹配处理块所需的类型信息。

这是一整摞由平台掌管的组件，而其中任何一个都可能不存在：

环境 为什么遗留异常不可用
freestanding、内核、引导程序、嵌入式 那里没有 unwinder、没有可以注册表的加载器、也没有 __cxa_* 运行时。这些表本身就是你付不起的体积，而失败路径还会分配
WebAssembly / WASI 展开栈并不属于基础目标：异常提案和各种 JS 宿主变体都要给引擎加表面积，而工具链默认就发布 -fno-exceptions
Any build with -fno-exceptions 编译器直接从语法上拒绝这些关键字。很多工具链、游戏主机、移动 SDK 以及 C++ 标准库的构建就是这样配置的
Across a GNU ↔ MSVC boundary Itanium 与 Microsoft 的异常 ABI 不同：表不同、personality routine 不同、对象布局不同。异常无法跨越，对端的捕获点也根本不存在
Inside a noexcept function 逃出它的异常会调用 ::std::terminate —— 析构函数和移动构造函数不许做的那些事，正是靠这条规则强制的

所以诚实的说法不是"遗留异常慢"。而是：在你大多要发布到的目标上，它根本不存在；而在它存在的地方，它是失败路径上的一次堆分配加一次栈遍历。一个用 throw 报告失败并被 -fno-exceptions 排除在外的库，是无法在内核里、在 Wasm 模块里、在板子上、或在任何以 -fno-exceptions 编译的项目里使用的。而那是大多数项目。

4. 所以：你不能用它

本书教遗留异常的方式，和教 virtual 与 new 的方式一样（第18章）：为了让你读懂。你会维护会抛出的代码，你会调用失败路径是 std::runtime_error 的库，你必须知道它跑起来会发生什么。但你自己的代码在 throws 通道上报告失败，这不是风格偏好 —— 这是本书所面向的每个目标上唯一能用的机制。

不要把两者混在一起指望它们相安无事。一处遗留的 throw 就会强迫整个构建保留 unwinder、保留那些表、保留 personality routine，并且让每个调用者的契约都变得不可见。本章最后一页（第19.4章）就是那份把这些选项彻底删掉的构建清单，好让任何人都无法不小心把它加回来。

而当你必须跨越边界 —— 你的代码调用会抛出的库，或者某个库调用你的代码、想要一个它能懂的异常 —— 只有一条受支持的路线，那就是 第19.3章。
