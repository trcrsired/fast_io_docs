第11.16章: Wine 文件 API

English

概述

Wine（“Wine Is Not an Emulator”）让 Windows 二进制程序运行在 Linux、FreeBSD 等 POSIX 系统上。Wine 通过把 Win32 与 NT API 翻译成宿主的系统调用来实现它们 — 而那些系统调用最终使用的是 POSIX 文件描述符。

Windows 二进制程序无法调用 write(2)：它只认识 HANDLE。所以当以 Windows 模块身份运行的 fast_io 代码需要用到 Wine 藏在 HANDLE 底下的那个宿主文件描述符时，仅靠 <windows.h> 是拿不到的 — 它需要一座位于宿主一侧、说固定 C ABI 的桥。那座桥就是 libwineunix，fast_io 通过下面两个类型把它暴露出来：

  • ::fast_io::wine_file — 对 Wine 宿主文件描述符的 RAII 所有权包装。
  • ::fast_io::wine_io_observer — 对已有 Wine 宿主文件描述符的非所有权视图。

重要 — wineunix.dll 并不随 fast_io 一起发布。fast_io 只包含它自己那份该桥 ABI 的私有视图，位于 include/fast_io_hosted/platforms/wine/：其中的导入声明用 __asm__ 标签绑定到 DLL 的导出名上，因此同时包含 fast_io 与 Wine 自带的 <__wine_unix/__wine_unix.h> 的翻译单元不会发生冲突，也不需要任何 winelibc 头文件。DLL 本身必须由你自己构建，源码在 https://github.com/trcrsired/libwineunix。在你构建它之前，::fast_io::wine_file 在链接期无函数可调，在运行期也无模块可加载。

自己构建 wineunix.dll

实现是一个独立项目：https://github.com/trcrsired/libwineunix。把它克隆下来、构建、然后把产物放在你自己的 .exe 旁边。它最多产出三个构建产物，你需要哪些取决于程序将在哪里运行：

产物 类型 用途
wineunix.dll PE 动态库 Windows 一侧链接的那座桥。导出 __wine_unix_* C ABI。
libwineunix.so 宿主共享对象 unix 那一半。DLL 在 Wine 下运行时调用的就是它；没有它，DLL 只能走 NT 路径。
libwineunix.a PE 导入库 由 llvm-dlltool 从 def/wineunix.def 生成。你的 .exe 链接它一次即可。

CMake 构建由下面这些选项驱动：

选项 默认值 含义
LIBWINEUNIX_UNIXLIB ON 用宿主编译器构建 libwineunix.so。需要非 Windows 宿主。
LIBWINEUNIX_WINEUNIX_DLL OFF 构建 PE 版 wineunix.dll。
LIBWINEUNIX_WINEUNIX_IMPL bundled bundled、unixcall 或 nt — 见下文。
LIBWINEUNIX_IMPORT_LIB ON 用 llvm-dlltool 生成 libwineunix.a。
LIBWINEUNIX_PE_CXX clang++ 面向 PE 的编译器驱动。PE 一侧由独立的、以 Windows 为目标的编译器编译，而不是由项目编译器编译。
LIBWINEUNIX_PE_CXXFLAGS 空 传给该驱动的额外选项（例如 --target=x86_64-w64-windows-gnu、--sysroot=...）。
LIBWINEUNIX_PE_MACHINE 自动推导 导入库使用的 llvm-dlltool -m 机器类型（i386:x86-64、arm64 等）。留空时由 CMAKE_SYSTEM_PROCESSOR 推导。
LIBWINEUNIX_FAST_IO_TEST OFF 构建一个测试 .exe，用来驱动本页讲的这一层。把 LIBWINEUNIX_FAST_IO_INCLUDE 指向 fast_io/include 目录。

在 Wine 下完整跑通整条链路的一次构建大致是这样： 


git clone https://github.com/trcrsired/libwineunix
cmake -S libwineunix -B libwineunix/build \
      -DLIBWINEUNIX_WINEUNIX_DLL=ON \
      -DLIBWINEUNIX_IMPORT_LIB=ON \
      -DLIBWINEUNIX_FAST_IO_TEST=ON \
      -DLIBWINEUNIX_FAST_IO_INCLUDE=/path/to/fast_io/include \
      -DLIBWINEUNIX_PE_CXXFLAGS="--target=x86_64-w64-windows-gnu --sysroot=/path/to/sysroot"
cmake --build libwineunix/build

# unixcall path: the DLL calls libwineunix.so
WINEDLLPATH=libwineunix/build wine libwineunix/build/fast_io_winetest.exe

# NT path: the DLL never touches the unixlib
wine libwineunix/build/fast_io_winetest.exe

bundled 实现通常就是你想要的那个：一个 DLL 同时携带两条路径，在运行期决定走哪条。在 Wine 下它会解析 libwineunix.so 并通过它调用；在真正的 Windows 机器上，同一个二进制改为转发给 ntdll。一个 .exe、一个 DLL，两个世界之间无需重新构建、也无需替换 DLL：

  • 在 Wine 下：your.exe → wineunix.dll → libwineunix.so → libc
  • 在 Windows 上：your.exe → wineunix.dll → ntdll

unixcall 只构建第一条路径（此时它依赖 libwineunix.so，且只能在 Wine 下运行）；nt 只构建第二条。它们的存在是为了单独测试各自那一半，而不是为了发布。

因为导入库就是一个普通的 PE 导入库，链接方式很平常：链接一次 libwineunix.a，再把 wineunix.dll 放在可执行文件旁边即可。

模式是一样的

fast_io 中的每一层都遵循同样的形状：

  1. 一个名为 xxx_file 的所有权 RAII 类型。
  2. 一个名为 xxx_io_observer 的非所有权观察者类型。
  3. 对 print、println 与 scan 的完整支持。
  4. 能够包装来自外部代码的原始句柄。

wine_file 也不例外。概念上它长这样： 


#include <fast_io.h>
#include <fast_io_device.h>

int main()
{
    try
    {
        using namespace ::fast_io::iomnp;

        // Opens a file through the Wine host layer.
        ::fast_io::wine_file wf(u8"hello_wine.txt", ::fast_io::open_mode::out);

        print(wf, "Hello from wine_file!\n");

        ::std::size_t const n{42zu};
        println(wf, "The answer is: ", n);
    }
    catch throws (::std::error e)
    {
        ::fast_io::perrln(e);
        return 1;
    }
    return 0;
}

包装一个 Wine 宿主文件描述符

当 Wine 翻译一个 Windows 的 CreateFileW 调用时，它最终会拿到一个宿主 POSIX 文件描述符，而 DLL 可以把这个数字交给你。用 wine_io_observer 把它包起来，你就能继续用 fast_io 操作它，同时不取得所有权 — 观察者绝不会关闭不是它打开的描述符： 


#include <fast_io.h>
#include <fast_io_device.h>

// Non-owning view over a host fd that Wine owns.
void write_via_wine(::fast_io::wine_host_fd_t host_fd) throws
{
    using namespace ::fast_io::iomnp;

    ::fast_io::wine_io_observer observer{host_fd};

    // The DLL surfaces a failed host write as a herbception, like every other
    // device in this chapter.
    println(observer, u8"Written through a wine_io_observer\n");
}

int main()
{
    try
    {
        write_via_wine(::fast_io::wine_stdout().native_handle());
    }
    catch throws (::std::error e)
    {
        ::fast_io::perrln(e);
        return 1;
    }
    return 0;
}

::fast_io::wine_stdout()、wine_stdin() 与 wine_stderr() 是这一层的标准流观察者，也是两种 DLL 实现唯一肉眼可见的差别：unixcall 路径给出 unix_fd + 1，NT 路径给出进程的 StandardOutput 句柄，两者都被包装成宿主 fd，所以你的其余代码分辨不出它们的区别。

为什么需要这一层？

Wine 是一套复杂的基础设施。生活在 Wine 内部的代码（例如 Wine 自己对 ntdll.dll 或 kernel32.dll 的实现）需要：

  • 从客户机代码那里接收一个 Windows HANDLE。
  • 通过 Wine 内部表把它翻译成宿主 int fd。
  • 在这个 fd 上做宿主 I/O，同时仍能把错误以 NTSTATUS 码的形式抛回客户机。

fast_io 的 Wine 层在不用 winelibc 的前提下做到了这件事：platforms/wine/api.h 自己声明 DLL 的导出符号，用 __asm__ 标签绑定到导出名，标志位取值也与 Wine 自己的 ABI 保持一致。因此一个已经在用 fast_io 的 Windows 模块，只需链接一个导入库就获得了宿主 I/O — 不需要第二套工具链，不需要 winelib，不需要重编整个世界。

与其他层的关系

在运行 Wine 的 POSIX 宿主上，完整的分层是这样的：

  • 客户机上的 Windows 二进制调用 WriteFile。在 Wine 内部它被解析为 ntdll!NtWriteFile。
  • Wine 的 ntdll 把它翻译成对某个宿主 fd 的 POSIX write(2) 调用 — 那个 fd 就是 wine_file 所包装的东西。
  • 同一个进程里的 fast_io 代码可以完全绕过这条路径：wine_file 直接向 wineunix.dll 索要宿主描述符并向它写入。

所以从客户机的角度看，这次 I/O 走的是 NT 层；从宿主的角度看，它走的是 POSIX。wine_file 就活在这两者的接缝处。

小结

  • ::fast_io::wine_file 是 Wine 宿主文件描述符的 RAII 包装；::fast_io::wine_io_observer 是非所有权视图。
  • wine_file 与 wine_io_observer 之外的每一层（POSIX、Win32、NT）都以完全相同的方式工作。
  • 那座桥是 wineunix.dll + libwineunix.so，来自 github.com/trcrsired/libwineunix。它必须由你自己构建：fast_io 只提供 ABI 声明，导入库也要你用 llvm-dlltool 自己生成。
  • bundled 版 DLL 同时适用于两个世界：在 Wine 下走 unixlib，在真正的 Windows 上走 ntdll。
  • 这里的一切都是 throws：打开、读取、写入与刷新都会把失败以赫布异常的形式报告出来，和 posix_file、win32_file、nt_file 完全一样。
  • 它活在一个 Windows 客户机与其所运行的 POSIX 宿主之间的边界上。
