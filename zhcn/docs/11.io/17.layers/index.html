第11.17章: 文件各层之间的关系

English

为什么这一章重要

到目前为止我们见到了六个文件类型家族：wine、nt、win32、posix、c 和 filebuf。它们看起来像是彼此平行、互不相干的 API — 但并不是。它们构成一个栈，每一层都是用下面那层实现的。

理解这个栈是良好使用 fast_io 的关键。它解释了为什么 iobuf_file 在每个平台上都“就是能用”、为什么你可以自由混用各层，以及 native_file 真正意味着什么。

层次结构

从最底层（最接近内核）到最高层：

  • 第 1 层：wine（最低层，Wine 翻译层）
  • 第 2 层：nt / zw（NT 内核接口，Nt* 与 Zw* 函数在用户空间完全相同）
  • 第 3 层：win32（Win32 API）
  • 第 4 层：posix（POSIX 文件描述符）
  • 第 5 层：c（C 标准库 FILE*）
  • 第 6 层：filebuf（C++ 标准库，最高层）

这 6 层在所有编程语言中都存在，不只是 C++。每种现代语言都建立在 C 或 C++ 运行时之上，或者直接使用同样的操作系统 API。当你在 Python、Java、Rust、Go 或任何其他语言里做文件 I/O 时，最终都要经过同样的这些层：

  • Python 的 open() 使用 CPython 的 C 实现，后者调用 libc
  • Java 的 FileInputStream 用 JNI 调用 C/C++ 代码
  • Rust 的 std::fs::File 直接调用操作系统 API，或者经由 libc
  • Go 的 os.Open 用 cgo 调用 C 函数，或者直接发起系统调用
  • Node.js 使用 libuv，而 libuv 包装 POSIX/Win32 API

理解这些层能帮你理解任何语言的文件 I/O 在底下是如何工作的，而不只是 C++。因此，理解它们对使用任何编程语言都至关重要 — 无论是在 Python 里调试性能问题、理解 Java 的文件操作为何表现出某种行为，还是在 Rust 里优化 I/O，同样的原理都适用。

写成一串链条，箭头表示“建立在……之上”： 


    wine (1)  =>  nt/zw (2)  =>  win32 (3)  =>  posix (4)  =>  c (5)  =>  filebuf (6)

每一层都包装它下面那层。当这不可能时（因为下面那层没有暴露可用的 API），这一层就直接调用底层系统调用并包装那个。

层次图

这个层栈是平台相关的，并非每个平台都有全部层。下面是展示所有可能层的一般层次： 


    +------------------------------------------------+
    |       std::filebuf  (C++ stdlib)               |  <- filebuf_file (Layer 6)
    +================================================+
                 |
                 v
    +------------------------------------------------+
    |     libc / CRT  (FILE*)                        |  <- c_file (Layer 5)
    +================================================+
                 |
                 v
    +------------------------------------------------+
    |   libc POSIX fd / CRT fd  (int fd)             |  <- posix_file (Layer 4)
    +================================================+
                 |
                 v
    +------------------------------------------------+
    |   Win32 HANDLE / System calls                  |  <- win32_file (Layer 3) / syscalls
    +================================================+
                 |
                 v
    +------------------------------------------------+
    |        NT HANDLE  (Windows only)               |  <- nt_file (Layer 2)
    +================================================+
                 |
                 v
    +------------------------------------------------+
    |   Wine host fd  (Wine only)                    |  <- wine_file (Layer 1)
    +================================================+
                 |
                 v
              [ kernel ]

注意：这是一个简化的概览。实际的层取决于平台，并非每个平台都有全部层：

  • 在 POSIX 系统上（Linux、macOS、FreeBSD）：只有第 4-6 层存在（libc POSIX fd、libc FILE*、filebuf）。第 1-3 层（wine、nt、win32）不存在。
  • 在 Windows 上（原生）：第 2-6 层都存在（NT HANDLE、Win32 HANDLE、CRT fd、CRT FILE*、filebuf）。CRT 文件描述符（第 4 层）由 C 运行时（MSVCRT/UCRT）提供，内部是 HANDLE 的包装。
  • 在 Wine 上：所有层都可能存在。Wine 把 Windows API 调用（第 2-3 层）翻译成宿主 POSIX 调用（第 4 层），再进入宿主内核。

下面是每个典型平台的详细图示。

在 POSIX 系统上（Linux、macOS、FreeBSD 等）


    +------------------------------------------------+
    |       std::filebuf  (C++ stdlib)               |  <- filebuf_file (Layer 6)
    +================================================+
             |
             v
    +------------------------------------------------+
    |        libc  (FILE*, fopen, fread, etc.)       |  <- c_file (Layer 5)
    +------------------------------------------------+
             |
             v
    +------------------------------------------------+
    |   libc POSIX layer  (int fd, open, read, etc.) |  <- posix_file (Layer 4)
    +================================================+
             |
             v
    +------------------------------------------------+
    |        System calls (open, read, write)        |  <- kernel interface
    +================================================+
             |
             v

在 POSIX 系统上，这个栈很直接：C++ 标准库包装 libc，libc 同时提供 FILE* 和 POSIX 文件描述符，后者包装进入内核的系统调用。FILE* 与 POSIX 文件描述符都是 libc 的一部分。

在 Windows 上（原生）


    +------------------------------------------------+
    |       std::filebuf  (C++ stdlib)               |  <- filebuf_file (Layer 6)
    +================================================+
             |
             v
    +------------------------------------------------+
    |     CRT  (msvcrt.dll / ucrt, FILE*)            |  <- c_file (Layer 5)
    +================================================+
             |
             v
    +------------------------------------------------+
    |     CRT file descriptors  (int fd)             |  <- posix_file (Layer 4)
    +================================================+
             |
             v
    +------------------------------------------------+
    |   Win32 HANDLE  (CreateFileW / CreateFileA)    |  <- win32_file (Layer 3)
    +================================================+
             |
             v
    +------------------------------------------------+
    |   NT HANDLE  (NtCreateFile / ZwCreateFile)     |  <- nt_file (Layer 2)
    +================================================+
             |
             v
          [ kernel: ntoskrnl.exe ]

在 Windows 上，CRT（C 运行时：MSVCRT 或 UCRT）同时提供 FILE*（第 5 层）和文件描述符（第 4 层）。文件描述符是 Win32 HANDLE 的包装 — 内部上，CRT 调用 CreateFileW 并保存 HANDLE，然后返回一个映射到该 HANDLE 的小整数文件描述符。你可以用 _get_osfhandle(fd) 与 _open_osfhandle(handle, flags) 在两者之间转换（见第11.14章）。

在 Wine 上（POSIX 宿主上的 Windows 程序）


    +------------------------------------------------+
    |       std::filebuf  (C++ stdlib)               |  <- filebuf_file (Layer 6)
    +================================================+
             |
             v
    +------------------------------------------------+
    |     CRT  (msvcrt.dll / ucrt, FILE*)            |  <- c_file (Layer 5)
    +================================================+
             |
             v
    +------------------------------------------------+
    |     CRT file descriptors  (int fd)             |  <- posix_file (Layer 4)
    +================================================+
             |
             v
    +------------------------------------------------+
    |   Win32 HANDLE  (CreateFileW / CreateFileA)    |  <- win32_file (Layer 3)
    +================================================+
             |
             v
    +------------------------------------------------+
    |   NT HANDLE  (NtCreateFile / ZwCreateFile)     |  <- nt_file (Layer 2)
    +================================================+
             |
             v
    +------------------------------------------------+
    |   Wine host fd  (Wine translating NT to host)  |  <- wine_file (Layer 1)
    +================================================+
             |
             v
    +------------------------------------------------+
    |   Host libc  (glibc, musl, etc.)               |  <- host POSIX layer
    +================================================+
             |
             v
    +------------------------------------------------+
    |   Host system calls (open, read, write)        |  <- host kernel interface
    +================================================+
             |
             v
          [ host kernel: Linux, macOS, etc. ]

在 Wine 上，Windows 各层（CRT、Win32、NT）都存在，但 Wine 把 NT 系统调用翻译成宿主 POSIX 系统调用。所以调用链经过 Wine 的翻译层（第 1 层），然后进入宿主的 libc，再进入宿主内核。这就是 Wine 程序能在 Linux、macOS 和 FreeBSD 上运行的原因。

每一层都对应一个真实的系统组件：

  • filebuf — C++ 标准库（libstdc++、libc++，或 MSVC 的 STL）。在 Windows 上它们以 libstdc++-6.dll（MinGW）、libc++.dll / c++.dll（LLVM libc++ — ${CPU}-windows-gnu 用 libc++.dll，${CPU}-windows-msvc 用 c++.dll）或 msvcp{version}.dll（MSVC，例如 msvcp140.dll）的形式存在。
  • c — libc（glibc、musl、msvcrt.dll/ucrt）。FILE*、fopen、fread、fprintf 和 printf 住在这里。在 POSIX 系统上，libc 还提供 POSIX 文件描述符层（第 4 层）。
  • posix — POSIX 文件描述符与系统调用（open、read、write、close）。在 Linux/macOS/FreeBSD 上这是 libc 的一部分。在 Windows 上没有原生 POSIX 层（兼容层除外）。
  • win32 — Windows 上的 kernel32.dll。CreateFileW、ReadFile、WriteFile 以及其他 Win32 文件 API 住在这里。这是“传统的”Windows API。
  • nt — Windows 上的 ntdll.dll。NtCreateFile、NtReadFile、NtWriteFile 以及其他原生 NT API 住在这里。这是真正的 Windows 内核接口 — kernel32.dll 本身也是建立在 ntdll.dll 之上的。
  • zw — 也在 ntdll.dll 里。ZwCreateFile、ZwReadFile、ZwWriteFile 等。在用户空间，Nt* 与 Zw* 函数完全相同 — 它们都调用进入内核。区别只在内核态：Nt* 函数校验指针参数（用于来自用户态的调用），而 Zw* 函数跳过参数校验（用于来自可信内核态代码的调用）。由于在用户空间行为相同，fast_io 把 ::fast_io::zw_file 提供为 ::fast_io::nt_file 的别名。
  • wine — Wine 的翻译层。在 Linux/macOS 上运行 Windows 程序时，Wine 把 NT 系统调用翻译成宿主 POSIX 系统调用。

所以当你调用 std::fstream 时，Windows 上的调用链是：C++ 标准库 → libc（MSVCRT/ucrt，FILE*）→ kernel32.dll（CreateFileW）→ ntdll.dll（NtCreateFile）→ 内核。在 Linux 上则是：C++ 标准库 → libc（glibc/musl，FILE* 与 POSIX fd）→ open()/read() 系统调用 → 内核。

fast_io 让你跳过一些层。如果你要不带缓冲地直接调用内核，就用 native_file；如果你需要与遗留代码兼容，就用 c_file 或 filebuf_file。你选适合自己需要的层。

在 Linux、FreeBSD 和 macOS 上只用 posix 分支。在 Windows 上使用 nt 与 win32 分支。只有在 POSIX 宿主上运行于 Wine 下时才使用 wine 分支。

平台可用性：

  • wine_file 只在为 Wine 编译时可用（运行在 POSIX 宿主上）。
  • nt_file 与 win32_file 只在 Windows（以及 Wine）上可用。
  • posix_file 在所有符合 POSIX 的系统（Linux、macOS、FreeBSD 等）上可用，在使用 POSIX 兼容层时在 Windows 上也可用。
  • c_file 与 filebuf_file 到处都可用，因为它们依赖 C 与 C++ 标准库。

重要：这些关系不是由 fast_io 定义的，而是由操作系统和编译器的 C/C++ 运行时供应商定义的。例如在 POSIX 系统上，libc 的 FILE* 是由 libc 实现（glibc、musl 等）建立在 POSIX 文件描述符之上的，而 C++ 标准库的 ::std::filebuf 是由 C++ 运行时库建立在 FILE* 之上的。fast_io 只是总结并包装这些既有的关系 — 它不发明新的关系。

完整的层参考

下表总结了所有文件层、它们的类型以及各自包装什么：

层 拥有式类型 观察者类型 句柄名 包装
wine ::fast_io::wine_file ::fast_io::wine_io_observer host_fd Wine 宿主 fd
nt ::fast_io::nt_file ::fast_io::nt_io_observer handle NtCreateFile / ZwCreateFile
win32 ::fast_io::win32_file ::fast_io::win32_io_observer handle CreateFileW / CreateFileA
posix ::fast_io::posix_file ::fast_io::posix_io_observer fd open / openat
c c ::fast_io::c_file ::fast_io::c_io_observer fp
FILE* / fopen filebuf ::fast_io::filebuf_file ::fast_io::filebuf_io_observer fb

句柄名一列给出用于访问底层原生句柄的成员函数名。例如 posix_file::native_handle() 返回 fd（文件描述符），而 nt_file::native_handle() 返回 handle（NT HANDLE）。

包装的黄金法则

fast_io 为每一层提供包装，而每个包装做两件事之一：

  1. 包装下面那层的 API。例如 c_file 建立在 posix_file 之上，因为 POSIX 上的 C 标准库本身就建立在 POSIX 文件描述符之上。
  2. 当下面的运行时没有暴露可用 API 时，直接调用更底层的系统调用。从 c_file 往下到 posix_file 时常常如此，因为 libc 并不公开暴露它内部的 fd — 于是 fast_io 直接发起系统调用并包装结果。

在层之间转换

当你在层之间移动时，方向决定方法：

  • 由低到高（例如 posix_file → c_file → filebuf_file）：使用 ::std::move。句柄的所有权被向上转移。
  • 由高到低（例如 filebuf_file → c_file → posix_file）：用 static_cast 转换到底层的 io_observer。这给你一个对底层句柄的非拥有视图。

跨层转换也是允许的。你不需要一层一层地转换。例如可以直接从 nt_file（Windows 最低层）移动到 filebuf_file（最高层），跳过中间的 win32_file、posix_file 和 c_file： 


// Cross-layer conversion: skip intermediate layers
::fast_io::nt_file nf(u8"example.txt", ::fast_io::open_mode::out);

// Move directly from nt_file (layer 1) to filebuf_file (layer 6)
::fast_io::filebuf_file fbf(::std::move(nf), ::fast_io::open_mode::out);

// This works because filebuf_file's constructor accepts any lower-layer file type

同样地，你可以从任何高层的 static_cast 直接到任何低层的观察者： 


// Direct cast from filebuf_file to nt_io_observer (skipping intermediate layers)
::fast_io::filebuf_file fbf(/* ... */);
auto nt_iob{static_cast<::fast_io::nt_io_observer>(fbf)};
HANDLE handle{nt_iob.native_handle()};  // access the raw NT handle

这种灵活性让你能直接跳到需要的层，而不必繁琐地逐步转换。

特殊情况：nt_file 与 win32_file

尽管从 API 角度看 nt_file（第 2 层）与 win32_file（第 3 层）在概念上是不同的层，但在操作系统层面它们使用同一种 HANDLE 类型。如果你需要在它们的观察者之间转换，直接用 static_cast 即可： 


// Convert between nt_io_observer and win32_io_observer
::fast_io::nt_io_observer nt_iob(/* ... */);
auto win32_iob{static_cast<::fast_io::win32_io_observer>(nt_iob)};

// The reverse also works
auto nt_iob2{static_cast<::fast_io::nt_io_observer>(win32_iob)};


// Standard layer-by-layer conversion
::fast_io::posix_file pf(u8"example.txt", ::fast_io::open_mode::out);
::fast_io::c_file cf(::std::move(pf), ::fast_io::open_mode::out);

// Higher to lower: static_cast to observer for a non-owning view
auto piob{static_cast<::fast_io::posix_io_observer>(cf)};
int fd{piob.fd};  // access the raw handle

native_xxx 是什么意思？

::fast_io::native_file 是 fast_io 在当前平台上想用的最低不带缓冲层的别名。它在编译期被选定：

  • Linux、FreeBSD、macOS 等 → ::fast_io::native_file = ::fast_io::posix_file
  • Windows NT 家族（NT、2000、XP、7、10、11）→ ::fast_io::native_file = ::fast_io::nt_file
  • Windows 9x 家族（95、98、ME）→ ::fast_io::native_file = ::fast_io::win32_file

同样的别名规则适用于观察者：native_io_observer 在 POSIX 系统上是 posix_io_observer，在 Windows NT 上是 nt_io_observer。

带缓冲的类型 basic_iobuf_file 则是用 basic_native_file 定义的： 


template<::std::integral char_type>
using basic_iobuf_file = ::fast_io::basic_iobuf<
    ::fast_io::basic_native_file<char_type>>;

所以当你写 ::fast_io::iobuf_file f(u8"x.txt", open_mode::out); 时，你得到的是建立在“fast_io 认为属于你平台的 native 层”之上的带缓冲 I/O。

混用各层

因为每一层都通过概念暴露相同的 print / scan 接口，你可以自由混用它们： 


#include <fast_io.h>
#include <fast_io_device.h>
#include <fast_io_legacy.h>

int main()
{
    using namespace ::fast_io::iomnp;

    // Start at the bottom: a POSIX file descriptor.
    ::fast_io::posix_file pf(u8"mixed.txt", ::fast_io::open_mode::out);
    println(pf, u8"Line 1 via posix_file");

    // Move it up to a C FILE*.
    ::fast_io::c_file cf(::std::move(pf), ::fast_io::open_mode::out);
    println(cf, u8"Line 2 via c_file");

    // Move it up again to a C++ std::filebuf.
    ::fast_io::filebuf_file fbf(::std::move(cf), ::fast_io::open_mode::out);
    println(fbf, u8"Line 3 via filebuf_file");

    // All three lines end up in the same file, in order.
}

每次 ::std::move 都把句柄提升一层。所有权被转移，而不是被复制。

从系统调用级别的句柄构建 std::fstream

因为每一层都能通过 ::std::move 从下面那层构造，你可以从系统调用层开始，逐层上升，直到得到一个完全可用的 ::std::fstream： 


#include <fast_io.h>
#include <fast_io_legacy.h>
#include <fstream>

int main()
{
    using namespace ::fast_io::iomnp;

    // Start at the syscall level (posix on Linux/macOS, nt/win32 on Windows).
    ::fast_io::posix_file pf(u8"syscall.txt", ::fast_io::open_mode::out);

    // Move up: posix -> c
    ::fast_io::c_file cf(::std::move(pf), ::fast_io::open_mode::out);

    // Move up: c -> filebuf
    ::fast_io::filebuf_file fbf(::std::move(cf), ::fast_io::open_mode::out);

    // Transfer the filebuf into an std::ofstream
    ::std::ofstream fout;
    *fout.rdbuf() = ::std::move(*fbf.fb);

    // Now you can use the fstream like normal C++.
    fout << "Hello from a syscall-originated fstream!\n";
}

每次 ::std::move 都把句柄提升一层。所有权被转移，而不是被复制。这不是杂耍 — 这是每一层都与相邻层可互操作的自然结果。

从 iobuf_file 中取出原始文件描述符

因为各层是透明的，你可以从顶层开始一路下降回原始的 int fd。惯用做法是通过 static_cast 转换到合适的观察者类型： 


#include <fast_io.h>
#include <fast_io_device.h>

int main()
{
    using namespace ::fast_io::iomnp;

    // iobuf_file is buffered I/O on top of native_file.
    ::fast_io::iobuf_file bf(u8"demo.txt", ::fast_io::open_mode::out);
    println(bf, u8"Buffered write");

    // Flush so everything hits the underlying file before we peek at it.
    ::fast_io::flush(bf);

    // Step 1: obtain a posix_io_observer from the iobuf_file.
    //         On POSIX systems, iobuf_file's native file is posix_file,
    //         so this static_cast is lossless.
    auto piob{static_cast<::fast_io::posix_io_observer>(bf)};

    // Step 2: pull the raw int fd out of the observer.
    int const fd{piob.fd};

    print("The underlying fd is: ", fd);

    // The fd is still owned by `bf`; we only borrowed a view.
}

在 Windows 上同样的思路也成立，只是你要下降到 ::fast_io::nt_io_observer（或 ::fast_io::win32_io_observer），而原始句柄是 void* 而不是 int。

要点

把这六层背下来。它们不是随意的 — 它们反映了操作系统和编译器运行时实际是如何实现文件 I/O 的。理解这个层次结构能解释 FILE* 为何有这样的行为、mmap 为何比 fread 快，以及不同 API 在底下是如何相互关联的。
  • 这六层构成严格的层次：wine => nt => win32 => posix => c => filebuf。
  • 每一层包装它下面那层。当下面那层没有暴露可用 API 时，fast_io 直接调用内核并包装那个。
  • fast_io 为每一层提供包装，并让你自由混用各层。
  • native_xxx 是 fast_io 在当前平台最低层想用的那一层：POSIX 系统上是 posix_file，Windows NT 上是 nt_file，Windows 9x 上是 win32_file。
  • 你可以从系统调用级别的句柄出发，逐层移动构建出 ::std::fstream：posix_file → c_file → filebuf_file → ::std::ofstream::rdbuf()。
  • 你也可以往反方向下降：static_cast 到合适的 xxx_io_observer 得到一个非拥有视图，而观察者暴露了原始原生句柄。
