Ch17.1: Operators Are Functions

中文（简体）

1. The Substitution, Stated Precisely

An operator expression is a function call with a different spelling. The compiler rewrites it, then does ordinary overload resolution:

You write The compiler calls
a + boperator+(a, b)
a += ba.operator+=(b)
-aoperator-(a)
a[i]a.operator[](i)
a(b, c)a.operator()(b, c)
a == boperator==(a, b), and in C++20 also a.operator==(b) with the operands reversed if that is the only candidate
delete pp->~T() then operator delete(p) (Ch18.1)

Two consequences follow immediately. First, an operator is looked up exactly like a function: if it is a member, the left operand must be of that class; if it is not a member, argument-dependent lookup finds it in the namespace of its arguments. Second, an operator can be called explicitly by name, which is how you prove to yourself that nothing magical happens.

2. A Complete Example: the Canonical Shape

The shape every arithmetic value type should follow: a compound assignment as the primitive that mutates and returns a reference, and a binary operator defined on top of it that takes its operands by value and returns a new value. 


#include <fast_io.h>
#include <cstdint>

namespace money_ns
{

struct money
{
	::std::int_least64_t cents{};

	constexpr money &operator+=(money other) noexcept
	{
		cents += other.cents;
		return *this;
	}
};

[[nodiscard]] inline constexpr money operator+(money a, money b) noexcept
{
	return a += b;
}

}

int main()
{
	try
	{
		using money_ns::money;
		money const a{1250};
		money const b{375};
		::fast_io::io::println("a + b        = ", (a + b).cents);
		::fast_io::io::println("operator+(a,b)= ", operator+(a, b).cents);
		money c{a};
		c += b;
		::fast_io::io::println("c += b       = ", c.cents);
	}
	catch throws (::std::error e)
	{
		::fast_io::io::print("error: ");
		::fast_io::io::println(e);
	}
}


a + b        = 1625
operator+(a,b)= 1625
c += b       = 1625

Everything worth noticing is in those twenty-five lines:

  • operator+= is a member because its left operand is modified and is the object. It returns money&, not void, so that a = b += c keeps the meaning it has for int.
  • operator+ is a non-member in the same namespace. It takes both operands by value, adds into the copy of the left one, and returns it — the copy is elided or moved, so this is the cheapest correct spelling. Because it is a non-member, money{1} + money{2} and any implicit conversion on either side work symmetrically (see Ch17.3).
  • Both are constexpr and noexcept: addition of two integers cannot fail, so the type must not pretend it can (Ch6.16).
  • [[nodiscard]] on operator+ catches a + b; used as a statement — a discarded result that was almost certainly a bug.
  • operator+(a, b) in main is the same function. There is no separate mechanism.

3. What You Cannot Do

The feature is narrower than people expect. You cannot overload an operator unless at least one operand is a class or enumeration type: 


int operator+(int a, int b) { return a * b; }


error: ‘int operator+(int, int)’ must have an argument of class or enumerated type

You cannot invent an operator that does not exist, so no **, no <>, no &&&: 


s operator**(s a, s b) { return a; }


error: expected initializer before ‘*’ token

You cannot change an operator's arity, its associativity, or its precedence: a + b * c groups as a + (b * c) for your type too, and a.b.c cannot be redefined as multiply. And you cannot overload ::, ., .*, ?:, sizeof, alignof, typeid, or a cast operator other than to a type.

That last restriction is what makes operator overloading safe to reason about: an expression such as a + b * c means the same shape for every type in the program, so a reader's parser never has to be told about your class. Everything this chapter warns about is inside that shape: the punctuation is fixed, but its meaning is not, and that is where the trouble lives.

4. Member or Non-Member?

Operator Must be a member Must be a non-member Choose freely, prefer
=, [], (), -> yes
<<, >> (as stream I/O) member, unless you are doing iostreams — and you are not (Ch17.6)
+= -= *= /= and friends member: they modify the object
+ - * / == <=> non-member: symmetry, and implicit conversions on both sides
operator T() yes do not write it at all (Ch17.6)

The symmetry argument is the only one that matters in practice: 2 * v calls operator*(int, vec2), which can only exist as a non-member, while v * 2 would work either way. If v * 2 compiles and 2 * v does not, you have leaked an implementation choice into the type's interface.

5. Rules of Thumb

  • Write the compound assignment first, and define the binary operator in terms of it. That guarantees the two agree.
  • Binary operators take their operands by value and return by value. That is not a pessimisation; it is what enables copy elision.
  • Every operator you write is a function, so it needs a contract: noexcept or throws, no exceptions.
  • Mark value-returning operators [[nodiscard]].
  • If the operator's result is not the obvious mathematical result — if it allocates, if it can fail, if it only sometimes applies — stop here and read Ch17.2: you want a named function instead.
