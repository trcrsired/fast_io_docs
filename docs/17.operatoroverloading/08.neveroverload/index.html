Ch17.8: Operators That Should Not Exist

中文（简体）

1. The Five That Are Always Wrong

Five operators are wrong in every program, for reasons that do not depend on style. Each one is not a matter of taste: overloading it changes what the language promises about that expression.

Operator What overloading it destroys
&& Short-circuit evaluation. a && b becomes a function call, so b is computed even when a is false. Every "check the pointer, then dereference it" idiom silently stops working.
|| The same, on the other side.
, Sequencing. The built-in comma operator evaluates left to right and discards the left result; an overloaded one is an ordinary function call whose arguments are evaluated in unspecified order.
& (unary, address-of) Address-of. A feature C has had for half a century, and the one the language should never have handed out (§3).
operator T() Local reasoning about conversions. Any implicit conversion anywhere in the program can call it. The one exception is explicit operator bool, which is checked at the point of use.

2. && Measured

The short-circuit claim is not theoretical, and it is easy to demonstrate: make the right operand a function that announces itself, then compare the built-in operator with the user-defined one. 


#include <fast_io.h>

/* explicit operator bool: usable in a boolean context, invisible everywhere else */
struct handle_flag
{
	bool open{};

	[[nodiscard]] constexpr explicit operator bool() const noexcept
	{
		return open;
	}
};

/* the right operand: proves whether it was evaluated */
[[nodiscard]] inline bool right() throws
{
	::fast_io::io::print("  right() was evaluated\n");
	return true;
}

struct short_circuit
{
	bool value{};

	[[nodiscard]] constexpr explicit operator bool() const noexcept
	{
		return value;
	}
};

namespace bad
{
struct gate
{
	bool value{};
};

/* a user-defined operator&&: both operands are evaluated before the call */
[[nodiscard]] inline bool operator&&(gate, bool b) noexcept
{
	return b;
}
}

int main()
{
	try
	{
		handle_flag const f{};
		::fast_io::io::println("static_cast<bool>(f) = ", static_cast<bool>(f), "   !f = ", !f,
							   "   (f + 1 would not compile)");

		::fast_io::io::println("builtin && with a false left operand:");
		bool const r1{static_cast<bool>(short_circuit{false}) && right()};
		::fast_io::io::println("  result = ", r1);

		::fast_io::io::println("user-defined operator&& with a false left operand:");
		bool const r2{bad::gate{false} && right()};
		::fast_io::io::println("  result = ", r2);
	}
	catch throws (::std::error e)
	{
		::fast_io::io::print("error: ");
		::fast_io::io::println(e);
	}
}


static_cast<bool>(f) = 0   !f = 1   (f + 1 would not compile)
builtin && with a false left operand:
  result = 0
user-defined operator&& with a false left operand:
  right() was evaluated
  result = 1

In the built-in case the transcript has no line from right() — it was never called. In the user-defined case right() was evaluated before the operator ran, because an operator is a function and a function's arguments are evaluated before the call. If your type needs "and" semantics, write a && b with explicit operator bool and let the language do it, or write a named function (both(a, b), a.and_then(b)) and let the name say that both sides run.

The explicit operator bool in the same program is the conversion that is worth having: it works in if, while, !, and &&, and it does not participate in anything else. That is a compile-time guarantee, not a convention: 


handle_flag f;
int x{f + 1};


error: no match for ‘operator+’ (operand types are ‘handle_flag’ and ‘int’)

Compare that with the 1998 alternative, operator bool() without explicit: it converts to int, so f + 1 compiles, so does f < g and f && x and if (f == true), and the type's meaning dissolves. explicit is the difference between a type that behaves like a boolean and a type that turns into an integer when you are not looking.

3. operator&: the One That Broke the Language

Allowing operator& was a mistake, and not a mild one. Every other entry in this chapter destroys a convenience: short-circuiting, sequencing, a stream's error channel. operator& destroys the only operation by which a C program has ever referred to an object.

In C, &obj means "the address of obj". Full stop. There is no exception, no type can redefine it, and every interface in the language is built on that sentence: malloc's result is stored through &p, scanf writes through &n, memcpy takes &x. C++ kept the syntax and let any class take the sentence away: 


#include <fast_io.h>
#include <memory>

struct sneaky
{
	int v{};

	[[nodiscard]] sneaky *operator&() noexcept /* C++ lets you write this. Never write it. */
	{
		return nullptr;
	}
};

template <typename T>
[[nodiscard]] bool points_at_its_argument(T &ref) noexcept
{
	return &ref != nullptr; /* true for every type in the language, except the ones that lie */
}

int main()
{
	try
	{
		int plain{7};
		sneaky s{7};

		::fast_io::io::println("plain: &x != nullptr        ", ::fast_io::mnp::boolalpha(points_at_its_argument(plain)));
		::fast_io::io::println("sneaky: &x != nullptr       ", ::fast_io::mnp::boolalpha(points_at_its_argument(s)));
		::fast_io::io::println("&s == nullptr               ", ::fast_io::mnp::boolalpha(&s == nullptr));
		::fast_io::io::println("::std::addressof(s) == null ", ::fast_io::mnp::boolalpha(::std::addressof(s) == nullptr));
		::fast_io::io::println("s.v                         ", s.v);
	}
	catch throws (::std::error e)
	{
		::fast_io::io::perrln("error: ", e);
	}
}


plain: &x != nullptr        true
sneaky: &x != nullptr       false
&s == nullptr               true
::std::addressof(s) == null false
s.v                         7

Read the third and fourth lines together. &s is nullptr, and the object is perfectly alive at a real address. There is no diagnostic, no warning, and no way for a caller to notice: a template that writes &ref — which is what every container, every wrapper, every sorting algorithm and every debugger does — silently receives a lie. That is the false on line two, where line one is true for every other type in the language.

The scar tissue: std::addressof

The standard library had to be given a way out, and it is one function with one job: 


  template<typename _Tp>
    [[__nodiscard__,__gnu__::__always_inline__]]
    inline _GLIBCXX17_CONSTEXPR _Tp*
    addressof(_Tp& __r) noexcept
    { return __builtin_addressof(__r); }

  // _GLIBCXX_RESOLVE_LIB_DEFECTS
  // 2598. addressof works on temporaries
  template<typename _Tp>
    const _Tp* addressof(const _Tp&&) = delete;

That is libstdc++'s <bits/move.h>, and it is worth staring at: std::addressof is not an algorithm and not a library feature. It is compiler magic with a standard name — __builtin_addressof — and the whole reason it exists is that & stopped meaning what & means. The deleted rvalue overload (LWG 2598) exists for the same reason: if & had kept its meaning, none of this wording would be needed.

So the cost of the feature is not paid by the type that overloads it. It is paid by every template in the world, which must now write ::std::addressof(x) where the language should have let it write &x; and by every reader who has to know that &x is not the address of x unless x's type was written by somebody who declined a feature. And it is paid unevenly: whether std::addressof is even available to you depends on your standard library and on whether you are freestanding at all. Chapter 20 takes that up, because the answer there is not "always".

Why was it allowed? The historical answer is COM. In the Microsoft object model a smart pointer conventionally answered &p with a T**, so that a function could install a fresh interface pointer into it, and call sites read CoCreateInstance(..., &p, ...). That convention is now unrecoverable: &p means "the address of p" to every template and "the address of the T* inside p" to every COM call site, and nothing in the type system tells them apart. If you want that out-parameter idiom, give it a name — p.address_for_init() — and let &p keep its meaning.

The rule for your own code has no exceptions: never overload unary &. Do not overload binary & either, for the arithmetic reason in Ch17.3 — if your type has a bitwise-and, the reader has to know which meaning was intended. And do not write an interface that requires one: a type that needs &x to mean something else has an interface problem that a named function solves.

4. << and >>: the Stream Operators

These deserve their own paragraph because they are the most overused operators in C++ and because Ch18.5 already establishes that iostreams cannot be used: they rely on virtual inheritance, on cross-DLL type_info identity, and on exception handling that most platforms do not have. What remains worth saying is why the operator form is wrong even where iostreams work.

  • << means two different things. For integers it is a bit shift; for streams it is "format this value into the stream and return the stream". The same glyph, two unrelated operations, chosen by whether the left operand is a stream.
  • It has no error channel. Failure is recorded in the stream's state bits, so std::cout << a << b cannot fail where you can see it; you must remember to check std::cout.fail() later, and nobody does.
  • It hides direction. a >> b reads like a comparison and is actually "read from a into b", with the arrows pointing the wrong way for most readers.
  • It is not extensible in one place. Formatting policy (encoding, width, base, locale, buffering) has to be threaded through a global stream object, because the operator has no place for it.

fast_io's answer is a pair of named functions and a customization point: ::fast_io::io::print(...) and ::fast_io::io::scan(...) for the call, and print_define / scan_define for the type's participation (Ch15.11). The format is an argument, the failure is a throws contract, and the type is printed by an overload found in its own namespace instead of by a global operator.

5. The Clever Operators

Then there is a category that is not wrong by rule but wrong in practice: punctuation that stands for an operation the glyph does not mean.

Written Actually means Write instead
p1 / p2 on paths join two paths with a separator, allocating a new string join(p1, p2)
a | b on flags or sets union, or bitwise-or, or pipe a value into a transform — three meanings set_union, with_flag
a & b similarity score, in some libraries similarity(a, b)
a ^ b symmetric difference, in some libraries symmetric_difference(a, b)
a * b on matrices a multiply that allocates, or a Hadamard product, depending on the library matmul(a, b)
a! as factorial a call to operator!, which cannot express failure or size factorial(n), and note that it overflows

The rule that separates this table from Ch17.3 is the four-question test from Ch17.2: if the operation can allocate, can fail, or means different things in different libraries, then it is not an arithmetic operation and it does not get arithmetic punctuation.

6. operator new and operator delete

Class-level allocation functions are the last member of this category, and they get a whole page because they are the one case where the operator is not just misleading but actively dangerous: it changes the allocation policy of every object of the type, is invisible at the call site, cannot be reported by the type system, and bakes an ABI decision into your header. See Ch18.7.

7. Rules of Thumb

  • Never overload &&, ||, ,, or &. There is no exception, and & is the worst of the four: it breaks a promise C has kept since 1972, and the repair cost the standard library a compiler intrinsic called std::addressof (§3).
  • explicit operator bool is the only conversion operator worth writing. Everything else gets a named function (to_integer(), as_string()).
  • No operator<< or operator>>. Use print, scan, and their customization points.
  • If the glyph's everyday meaning is not the operation's meaning, the operation gets a name.
  • Never operator new / operator delete at class level (Ch18.7).
