Ch11.16: Wine File APIs

中文（简体）

Overview

Wine (“Wine Is Not an Emulator”) lets Windows binaries run on POSIX systems such as Linux and FreeBSD. Wine implements the Win32 and NT APIs by translating them into host system calls — and those host system calls ultimately use POSIX file descriptors.

A Windows binary cannot call write(2): it only knows HANDLEs. So when fast_io code running as a Windows module needs the host file descriptor that Wine keeps underneath a HANDLE, it cannot get there with <windows.h> alone — it needs a bridge that lives on the host side and speaks a fixed C ABI. That bridge is libwineunix, and fast_io exposes it through:

  • ::fast_io::wine_file — an RAII owning wrapper over a Wine host file descriptor.
  • ::fast_io::wine_io_observer — a non-owning view over an existing Wine host file descriptor.

IMPORTANT — wineunix.dll is not shipped with fast_io. fast_io only contains its own private view of the bridge’s ABI, in include/fast_io_hosted/platforms/wine/: the imports are declared with __asm__ labels bound to the DLL’s export names, so a translation unit that includes both fast_io and Wine’s own <__wine_unix/__wine_unix.h> sees no collision and needs no winelibc headers. The DLL itself you must build yourself, from https://github.com/trcrsired/libwineunix. Until you do, ::fast_io::wine_file has nothing to call at link time and nothing to load at run time.

Building wineunix.dll Yourself

The implementation is a separate project: https://github.com/trcrsired/libwineunix. Clone it, build it, and put the result next to your own .exe. It produces up to three artifacts, and which ones you need depends on where the program will run:

Artifact Kind What it is for
wineunix.dll PE dynamic library The bridge the Windows side links against. Exports the __wine_unix_* C ABI.
libwineunix.so host shared object The unix half. It is what the DLL calls when it runs under Wine; without it the DLL can only use the NT path.
libwineunix.a PE import library Generated by llvm-dlltool from def/wineunix.def. Your .exe links this once.

The CMake build is driven by these options:

Option Default Meaning
LIBWINEUNIX_UNIXLIB ON Build libwineunix.so with the host compiler. Needs a non-Windows host.
LIBWINEUNIX_WINEUNIX_DLL OFF Build the PE wineunix.dll.
LIBWINEUNIX_WINEUNIX_IMPL bundled bundled, unixcall or nt — see below.
LIBWINEUNIX_IMPORT_LIB ON Generate libwineunix.a with llvm-dlltool.
LIBWINEUNIX_PE_CXX clang++ The PE-targeting driver. The PE side is compiled by a separate windows-targeting compiler, not by the project compiler.
LIBWINEUNIX_PE_CXXFLAGS empty Extra flags for that driver (e.g. --target=x86_64-w64-windows-gnu, --sysroot=...).
LIBWINEUNIX_PE_MACHINE derived llvm-dlltool -m machine for the import library (i386:x86-64, arm64, ...). Derived from CMAKE_SYSTEM_PROCESSOR when left empty.
LIBWINEUNIX_FAST_IO_TEST OFF Build a test .exe that drives this very page’s layer. Point LIBWINEUNIX_FAST_IO_INCLUDE at the fast_io/include directory.

A build that exercises the whole stack under Wine looks like this: 


git clone https://github.com/trcrsired/libwineunix
cmake -S libwineunix -B libwineunix/build \
      -DLIBWINEUNIX_WINEUNIX_DLL=ON \
      -DLIBWINEUNIX_IMPORT_LIB=ON \
      -DLIBWINEUNIX_FAST_IO_TEST=ON \
      -DLIBWINEUNIX_FAST_IO_INCLUDE=/path/to/fast_io/include \
      -DLIBWINEUNIX_PE_CXXFLAGS="--target=x86_64-w64-windows-gnu --sysroot=/path/to/sysroot"
cmake --build libwineunix/build

# unixcall path: the DLL calls libwineunix.so
WINEDLLPATH=libwineunix/build wine libwineunix/build/fast_io_winetest.exe

# NT path: the DLL never touches the unixlib
wine libwineunix/build/fast_io_winetest.exe

The bundled implementation is what you normally want: one DLL that carries both paths, chosen at run time. Under Wine it resolves libwineunix.so and calls through it; on a real Windows machine the same binary forwards to ntdll instead. One .exe, one DLL, no rebuild and no DLL swapping between the two worlds:

  • under Wine: your.exe → wineunix.dll → libwineunix.so → libc
  • on Windows: your.exe → wineunix.dll → ntdll

unixcall builds the DLL with only the first path (it then requires libwineunix.so and runs under Wine only); nt builds it with only the second. Those exist for testing the halves in isolation, not for shipping.

Because the import library is a plain PE import library, linking is ordinary: link libwineunix.a once and place wineunix.dll next to the executable.

The Pattern Is the Same

Every layer in fast_io follows the same shape:

  1. An owning RAII type named xxx_file.
  2. A non-owning observer type named xxx_io_observer.
  3. Full support for print, println, and scan.
  4. The ability to wrap raw handles from outside code.

wine_file is no exception. Conceptually it looks like this: 


#include <fast_io.h>
#include <fast_io_device.h>

int main()
{
    try
    {
        using namespace ::fast_io::iomnp;

        // Opens a file through the Wine host layer.
        ::fast_io::wine_file wf(u8"hello_wine.txt", ::fast_io::open_mode::out);

        print(wf, "Hello from wine_file!\n");

        ::std::size_t const n{42zu};
        println(wf, "The answer is: ", n);
    }
    catch throws (::std::error e)
    {
        ::fast_io::perrln(e);
        return 1;
    }
    return 0;
}

Wrapping a Wine Host File Descriptor

When Wine translates a Windows CreateFileW call it ends up with a host POSIX file descriptor, and the DLL can hand you that number. Wrapping it in a wine_io_observer lets you keep using fast_io on it without taking ownership — the observer never closes a descriptor it did not open: 


#include <fast_io.h>
#include <fast_io_device.h>

// Non-owning view over a host fd that Wine owns.
void write_via_wine(::fast_io::wine_host_fd_t host_fd) throws
{
    using namespace ::fast_io::iomnp;

    ::fast_io::wine_io_observer observer{host_fd};

    // The DLL surfaces a failed host write as a herbception, like every other
    // device in this chapter.
    println(observer, u8"Written through a wine_io_observer\n");
}

int main()
{
    try
    {
        write_via_wine(::fast_io::wine_stdout().native_handle());
    }
    catch throws (::std::error e)
    {
        ::fast_io::perrln(e);
        return 1;
    }
    return 0;
}

::fast_io::wine_stdout(), wine_stdin() and wine_stderr() are the standard-stream observers of this layer, and they are the one place where the two DLL implementations differ visibly: the unixcall path yields unix_fd + 1, the NT path yields the process’s StandardOutput handle, and both are wrapped as a host fd so the rest of your code cannot tell them apart. That +1 is not cosmetic — read the next section before you pass a host fd anywhere.

A Host fd Is Not a Unix fd: the +1 Bias

This is the one place where guessing produces silently wrong I/O. On the implementations that carry a POSIX descriptor, the number inside a ::fast_io::wine_host_fd_t is the real descriptor plus one: 


host_fd = unix_fd + 1     // encoding, done once at the boundary
unix_fd = host_fd - 1     // decoding, done once at the boundary

So ::fast_io::wine_stdout().native_handle() is 2, not 1; wine_stdin() is 1 and wine_stderr() is 3. And 0 is not a descriptor at all — it is “nothing”. That is the whole reason for the bias: a negative descriptor has to be expressible as an unsigned host_fd, and without it real descriptor 0 and the null sentinel would collide. Decoding rejects 0 with EBADF for the same reason.

Forgetting the bias does not fail loudly — it addresses the neighbour. Hand fd 1 to something that expects a host fd and it is decoded as descriptor 0, so writes land on stdin, and a close() shuts a descriptor you never opened. Nothing reports an error; the wrong stream simply receives your bytes.

The bias is also implementation-defined, which is why you should not decode by hand when you can avoid it. Ask ::fast_io::wine::wine_unix_is_unix(): nonzero means the calls run through the unix backend (libwineunix.so under Wine) and the numbers are biased descriptors; zero means the NT backend, where the same host_fd slot holds a Windows HANDLE reinterpreted as an integer, with no bias at all. The same applies to directory descriptors: do not write -100 or 0 yourself, call ::fast_io::wine::wine_unix_at_fdcwd(), which is AT_FDCWD + 1 on one backend and a -3 sentinel on the other.

When you really do need the descriptor back, the conversion is one subtraction — and the order matters, because ::fast_io::wine_host_fd_t is unsigned: 


#include <fast_io.h>
#include <fast_io_device.h>

// Recover the descriptor a unix-backend host fd names. Only meaningful when
// wine_unix_is_unix() is nonzero: on the nt backend host_fd is a HANDLE and
// no bias was ever applied.
int host_fd_to_unix_fd(::fast_io::wine_host_fd_t host_fd) throws
{
    if (host_fd == 0)
    {
        // 0 is the null sentinel, never stdin.
        throw throws ::std::errc::bad_file_descriptor;
    }
    // Decode first: host_fd is unsigned, so subtracting from a biased negative
    // descriptor wraps, and the sign is only meaningful after the cast.
    int unix_fd{static_cast<int>(host_fd - 1)};
    if (unix_fd < 0)
    {
        throw throws ::std::errc::bad_file_descriptor;
    }
    return unix_fd;
}

int main()
{
    try
    {
        int const fd{host_fd_to_unix_fd(::fast_io::wine_stdout().native_handle())};
        // 2 - 1 == 1: stdout, as the host libc numbers it.
        ::fast_io::perrln("wine stdout is host fd ", fd);
    }
    catch throws (::std::error e)
    {
        ::fast_io::perrln(e);
        return 1;
    }
    return 0;
}

Note that this helper is for descriptors. A directory token from wine_unix_at_fdcwd() decodes to AT_FDCWD itself (-100), so a real implementation keeps that one negative value instead of rejecting it — the fast_io side never needs to, because host_dirfd parameters are passed straight back to the DLL.

Why Does This Layer Exist?

Wine is a complex piece of infrastructure. Code that lives inside Wine (for example, Wine's own implementation of ntdll.dll or kernel32.dll) needs to:

  • Receive a Windows HANDLE from guest code.
  • Translate it into a host int fd via Wine's internal table.
  • Perform host I/O on that fd while still being able to surface errors back to the guest as NTSTATUS codes.

fast_io’s Wine layer does that without winelibc: platforms/wine/api.h declares the DLL’s exports itself, with __asm__ labels bound to the export names, and the flag values mirror Wine’s own ABI. A Windows module that already uses fast_io therefore gains host I/O by linking one import library — no second toolchain, no winelib, no recompiling the world.

Relationship to the Other Layers

On a POSIX host running Wine, the full layering looks like this:

  • A guest Windows binary calls WriteFile. That resolves, inside Wine, to ntdll!NtWriteFile.
  • Wine’s ntdll translates that to a host POSIX write(2) call on a host fd — and that fd is what wine_file wraps.
  • fast_io code in the same process can bypass that path entirely: wine_file asks wineunix.dll for the host descriptor and writes to it directly.

So from the guest's point of view, the I/O went through the NT layer. From the host's point of view, it went through POSIX. wine_file lives at the seam between the two.

Summary

  • ::fast_io::wine_file is the RAII wrapper for Wine host file descriptors.
  • ::fast_io::wine_io_observer is the non-owning view.
  • The bridge is wineunix.dll + libwineunix.so from github.com/trcrsired/libwineunix. You build it yourself: fast_io ships only the ABI declarations, and the import library is yours to generate with llvm-dlltool.
  • The bundled DLL works in both worlds at once: the unixlib under Wine, ntdll on real Windows.
  • Everything here is throws: opening, reading, writing and flushing all report failures as herbceptions, exactly like posix_file, win32_file and nt_file.
  • It lives at the boundary between a Windows guest and the POSIX host that Wine runs on.
