Ch11: I/O

中文（简体）

Overview

This chapter covers fast_io’s I/O system — the core of the library. We will learn how to perform file I/O, define custom types for printing and scanning, use manipulators, understand the operations layer, and work with every level of the OS file API.

Important assumption: This chapter assumes you are running in a standard hosted environment with full filesystem access. If you are running in an application sandbox (e.g., app sandboxes, browser WASM sandbox, container restrictions) or a freestanding environment (e.g., embedded systems without an OS, kernel development), many of the assumptions about file I/O break down. We will discuss these special environments in future chapters.

Every example in this chapter is a complete program that handles its errors. I/O is the one part of a program that fails as a matter of routine, so this chapter never pretends otherwise — read section 0 before anything else.

0. I/O Fails. Constantly. Handle It.

Every earlier chapter dealt with values you computed, and a computation either produces its result or it does not. I/O is not like that. The file is not there. The disk is full. The directory is not writable. The pipe reader went away. The socket was reset by the peer. The device is busy, the network mount timed out, the quota was exceeded, the descriptor table is full. None of these are exceptional events on a real system: they are Tuesday. A chapter that teaches I/O without showing how the failure is reported and handled would be teaching you to write programs that die in the field.

So the rule for this whole chapter is the rule from Ch6.16, applied where it matters most: anything that talks to a device is a throws operation, and every program below catches what it throws. There is exactly one handler shape, and you will see it in every single example in this chapter: 


#include <fast_io.h>
#include <fast_io_device.h>

int main()
{
    try
    {
        ::fast_io::obuf_file obf(u8"out.txt");
        ::fast_io::io::println(obf, "written only if the disk accepted it");
    }
    catch throws (::std::error e)
    {
        ::fast_io::perrln(e);
        return 1;
    }
    return 0;
}

The try covers the whole body, not just the constructor. Opening can fail, writing can fail, and flushing can fail; which one it was is the handler’s job to find out, not the program’s job to guess. Read Ch3.16 for every member of ::std::error and Ch7.7 for how the same handler works in a constexpr context.

IMPORTANT — the rules for this chapter.
  • Never drop a handler. catch (...) does not catch herbceptions, and catch (::std::error) without throws is not valid C++. The only handler that catches a failure is catch throws (::std::error e).
  • Put the handler as high as you can. In a program that does one job, that is main. In a long-running service it is the top of whatever loop supervises the work. Do not sprinkle handlers into every helper: a helper that reports is more useful than a helper that prints and continues.
  • Do not swallow. The empty handler catch throws (::std::error) { } is legal and occasionally correct (see Ch6.16 §4), but it is wrong here: I/O errors are exactly the errors a program can usually do something about.
  • Reporting is I/O too. ::fast_io::perrln(e) writes to stderr and can itself fail. That is why it lives in main: if printing the error fails there is nowhere left to report it, and returning non-zero is the last honest answer.
  • A destination you never flushed has not reported anything. Buffered writes succeed into a buffer. The write that can fail happens at flush or close — which is why the try encloses the closing brace of every buffer in this chapter, and why you should scope buffers or call flush()/close() inside the try when the outcome matters.

Two habits follow from this, and both of them are visible in the code on every page of this chapter:

  • Handle by meaning, not by number. An error carries a domain and a code; e.domain() tells you which code space it belongs to and e.code() which failure inside it. A handler that switches on the domain can tell “the file is not there” from “this process may not open it” from “the device is gone”, and do something different about each. A handler that only prints is still far better than none.
  • Let every step be fallible on paper. When you read print(f, x) in this chapter, read it as “attempt print”. Every call to a device is a question with two answers, and the code you are reading is the version that answers both.

Key Takeaways

  • I/O is layered: device, buffer, operation and formatting are separate concerns.
  • Every operation can fail; handle the error at the boundary where you can act on it.
  • Prefer print, scan and transmit; scan requires buffered input.
  • The OS APIs are exposed directly, so know which layer you are calling.
  • Processes and pipes use the same file-shaped model: redirect the three standard handles, close unused pipe ends, and use transmit for byte movement.
