Ch3.16: Herbceptions

IMPORTANT — this is the most important page of this chapter. Every single page before this one quietly assumed that nothing can fail. From here on, nothing is quiet: every error in fast_io is reported as a herbception. Herbceptions are the only way errors are reported in this tutorial and in the library. If you skip this page, the rest of the tutorial will not compile.

Overview

In Ch3.2 you learned the compound statement. A try block is a compound statement with a contract attached: if something inside fails, control does not run to the next line — it runs into the handler below.

Herbceptions are C++’s error-reporting mechanism designed for exactly that contract, without the machinery of legacy C++ exceptions (stack unwinding, heap allocation, exception objects, std::exception hierarchies, RTTI walks). An error is a value: a pair of two machine words.

In this chapter you will learn:

  • how to build with -fherbceptions -lherbceptions — and which compilers support it
  • the throw throws statement
  • the try { } catch throws (::std::error e) { } statement
  • every member function of ::std::error
  • every error domain the runtime ships with, and how to report one
  • why a herbception costs nothing on the happy path

1. What a Herbception Actually Is

A herbception is a two-word error value: 


struct raw_herbception
{
    ::std::error_domain_singleton const *domain;   // which error code-space
    ::std::size_t code;                            // the code inside that space
};

That is sizeof(::std::error) == 2 * sizeof(void *), no matter what the error is. It travels back to the caller in the return registers, together with one failure bit in the condition register — CF on x86, NZCV.C on AArch64. There is no second return path:

  • no stack unwinding, no .eh_frame unwinding tables, no personality routines
  • no heap allocation for an error object — ever
  • no std::exception base class, no what(), no RTTI
  • the error is a value, it is not "thrown" in the legacy sense, nothing is captured

Consequence: herbceptions are very, very cheap, on both paths. The happy path of a function that reports errors this way is the same code a function returning an error code would produce — the error value is simply not stored, only a flag says "success". The failure path is also just a return: the two-word payload rides the return registers like any other aggregate. There is no "zero-cost-exceptions tradeoff" to weigh here, and no reason to avoid reporting an error because "throwing is expensive". Do not worry about the performance of the thrown path, and do not worry about the happy path either.

Note: because there is no unwinding, a herbception does not run destructors on the way out. Local objects in the failing function are destroyed normally — the failure is a return, and returns destroy locals — but the the error value itself is just a pair of integers.

2. The Toolchain: -fherbceptions -lherbceptions

Herbceptions are a compiler feature, not a library trick. You need a compiler that implements them, and only our GCC and LLVM builds do:

  • GCC: our herbceptions GCC fork (g++ 17+ from the herbceptions toolchain build).
  • Clang / LLVM: our herbceptions LLVM fork (clang++ 24+).
  • MSVC is not supported. cl.exe has no -fherbceptions, so you cannot compile this tutorial with MSVC. Windows builds are still fine — use our Clang with a Windows target, or our MinGW GCC.

Both compilers need the same two flags:

  • -fherbceptions — turns the language feature on. It must be passed when compiling every translation unit, not only when linking.
  • -lherbceptions — links the runtime library, which owns the error domains’ vtables (the code that names and formats an error).

That is all: the herbceptions runtime and headers are part of the toolchain you installed, so -lherbceptions is the entire addition. A complete native build with our Clang: 


clang++ --config=$HOME/cfgs/x86_64-linux-gnu-libcxx.cfg \
  -O3 -flto=thin -fherbceptions \
  -I$HOME/libraries/fast_io/include \
  hello.cpp -lherbceptions -o hello

./hello

and with our GCC (plain g++, no paths needed): 


g++ -std=c++26 -O3 -fuse-ld=lld -fherbceptions \
  -I$HOME/libraries/fast_io/include \
  hello.cpp -lherbceptions -o hello

./hello

Windows, from Linux, with the same flags (cross-compilation is just a target switch). The MSVC sysroot carries the Windows herbceptions runtime (herbceptions.lib to link, herbceptions.dll at run time), so --sysroot finds it and there is no -L to write: 


# Clang, MSVC ABI
clang++ --config=$HOME/cfgs/x86_64-windows-msvc.cfg \
  -O3 -flto=thin -fherbceptions \
  -I$HOME/libraries/fast_io/include \
  hello.cpp -lherbceptions -o hello.exe

# our MinGW g++ (reuses the same herbceptions.dll; -lntdll because fast_io talks to NT directly)
x86_64-w64-mingw32-g++ -std=c++26 -O3 -s -fherbceptions \
  -I$HOME/libraries/fast_io/include \
  hello.cpp -lherbceptions -lntdll -o hello.exe

wine ./hello.exe

If a Windows binary fails to start, ask it what a DLL does not resolve to: 


wine $HOME/softwares/win-ldd/x86_64-windows-msvc/win-ldd.exe ./hello.exe

If you forget -fherbceptions, the compiler rejects the syntax outright. If you forget -lherbceptions, the compile succeeds and the link fails on the domain symbols.

3. The throw throws Statement

Reporting an error is a statement: 


throw throws expression;

throws is the marker that says "this error travels through the herbception channel". The expression is a value of any type that has an ::std::error_domain specialization — in practice one of the standard error enums listed in section 6. The whole statement ends with ;, exactly like an assignment. 


#include <fast_io.h>

using namespace ::fast_io::io;

int read_count(int n) throws
{
    if (n < 0)
    {
        throw throws ::std::errc::invalid_argument;   // report and leave
    }
    return n * 2;
}

int main()
{
    try
    {
        print("result: ", read_count(-1), "\n");
    }
    catch throws (::std::error e)
    {
        print("failed: ", e, "\n");
    }
}

Output: 


failed: [posix](22)Invalid argument

Three rules govern the statement, and the compiler enforces all three:

  • It must be inside a function declared throws (or return_failure{...}, which we cover later). Writing throw throws inside a noexcept function is a compile error: 'throw throws' is only allowed inside a function declared 'throws' or 'return_failure{...}'. This is the whole point: a function that cannot fail cannot lie about failing.
  • It does not return. Nothing after the statement runs in that path, so you do not need a return after it.
  • Rethrowing is throw throws; — with no operand — and is only valid inside a catch throws handler. 

int inner(int b) throws
{
    if (b == 0)
    {
        throw throws ::std::errc::invalid_argument;
    }
    return b;
}

int outer(int b) throws
{
    try
    {
        return inner(b);
    }
    catch throws (::std::error e)
    {
        print("inner failed: ", e, "\n");
        throw throws;              // rethrow: pass it to our own caller
    }
}
Validate early, report once. Check the precondition at the top of the function and throw throws immediately. That is how fast_io itself is written: a constructor that cannot open the file fails at the constructor, not three calls later when the handle is first used.

4. The try { } catch throws (::std::error e) { } Statement

Handling is a statement too, and it has exactly one shape: 


try
{
    /* code that may fail */
}
catch throws (::std::error e)
{
    /* handler: inspect / report / recover / rethrow */
}

The rules, again enforced by the compiler:

  • The handler must declare ::std::error by value. Not by reference, not by const&, not ::std::errc, not ::std::exception. The compiler says so: 'catch throws' must declare std::error by value, not '::std::errc'.
  • You cannot store or copy the error. ::std::error has a deleted copy constructor, a deleted move constructor, and no default constructor. Only the compiler can create one, and only the handler owns it. Read what you need out of it inside the handler body.
  • The handler may be unnamed: catch throws (::std::error) { }. Use this form when you only need to swallow a failure you cannot do anything about — for example when a noexcept function is forced to call something fallible.
  • catch (...) does not catch herbceptions, and it is forbidden in this tutorial. A call to a throws function is only considered handled if there is a catch throws block around it; a legacy catch-all does not count and the program does not compile.
  • catch (::std::error e) — without throws — is not valid either. It is a legacy-EH handler; the compiler rejects it with call to deleted constructor of '::std::error'. Legacy C++ exception handling is not part of this tutorial; herbceptions replace it completely. 

#include <fast_io.h>

using namespace ::fast_io::io;

int read_count(int n) throws
{
    if (n < 0)
    {
        throw throws ::std::errc::invalid_argument;
    }
    return n * 2;
}

// a noexcept function may still call a fallible one,
// provided it handles the failure itself
int read_count_or_zero(int n) noexcept
{
    try
    {
        return read_count(n);
    }
    catch throws (::std::error)
    {
        return 0;
    }
}

int main()
{
    print(read_count_or_zero(-1), "\n");   // 0
    print(read_count_or_zero(21), "\n");   // 42
}

5. ::std::error: Every Member Function

::std::error is deliberately tiny: two pointers, one destructor, and a handful of observers. There is nothing else to learn. This is the complete list.

Expression Result Meaning
e.domain() ::std::error_domain_singleton const * Which code-space the error belongs to. Never null inside a handler.
e.code() ::std::size_t The raw code inside that domain — for POSIX errors it is the errno value.
e == ::std::errc::permission_denied bool Exact match: same domain and same code. Works with any domain’s value on either side of ==; the argument type selects the domain.
e.equivalent(::std::errc::no_such_file_or_directory) bool Cross-domain match: asks the domain whether the error means the same thing as the given code. An HTTP 404 is equivalent to ENOENT, a Win32 ERROR_FILE_NOT_FOUND too.
e.to_errc() ::std::errc The POSIX equivalent of the error, as a ::std::errc. For a POSIX-domain error this is the identity; for any other domain the runtime demotes it.
e.is_code_of<::std::http_errc>() bool "Was this error produced by this domain?", ignoring the code. This is the domain-membership test; e == value is the code test.
::std::herbception_cast<::std::tls_alert>(e) ::std::tls_alert Converts the payload back into the domain’s own value type. Only exists for domains that define the conversion (today: tls_alert).
e.throw_legacy_exception() [[noreturn]] void Bridge into legacy C++ EH (for code that still uses catch (::std::exception const&)). Mentioned only. We do not teach legacy EH in this tutorial — it is covered later, once you know enough to defend yourself against it. 

#include <fast_io.h>

using namespace ::fast_io::io;

int main()
{
    try
    {
        throw throws ::std::http_errc::not_found;
    }
    catch throws (::std::error e)
    {
        print("domain is http: ", e.is_code_of<::std::http_errc>(), "\n");   // 1
        print("is posix:       ", e.is_code_of<::std::errc>(), "\n");         // 0
        print("== not_found:   ", e == ::std::http_errc::not_found, "\n");     // 1
        print("== ok:          ", e == ::std::http_errc::ok, "\n");            // 0
        print("== errc ENOENT: ", e == ::std::errc::no_such_file_or_directory, "\n"); // 0
        print("equivalent:     ", e.equivalent(::std::errc::no_such_file_or_directory), "\n"); // 1
        print("to_errc:        ", static_cast<int>(e.to_errc()), "\n");       // 2
        print("code:           ", e.code(), "\n");                            // 404
    }
}

Note the difference between == and equivalent in that output: the error is not an ENOENT (different domain, so == is false), but it means the same thing, so equivalent is true.

6. Reporting an Error with fast_io

Because an error is just {domain, code}, fast_io can print it, and it does so through the same print you already know. The default layout is: 


[domain-name](code)message


#include <fast_io.h>

using namespace ::fast_io::io;

int main()
{
    try
    {
        throw throws ::std::errc::no_space_on_device;
    }
    catch throws (::std::error e)
    {
        perrln(e);                                        // whole line to stderr
        perr("plain print: ", e, "\n");                   // inside a larger line
        perr("only the name: ", ::fast_io::mnp::name(e), "\n");
        perr("only the text: ", ::fast_io::mnp::message(e), "\n");
        perr("posix name:    ", ::fast_io::mnp::posix_equivalent_name(e), "\n");
        perr("posix message: ", ::fast_io::mnp::posix_equivalent_message(e), "\n");
    }
}

Output: 


[posix](28)No space left on device
plain print: [posix](28)No space left on device
only the name: posix
only the text: (28)No space left on device
posix name:    posix
posix message: (28)No space left on device
  • e alone — the full [domain](code)message form.
  • ::fast_io::mnp::name(e) — the domain name only.
  • ::fast_io::mnp::message(e) — the code and text, without the domain name.
  • ::fast_io::mnp::name_message(e) — the same as printing e.
  • ::fast_io::mnp::posix_equivalent_name / _message / _name_message(e) — the same three, but for the POSIX equivalent of a non-POSIX error, so a log line always speaks errc.
Style used in this tutorial: the handler reports, it does not swallow. catch throws (::std::error e) { ::fast_io::perrln(e); return 1; } in main, and throw throws; everywhere else.

7. Every Error Domain

A domain is a code-space. Each one is a type with an ::std::error_domain specialization, and each has its own code() packing. These are all of them — there is no "user domain" chapter here, because you do not define domains: you use them. To report a failure you pick the domain that describes the failure, and throw throws one of its values.

Domain value type Printed tag code() is What it describes
::std::errc [posix] the errno value POSIX / C errors: invalid_argument, no_such_file_or_directory, permission_denied, no_space_on_device, connection_reset, ... The default domain of the whole library.
::std::parse_errc [parse] 1 = end_of_file, 2 = partial, 3 = invalid, 4 = overflow Text parsing and scanning failures, independent of any OS.
::std::cmath_errc [parse] (see note) the FE_* flag bits Floating-point exceptions: invalid, divbyzero, inexact, overflow, underflow.
::std::http_errc [http] the HTTP status code HTTP responses: not_found (404), im_a_teapot (418), internal_server_error (500), ...
::std::tls_alert [tls] (level << 8) | description TLS alerts, carrying both fields: level (warning/fatal) and description (certificate_expired, bad_record_mac, handshake_failure, ...).
::std::win32_errc [win32] the GetLastError() / ERROR_* value Windows API failures. Windows targets only.
::std::nt_errc [nt] the NTSTATUS / STATUS_* value NT native API failures. Windows targets only.
::std::com_errc [com] the HRESULT value COM failures. Windows targets only.
::std::wine_errc [wine] Wine’s own UNIX errno values Host-side errors reported by Wine’s ntdll unixlib. Windows targets running under Wine.
::std::exception_ptr [itanium] / [msvc] an identity for a boxed legacy-EH object The legacy C++ exception domain: what you get when code that still uses throw std::runtime_error(...) crosses a herbceptions boundary. Mentioned so you recognise it; we teach legacy EH later, not here.
Note on cmath_errc: the current herbceptions runtime reports it under the [parse] tag. Treat the tag as a runtime detail, not as part of the interface — compare with e.is_code_of<::std::cmath_errc>() or e == ::std::cmath_errc::overflow, not with the printed text.

Reporting one error per domain


#include <fast_io.h>

using namespace ::fast_io::io;

// the handler reports and returns, so the helper itself is 'throws'
void report_and_continue(auto fn) throws
{
    try
    {
        fn();
    }
    catch throws (::std::error e)
    {
        perrln(e);            // reporting can fail too -- then it propagates
    }
}

int main()
{
    // POSIX
    report_and_continue([]() throws {
        throw throws ::std::errc::no_such_file_or_directory;
    });
    // parsing
    report_and_continue([]() throws {
        throw throws ::std::parse_errc::invalid;
    });
    // floating point
    report_and_continue([]() throws {
        throw throws ::std::cmath_errc::overflow;
    });
    // HTTP
    report_and_continue([]() throws {
        throw throws ::std::http_errc::not_found;
    });
    // TLS: level + description
    report_and_continue([]() throws {
        throw throws ::std::tls_alert{
            ::std::tls_alert::alert_level::fatal,
            ::std::tls_alert::alert_description::certificate_expired};
    });
}

(A program that actually used the helper would wrap its body in try { } catch throws (::std::error e) { perrln(e); return 1; }, because report_and_continue is throws.)

Output (native build, Linux): 


[posix](2)No such file or directory
[parse](3)Invalid format
[parse](8)Unknown
[http](404)Not Found
[tls](2:45)Fatal: Certificate Expired

win32_errc{5} (ERROR_ACCESS_DENIED) 5 13 errc::permission_denied
nt_errc{0xC0000022} (STATUS_ACCESS_DENIED) 3221225506 13 errc::permission_denied

That last column is the whole reason equivalent() and to_errc() exist: a Win32, NT, COM and POSIX failure with completely different numeric codes can still be one test, e == ::std::errc::permission_denied is false for the Windows values (different domain) while e.equivalent(::std::errc::permission_denied) is true for all of them.

Which domain should you pick? In portable code, ::std::errc. Use a platform or protocol domain only when the code comes from that platform or protocol — a failed GetLastError() is a win32_errc, a TLS alert from the peer is a tls_alert, and an HTTP status you want to propagate is an http_errc. Do not translate: herbceptions carry the original code-space, and equivalent() / to_errc() do the translation at the point where somebody needs POSIX semantics.

8. There Is No "Uncaught Herbception"

A herbception that reaches the top of the program has nobody to be handed to, so the process traps — on x86-64 the kernel raises SIGILL, and you get a core dump, not a pretty message: 


#include <fast_io.h>

int f(int b) throws
{
    if (b)
    {
        throw throws ::std::errc::no_space_on_device;
    }
    return b;
}

int main()
{
    ::fast_io::println(f(1));   // no handler: the program dies here
}


$ ./a.out
Illegal instruction (core dumped)

That is by design: an unreported error is a bug, and the fastest way to notice a bug is to stop. Two consequences shape how you write main:

  • main cannot be declared throws. The compiler refuses: 'main' cannot be declared with a herbceptions ('throws'/'return_failure{...}') exception specification; 'main' has no caller able to consume an error result, and uncaught errors in 'main' trap instead.
  • So main catches. This is the single exception to the rule you will learn in Ch6.16: every function besides main declares either noexcept or throws. main is the boundary where the error chain ends, so it is where errors get printed and turned into an exit code. 

#include <fast_io.h>

int main()
{
    try
    {
        ::fast_io::println("work");
    }
    catch throws (::std::error e)
    {
        ::fast_io::perrln(e);
        return 1;
    }
    return 0;
}

9. Where fast_io Fits In

Every fallible fast_io operation is declared throws, and every infallible one is noexcept. That includes I/O: 


#include <fast_io.h>

using namespace ::fast_io::io;

int main()
{
    // both print and scan report failures as herbceptions
    static_assert(!noexcept(println(1)));                      // can fail: write error
    static_assert(!noexcept(scan(::fast_io::c_stdin(),        // can fail: read/parse error
                                 ::std::declval<int&>())));

    int value{};
    try
    {
        print("give me a number: ");
        scan(::fast_io::c_stdin(), value);            // throws parse_errc on bad input
        print("you typed ", value, "\n");
    }
    catch throws (::std::error e)
    {
        perrln(e);
        return 1;
    }
    return 0;
}

You do not have to check return codes, and you do not have to inspect errno after a call: a call that fails leaves through the throws channel with the original code-space intact. The next chapters build on exactly that — file constructors, sockets, scanners, filesystem walks, everything reports failures this way.

10. Common Mistake Checklist

Mistake The compiler tells you
throw throws in a noexcept function 'throw throws' is only allowed inside a function declared 'throws' or 'return_failure{...}'
calling a throws function without handling it call to 'throws' function in a non-'throws' function must be handled by an enclosing 'try { } catch throws' block, or mark the calling function as 'throws' so herbceptions can propagate
catch throws (::std::errc e) 'catch throws' must declare std::error by value, not '::std::errc'
catch (::std::error e) (legacy handler) call to deleted constructor of '::std::error'
catch (...) { } around a throws call call to 'throws' function ... must be handled by an enclosing 'try { } catch throws' block
void f() noexcept throws 'throws'/'return_failure' and 'noexcept' cannot be combined
int main() throws 'main' cannot be declared with a herbceptions ... exception specification
forgetting -fherbceptions expected unqualified-id / unknown exception specification at the first throws
forgetting -lherbceptions undefined reference to __cxa_error_domain_* at link time

Key Takeaways

  • All errors in fast_io are herbceptions. There is no return-code error API to check and no legacy C++ exceptions in this tutorial.
  • Build with -fherbceptions (every TU) and -lherbceptions (link), using our GCC or LLVM builds. MSVC does not support it — on Windows use our Clang with a Windows target or our MinGW GCC.
  • Report with throw throws value; inside a throws function; handle with try { } catch throws (::std::error e) { }; forward with throw throws;.
  • The handler must declare ::std::error by value. It cannot be copied, stored, or constructed by you.
  • ::std::error has exactly: domain(), code(), ==, equivalent(), to_errc(), is_code_of<T>(), herbception_cast<T>(), and the legacy-EH bridge we will cover later.
  • The domains are errc, parse_errc, cmath_errc, http_errc, tls_alert, win32_errc, nt_errc, com_errc, wine_errc, plus the legacy C++ EH domain. Use them; do not define them.
  • Herbceptions are extremely cheap on both paths — the error rides the return registers next to a condition flag. Never choose an error-code style API "for speed", and never fear the failure path.
  • An uncaught herbception traps, and main cannot be throws — so main is where errors are printed and converted to an exit code.
