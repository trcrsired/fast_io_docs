Ch14.1: Ownership: The Destructor Starts the Rule

中文（简体）

1. A Handle Is Not a Value

::open returns an int, but the int is not the file. It is an index into a table the kernel owns. The same number can be reused for a different file after the first one is closed, and copying the number does not create a second file. Three properties follow:

  • It must be released. The table is finite. A descriptor that is never ::closed leaks a slot.
  • It has one owner while it is alive. Two objects that both believe they own the same number will both release it.
  • The number is not the resource. The open file description lives in the kernel; the number is only the handle.

The compiler has no idea which int is a handle and which is a count. It copies every int the same way. That is the entire source of the bugs in this chapter.

2. The Rule: A Destructor Changes the Copy

Write the destructor first, because it is the declaration that tells you the class owns something: 

class my_posix_file
{
    int fd_{-1};

public:
    explicit my_posix_file(::fast_io::cstring_view path, ::std::int_least32_t flags) throws;

    ~my_posix_file() noexcept
    {
        if (fd_ != -1)
        {
            ::close(fd_);
        }
    }
};

The compiler still generates a copy constructor and a copy assignment for this class. Both copy fd_. Both produce a second object that thinks it owns the same descriptor. The first destructor closes it; the second destructor closes the number again, which may now belong to an unrelated file. This is not a theoretical bug.

If a class has a destructor that releases a resource, it must declare its copy operations. Delete them, or write a correct copy. Leaving them implicit is the bug.

Warning: a destructor without a copy decision is a bug. If the class has a destructor but no = delete and no real copy constructor/copy assignment, the compiler will generate shallow copies. For a resource owner this is a double release, a use-after-release, or both. At minimum write: 
T(T const &) = delete;
T &operator=(T const &) = delete;
and then decide whether the type is also movable.

The safe default is deletion: 

    my_posix_file(my_posix_file const &) = delete;
    my_posix_file &operator=(my_posix_file const &) = delete;

These are declarations, not comments. They participate in overload resolution and the compiler rejects any attempt to copy the object. If the type should be movable, declare the move operations next; if it should not, delete them too: 

    my_posix_file(my_posix_file &&other) noexcept;
    my_posix_file &operator=(my_posix_file &&other) noexcept;

"Maybe move operations" is the right phrase. Moving is a separate capability. A non-movable type deletes all four copy/move operations and keeps only the destructor and the resource-owning constructor. A movable type implements the two moves and deletes the two copies. What you must not do is leave the copy implicit.

3. The C++ Primer Example

C++ Primer, Fifth Edition demonstrates the failure with HasPtr: a class that owns a std::string through a raw pointer and frees it in the destructor, but does not write the copy operations. The book uses new and delete. This tutorial uses the same example with fast_io's allocator and an explicit placement new, so the allocation policy is visible.

There are two allocator layers. ::fast_io::native_global_allocator is the untyped allocator: it hands out raw bytes. ::fast_io::native_typed_global_allocator<T> is the typed adapter: its allocate_die(1) reserves storage for one T with the right size and alignment. Neither one constructs the object. Placement new does that: 

#include <new>
#include <string>

using string_alloc = ::fast_io::native_typed_global_allocator<::std::string>;

std::string *make_string(std::string const &s)
{
    auto *p{string_alloc::allocate_die(1)}; // storage, not an object
    try
    {
        return ::new (static_cast<void *>(p)) std::string(s); // placement new
    }
    catch (...)
    {
        string_alloc::deallocate_n(p, 1);
        throw;
    }
}

void destroy_string(std::string *p) noexcept
{
    if (p != nullptr)
    {
        p->~basic_string();               // end the object's lifetime
        string_alloc::deallocate_n(p, 1); // return the storage
    }
}

allocate_die terminates on allocation failure, which is the policy this book uses; allocate and allocate_try are the throwing variants. The important part is the lifetime split: allocation gives you storage, placement new starts an object, the destructor ends it, and deallocate_n returns the storage. There is no delete and no mismatch between the allocator that produced the block and the one that frees it. 

class HasPtr
{
public:
    HasPtr(std::string const &s = std::string())
        : ps{make_string(s)}, i{} {}

    ~HasPtr() { destroy_string(ps); }

    // WRONG: the compiler generates these two.
    // They copy ps, not the string.
    // HasPtr(HasPtr const &) = default;
    // HasPtr &operator=(HasPtr const &) = default;

private:
    std::string *ps;
    int i;
};

Pass one by value and the bug becomes visible: 

HasPtr f(HasPtr hp)      // hp is a shallow copy
{
    HasPtr ret = hp;     // another shallow copy
    return ret;          // hp and ret are destroyed
}

int main()
{
    HasPtr p{"some values"};
    f(p);                // both destructors destroy p.ps
    HasPtr q{p};         // p.ps is already dangling
}

The parameter and the local copy share the same ps. When f returns, two destructors run on one pointer: a double destruction and a double deallocation. The caller's object is left dangling, so the next copy reads freed memory. The destructor was correct; the implicit copy was not.

The fix is one of two explicit choices. If copying has no meaning, delete it: 

    HasPtr(HasPtr const &) = delete;
    HasPtr &operator=(HasPtr const &) = delete;

Now f(p) and HasPtr q{p} fail to compile. If copying is meaningful, write a real copy that allocates its own string; that is Ch14.3 and Ch14.4.

4. Chromium Had the Same Bug at Scale

This is not only a teaching example. Chromium's ChromeDriver 130 release notes record a rule-of-five cleanup: an out-of-line destructor was declared without matching move operations, so the compiler silently fell back to copies. The fix added the missing declarations. The relevant change is crrev.com/c/5846757, tracked as crbug.com/364788123.

The compiler accepted the code. The symptom appeared somewhere else. That is the signature of a missing special member: the language gives you a default, and the default is wrong for an owner. HasPtr is the smallest version of the same failure; Chromium is the same failure across a large codebase.

5. What This Chapter Builds

The running example is a move-only file: 

class my_posix_file
{
    int fd_{-1};

public:
    my_posix_file() noexcept = default;
    explicit my_posix_file(::fast_io::cstring_view path, ::std::int_least32_t flags) throws;

    ~my_posix_file() noexcept;

    my_posix_file(my_posix_file const &) = delete;
    my_posix_file &operator=(my_posix_file const &) = delete;

    my_posix_file(my_posix_file &&other) noexcept;
    my_posix_file &operator=(my_posix_file &&other) noexcept;

    void swap(my_posix_file &other) noexcept;

    [[nodiscard]] bool is_open() const noexcept;
    [[nodiscard]] ::std::int_least32_t native_handle() const noexcept;
};

A file descriptor is an identity, not a value. Two descriptors for the same file are possible, but they are a deliberate system call (::dup), not something the compiler should do behind your back. Deleting copy states that clearly. Moving is still useful: returning a file from a factory, storing it in a container, or passing ownership to another scope.

fast_io's own file types make the same choice: they are movable, not copyable. The reduced class here keeps only what the rule needs, so every declaration can be checked against the code on the page.

6. The Five Members, and the One Decision

Declaration Question it answers For this class
~my_posix_file() Who closes the descriptor? ::close, once, in one place.
my_posix_file(my_posix_file const&) What does a copy own? = delete: a copy would be a second owner.
operator=(my_posix_file const&) What happens on copy assignment? = delete, for the same reason.
my_posix_file(my_posix_file&&) How is ownership transferred? Take fd_, leave -1.
operator=(my_posix_file&&) How is ownership replaced? Close ours, take theirs, empty the source.

The decision is not "five functions or none". It is "does this class own a resource?" If it does, the destructor starts the rule, and the copy operations are the first thing you must make explicit.
