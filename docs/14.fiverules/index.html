Ch14: The Rule of Five

中文（简体）

1. The Rule Is Not "Write Five Functions"

The name is misleading. The rule of five does not say that every class should have five hand-written special members. It says that the five special members are a package: if you declare one of them, you must decide what happens to the others. Most classes should declare none of them. A class that owns a resource must declare all of the ones it needs.

C++ Primer introduces the copy constructor, copy assignment and destructor first, then states the rule. This chapter starts with the destructor, because the destructor is the warning sign: once a class says "I release a resource", the copy question is forced. The mechanics are the same; the order is chosen to make the bug obvious earlier.

The dangerous case is smaller and sharper than the name suggests:

If a class has a destructor that releases a resource, the compiler-generated copy constructor and copy assignment are almost certainly wrong. Declare them = delete, or write a correct copy. Never leave them implicit.

The destructor says "this object owns something and must release it." The implicit copy says "copy the handle." Those two statements cannot both be true. The result is two objects that believe they own the same resource: a double release, a use-after-release, or both.

Warning: a destructor without = delete is a bug. If you write a destructor and leave the copy operations implicit, the compiler will shallow-copy the handle. At minimum declare both copy operations deleted. If the type is also movable, declare the moves; if not, delete those too.

2. C++ Primer's HasPtr: The Minimal Bug

C++ Primer, Fifth Edition uses this example in its copy-control chapter. The class owns a std::string through a raw pointer and frees it in the destructor, but it leaves copy construction and copy assignment to the compiler. The allocation helpers make_string and destroy_string use fast_io's allocator and placement new; they are introduced in Ch14.1. 

class HasPtr
{
public:
    HasPtr(std::string const &s = std::string())
        : ps{make_string(s)}, i{} {}

    ~HasPtr() { destroy_string(ps); }

    // WRONG: copy construction and copy assignment are compiler-generated.
    // They copy ps, not the string.

private:
    std::string *ps;
    int i;
};

Now pass one by value: 

HasPtr f(HasPtr hp)      // hp is a copy of the argument
{
    HasPtr ret = hp;     // another copy of the same pointer
    // ...
    return ret;          // ret and hp are destroyed here
}

int main()
{
    HasPtr p{"some values"};
    f(p);                // hp and ret both delete p.ps
    HasPtr q{p};         // p.ps is already dangling
}

The parameter hp is a shallow copy of p: it holds the same ps pointer. The local ret is another shallow copy. When f returns, both destructors run and both call delete on the same pointer. That is a double free. The caller's p is left with a dangling pointer, so the next HasPtr q{p} copies a pointer that is already invalid. The bug is not in the destructor; it is in the copy the compiler wrote.

The fix is not a comment. It is a declaration: 

class HasPtr
{
public:
    HasPtr(std::string const &s = std::string())
        : ps{make_string(s)}, i{} {}

    ~HasPtr() { destroy_string(ps); }

    HasPtr(HasPtr const &) = delete;
    HasPtr &operator=(HasPtr const &) = delete;

private:
    std::string *ps;
    int i;
};

f(p) and HasPtr q{p} now fail to compile. That is the point: the bug has been moved from run time to compile time. If copying is meaningful, the alternative is to write a real copy constructor and copy assignment that allocate a new string; the two choices are "delete" and "implement", never "leave it to the compiler".

3. Chromium Has Paid for This Bug at Scale

This is not a textbook-only concern. Chromium's ChromeDriver 130 release notes record a rule-of-five cleanup across classes where an out-of-line destructor was declared without matching move operations, so the compiler silently fell back to copies. The missing declarations were added for exactly the reason above: a destructor plus an implicit copy is an ownership bug waiting to happen.

The relevant Chromium change is crrev.com/c/5846757, tracked as crbug.com/364788123. The fix is mechanical, but finding it is not: the compiler accepted the code, and the symptom appeared somewhere else. That is the signature of a missing special-member declaration.

C++ Primer's HasPtr is the smallest possible version of the same failure. Chromium is the same failure repeated across a large codebase. The rule is the same at both scales.

4. The Five Members, as a Package

Member What it decides If you own a resource
~T() How the resource is released Write it. This is the declaration that starts the rule.
T(T const&) What a new object owns when copied = delete, or allocate/duplicate a real resource.
operator=(T const&) What an existing object owns after assignment = delete, or release the old and acquire a real one.
T(T&&) How a dying object's resource is taken Implement it if the type should be movable; otherwise delete it.
operator=(T&&) How an existing object takes over and empties the source Implement it if the type should be movable; otherwise delete it.

The compiler does not generate a move constructor or move assignment if the class has a user-declared destructor, copy constructor or copy assignment. That is why a destructor alone silently leaves you with copies, and why "delete the copy" is usually followed by "write the moves" or "delete the moves too".

The best outcome is still the rule of zero: own no raw resource at all. Put the int inside a type that already implements the rule, and let composition generate the special members for you. This chapter is about the day you cannot do that.

5. Two Running Examples

The chapter uses two owners to teach the same rule. The first is memory: C++ Primer's HasPtr, which allocates storage with fast_io's native_typed_global_allocator<std::string>, constructs the string with placement new, and explicitly destroys and deallocates it in the destructor. The second is a file descriptor: my_posix_file, which owns a POSIX descriptor acquired by ::open and released by ::close. It is deliberately move-only, like fast_io's own file types: a descriptor is an identity, not a value, so copying it is not allowed. The skeleton is: 

class my_posix_file
{
    int fd_{-1};

public:
    my_posix_file() noexcept = default;
    explicit my_posix_file(::fast_io::cstring_view path, ::std::int_least32_t flags) throws;

    ~my_posix_file() noexcept;

    my_posix_file(my_posix_file const &) = delete;
    my_posix_file &operator=(my_posix_file const &) = delete;

    my_posix_file(my_posix_file &&other) noexcept;
    my_posix_file &operator=(my_posix_file &&other) noexcept;

    void swap(my_posix_file &other) noexcept;
};

The copy operations are not missing. They are deleted, explicitly, in the class. That is the difference between a class that compiles and a class that is correct.

7. How to Read This Chapter

Read 14.1 and 14.2 as the rule. Read 14.3 and 14.4 as the two legitimate answers for a copy: delete it, or write a real one. Read 14.5 and 14.6 because most resource-owning types are movable even when they are not copyable. Read 14.7 to 14.10 as the mechanics that make the good implementations safe. Read 14.11 as the complete class.

If your class has no raw resource, stop at the rule of zero: write none of the five and let the compiler do its job. The rest of this chapter is only for the classes that actually own something.
