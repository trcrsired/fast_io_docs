Ch14.3: Copy Construction: Delete It, or Deep-Copy It

中文（简体）

1. The Compiler's Copy Is Shallow

A copy constructor is called whenever a new object is made from an existing one. If you do not declare one, the compiler writes a member-wise copy. For a class that owns a resource, that copy is almost always wrong.

The C++ Primer HasPtr from the previous page is the minimal example. Its destructor destroys the string through ps; its compiler-generated copy copies the pointer: 

HasPtr f(HasPtr hp)      // hp is a shallow copy
{
    HasPtr ret = hp;     // another shallow copy
    return ret;          // both destructors destroy ps
}

The parameter and the local object share one std::string. When the function returns, the same pointer is destroyed twice, and the caller's object is left dangling. The bug is not that the destructor exists. The bug is that the copy was left implicit.

There are exactly two valid answers: delete the copy, or write a copy that acquires its own resource. There is no third answer called "let the compiler do it".

Warning: the implicit copy is not a copy of the resource. If the class owns a handle, the compiler's copy constructor copies the handle. That is why a class with a destructor must declare = delete for both copy operations, or write real ones. "I have a destructor" is the warning sign; "the compiler will handle the copy" is the bug.

2. Answer One: = delete

This is the default for a resource owner. The class owns a handle; copying the handle would create a second owner. Delete both copy operations: 

class my_posix_file
{
    int fd_{-1};

public:
    explicit my_posix_file(::fast_io::cstring_view path, ::std::int_least32_t flags) throws;
    ~my_posix_file() noexcept;

    my_posix_file(my_posix_file const &) = delete;
    my_posix_file &operator=(my_posix_file const &) = delete;

    my_posix_file(my_posix_file &&other) noexcept;
    my_posix_file &operator=(my_posix_file &&other) noexcept;
};

The two deleted functions are declarations. The compiler uses them during overload resolution and rejects a copy with a clear error: 

error: use of deleted function 'my_posix_file::my_posix_file(const my_posix_file&)'
error: use of deleted function 'my_posix_file& my_posix_file::operator=(const my_posix_file&)'

This is what you want. The incorrect program does not compile, and the error points at the copy. If you want the type to be movable, declare the move operations as well. If not, delete them too; a non-movable owner is a perfectly valid type.

Declaring the copy constructor deleted also prevents the compiler from generating a move constructor. That is why the move declarations above are explicit. A deleted copy and a missing move leaves the type neither copyable nor movable, which is correct for a non-movable owner and a surprise for a type that should be movable.

3. Answer Two: A Real Deep Copy

If copying has a clear meaning, write a copy constructor that creates a new resource. For HasPtr, that means a new std::string: 

class HasPtr
{
public:
    HasPtr(std::string const &s = std::string())
        : ps{make_string(s)}, i{} {}

    HasPtr(HasPtr const &other)
        : ps{other.ps ? make_string(*other.ps) : nullptr},
          i{other.i}
    {
    }

    ~HasPtr() { destroy_string(ps); }

private:
    std::string *ps;
    int i;
};

The new object has its own ps. Destroying one object does not affect the other. The null check is there because a moved-from HasPtr may have a null pointer once move operations are added; a copy constructor should still be safe.

A deep copy is a real operation with a real cost: one allocation and one string copy. That cost is why deletion is the default for handles. A file descriptor can be duplicated with ::dup, but that is a deliberate system call that creates a second descriptor for the same open file; it is not what the compiler's member-wise copy does. If you want that semantics, write it explicitly and document the sharing.

4. What std::move Does When Copy Is Deleted

::std::move does not move anything. It casts to an rvalue reference and makes a move constructor eligible. If the move constructor is not declared, overload resolution falls back to the copy constructor. If the copy constructor is deleted, the fallback is a deleted function, so the program does not compile: 

my_posix_file a{"demo.txt", O_RDONLY};
my_posix_file b{::std::move(a)}; // error if no move constructor is declared

That is the correct behavior for a move-only owner: transferring ownership must be explicit in the class, not an accidental copy. The move constructor itself is Ch14.5.

5. What to Remember

  • The implicit copy is member-wise; for a handle, that means a second owner.
  • If the class has a destructor that releases a resource, declare the copy.
  • Default to = delete for unique ownership.
  • Write a deep copy only when copying has a defined meaning and a documented cost.
  • Delete both copy construction and copy assignment; they are one decision.
  • If the type is movable, declare the moves; if not, delete them too.

The next page applies the same decision to copy assignment: delete it, or write a real assignment with a critical line.
