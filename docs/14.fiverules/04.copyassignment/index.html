Ch14.4: Copy Assignment: Delete It, or Use the Critical Line

中文（简体）

1. Copy Construction and Copy Assignment Are One Decision

Copy construction creates a new object. Copy assignment changes an existing object that already owns something. They are different operations, but they answer the same policy question: does this type allow a second owner?

If the answer is no, delete both: 

    my_posix_file(my_posix_file const &) = delete;
    my_posix_file &operator=(my_posix_file const &) = delete;

A class with a deleted copy constructor but a usable copy assignment is almost always a mistake. The two operations should agree, and the compiler will not enforce that for you. Make the pair explicit in the class.

Warning: deleting only one of the pair is incomplete. If you write T(T const &) = delete; but leave the copy assignment implicit, the compiler may still generate an assignment that shallow-copies the handle. Delete both, or implement both.

2. If You Choose Copy: The Critical Line

Assignment has a problem that construction does not: the left-hand object already owns a resource. The function must release the old resource and acquire a new one. The only question is the order, and the wrong order is the one everyone writes first: 

    // WRONG: destroy first
    HasPtr &operator=(HasPtr const &other)
    {
        destroy_string(ps);              // old string gone
        ps = make_string(*other.ps);     // may fail; *this is now broken
        i = other.i;
        return *this;
    }

If the allocation fails, the object has already lost its old value and has nothing to replace it with. Do the fallible work first, into a local, while the object is still untouched: 

    HasPtr &operator=(HasPtr const &other)
    {
        auto *new_ps{make_string(*other.ps)}; // may fail, *this untouched
        destroy_string(ps);                   // ---- critical line ----
        ps = new_ps;
        i = other.i;
        return *this;
    }

Above the line: the allocation may fail, and *this is unchanged. Below the line: destroy_string and the pointer/integer writes cannot fail, so the object moves from the old value to the new one without an intermediate broken state. That is the strong exception safety guarantee.

This order also makes self-assignment safe without a special case. If this == &other, the new string is allocated and copied before the old old string is destroyed, then the pointer is replaced. The object ends up with a new string holding the same value. No data is lost.

3. The Whole Deep-Copy Class

class HasPtr
{
public:
    HasPtr(std::string const &s = std::string())
        : ps{make_string(s)}, i{} {}

    HasPtr(HasPtr const &other)
        : ps{other.ps ? make_string(*other.ps) : nullptr},
          i{other.i}
    {
    }

    HasPtr &operator=(HasPtr const &other)
    {
        auto *new_ps{other.ps ? make_string(*other.ps) : nullptr};
        destroy_string(ps);
        ps = new_ps;
        i = other.i;
        return *this;
    }

    ~HasPtr() { destroy_string(ps); }

private:
    std::string *ps;
    int i;
};

This class is copyable, so it must also handle move operations or accept that moves fall back to copies. The move operations are a separate decision; see Ch14.5 and Ch14.6. The important part here is that copy assignment is explicit: it knows about the old resource, and it has a critical line.

4. The Return Type and the Self-Check

Return *this by reference so assignment chains and behaves like the built-in assignment: 

a = b = c; // parsed as a = (b = c)

A self-check is not required when you allocate before deleting. It is required when the implementation releases first, because then a = a destroys the value before reading it. If you write the safe order, do not add a check just because tutorials do; if you write the unsafe order, the check is not enough to fix the failure path.

The same reasoning applies to move assignment, but the order is forced: a move has no duplicate to allocate, so it must release first, and therefore it must check for self-move. That asymmetry is covered in Ch14.6.

5. The Two Valid Answers

Ownership Copy constructor Copy assignment
Unique (file, socket, lock) = delete = delete
Copyable with a real resource (deep copy) Allocate/duplicate a new resource Allocate first, then commit below the critical line

There is no third row for "leave it to the compiler". If the class has a destructor, that row is the bug.

6. What to Remember

  • Delete copy construction and copy assignment together, or implement both correctly.
  • Assignment must release the old resource, but only after the new one is secured.
  • The critical line separates fallible preparation from infallible commit.
  • Allocate before destroy; self-assignment then works without a special case.
  • Return *this by reference.
  • Move assignment has the opposite order and does need a self-check.
