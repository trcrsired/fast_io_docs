Ch18.9: Virtual Inheritance and the Diamond

中文（简体）

Why This Page Is Separate

Ch18.2 covers ordinary virtual dispatch: the vptr, the vtable, the indirect call. This page covers a different feature that happens to share the same keyword. virtual in a base-class list is virtual inheritance, and it exists to make multiple inheritance share one base subobject instead of duplicating it.

It is not a better form of inheritance, and it is not a reuse tool. It is a layout and lifetime mechanism for a specific shape: the diamond.

1. Virtual Inheritance: The Diamond

virtual in a base-class list is a different feature from virtual on a function. It solves a different problem: multiple inheritance can put more than one copy of a common base into one object. 

struct base
{
    int id{};
    virtual ~base() = default;
};

struct left : base
{
    int l{};
};

struct right : base
{
    int r{};
};

struct bottom : left, right
{
    int b{};
};

A bottom object now contains two base subobjects: one through left, one through right. The name id is ambiguous, and so is the conversion to base&: 

bottom x;
// x.id = 1;            // error: ambiguous, which base?
// base &br = x;        // error: ambiguous base

left &l = x;
right &r = x;
base &bl = l;           // the base inside left
base &br = r;           // the base inside right

The two bases also have separate state. If base holds an id, a change through bl is not visible through br. For a true "is-a" diamond — one shared base subobject — declare the inheritance from base as virtual: 

struct left : virtual base
{
    int l{};
};

struct right : virtual base
{
    int r{};
};

struct bottom : left, right
{
    int b{};
};

Now bottom has exactly one base subobject, shared by the left and right branches. The name is no longer ambiguous: 

bottom x;
x.id = 1;               // OK: one shared base
base &br = x;           // OK: one shared base
left &l = x;
base &bl = l;           // still refers to the same shared base

2. Layout and Construction

The cost is layout. A virtual base cannot be placed at a fixed offset in every complete object, because the path to it depends on the most-derived type. The implementation usually adds a pointer or an offset table (a virtual base pointer, or vbptr) to the class, and access to a virtual base member becomes an indirect access. The standard does not mandate the layout; sizeof, offsets and the number of hidden pointers are ABI details. Do not build a wire format on them.

Construction order is the other sharp edge. Virtual base classes are constructed before non-virtual base classes, and the most-derived class is responsible for initializing the virtual base. Initializers for that virtual base in intermediate classes are ignored when the intermediate class is not the most-derived object: 

struct base
{
    base() { std::print("base\n"); }
};

struct left : virtual base
{
    left() : base{} { std::print("left\n"); }
};

struct right : virtual base
{
    right() : base{} { std::print("right\n"); }
};

struct bottom : left, right
{
    bottom() { std::print("bottom\n"); }
};

bottom x; // base, left, right, bottom

Destruction runs in the reverse order: bottom, right, left, base. If you write a constructor that assumes it controls the virtual base, test it both as a standalone object and as a base of a more-derived object. The same constructor can see different base initialization in the two cases.

3. Cross-Casts and the Alternative

Cross-casting between sibling branches needs RTTI. A static_cast from left* to right* is not allowed, because the compiler cannot know the offset without the complete object. dynamic_cast can find the shared base or the sibling subobject, but it requires a polymorphic type and a runtime search: 

bottom x;
left *lp = &x;
base *bp = dynamic_cast<base *>(lp); // shared virtual base
right *rp = dynamic_cast<right *>(lp); // sibling subobject, or nullptr

This is exactly the kind of code the rest of the chapter argues against: a runtime cast to recover a relationship that the type system could have expressed with composition. If you need a shared interface, prefer a pure interface with no data, or composition plus a reference. If you need shared state, make the sharing explicit with a pointer or a reference member, not with a virtual base.

Virtual inheritance is not a general-purpose code-reuse tool. It is for the narrow case where a diamond is genuinely part of the domain model and one shared base subobject is the correct semantic. It is expensive in layout, construction order and casts, and it is easy to get wrong. In new code, composition is almost always clearer.
